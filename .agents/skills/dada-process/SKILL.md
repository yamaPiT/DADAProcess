# DADAプロセス 標準開発ワークフロー

本スキルは、DADAプロセス全体の進行を制御するオーケストレーターです。各Phaseでは、指定されたペルソナスキル（`.agents/skills/` 配下）を読み込んで作業を実行します。

**工程順序（テストファースト）**: Phase 1 要求定義 → **Phase 2 総合テスト仕様** → **Phase 3 アーキテクチャ設計** → Phase 4 実装・総合テスト報告 → Phase 5 評価。
テスト仕様を設計より先に作るのは、「テストが書けない要求＝曖昧な要求」を設計・実装に流す前にPhase 1へ差し戻し、手戻りを最小化するためである。

## 起動時の状態判定（毎回必ず実行）

新しい会話でこのスキルを開始したら、**作業を始める前に**以下を上から順に行い、現在地を宣言すること。

1. `docs/process/last_phase_summary.md` を読む。
2. **実ファイルで裏を取る**: `python tools/dada_check.py all --summary` を実行し、どの開発文書が実在するかを1行で確認する（サマリーが古い・手で編集された場合の食い違いを防ぐため）。実行できない環境では `docs/artifacts/` の一覧を確認する。
3. 判定する。
   - サマリーの「次フェーズ」が具体的に記載されている場合 → **そのPhaseから再開**する。「承認済みドキュメント一覧」に記載されたファイルを読み込み、文脈を復元する。
   - 記載が空欄・テンプレートのままで、開発文書も存在しない場合 → **新規開発**である。Phase 0 から開始する。
   - サマリーと実ファイルが食い違う場合 → **推測で進めず、食い違いの内容をProduct Ownerに報告**して指示を仰ぐ。
4. 使用可能なツール一覧を確認して動作モード（次節参照）を決め、Phase 0の3判定（開発対象・実行モード・スケール）を行い、必ず最初の応答で以下の形式で宣言する。

   > 現在の状態: **[Phase N から再開 / 新規開発]**（根拠: last_phase_summary.md の記載と実ファイルの照合結果）
   > 開発対象: **[従来型プログラム / エージェント定義]**（根拠: Product Ownerの指示または成果物の性質。`.agents/AGENTS.md` 第9節）
   > 実行モード: **[承認ゲート型 / 自律型]**（根拠: 起動指示に自律実行の明示があるか。`.agents/AGENTS.md` 第10節）
   > 動作モード: **[ツールが自動的にサブエージェントを作る / 人間がサブエージェントを作る]**（根拠: エージェント開発/実行ツールがサブエージェントを自動作成できるか。推奨はツールが自動的にサブエージェントを作る）
   > 実行プロファイル: **[Guided / Autonomous]**（既定はGuided。`.agents/AGENTS.md` 第4節）

   **用語の区別（混同禁止）**: 「**実行モード**」は、DADAプロセス承認ゲート型か DADAプロセス自律型かの選択である。「**動作モード**」は、開いている**エージェント開発/実行ツール**（Antigravity）がサブエージェントを自動作成できるかによる技術的な差である。**ツールが自動的にサブエージェントを作る**か、**人間がサブエージェントを作る**かで分かれる。両者は独立しており、実行モード×動作モードの4通りすべてが成立する。これは冒頭の **P承認ゲート / P自律 / A承認ゲート / A自律**（開発対象×実行モードの4つの使い方）とは別軸である。**P承認ゲート / A承認ゲートの「A」（Agent）と動作モードを混同しないこと。** 実行プロファイルの **Autonomous**（手順のまとめ方）と、実行モードの **自律型**（工程の関門）も別である。

## フェーズ実行の方式（環境による切り替え）

実行環境によってアテンション・リセットの実現方法が異なる。**起動時の状態判定と同時に、自分の使用可能なツール一覧にサブエージェント起動ツール（`invoke_subagent` 等）があるかを確認し、動作モードを決めて宣言すること。**

**推奨は、ツールが自動的にサブエージェントを作る**ことである。人間がサブエージェントを作る動作は、エージェント開発/実行ツールがサブエージェントを自動作成できない環境のフォールバックである。Product Ownerが動作モードを指定する必要はない（開いているエージェント開発/実行ツールで自動判定する）。

| 実行環境 | サブエージェントの作り手 | 動作モード | 位置づけ |
| :--- | :--- | :--- | :--- |
| Antigravity 2.0 / Antigravity CLI | ツールが自動作成 | **ツールが自動的にサブエージェントを作る** | **推奨** |
| Antigravity IDE / Antigravity v1 | 人間が作成 | **人間がサブエージェントを作る** | 2.0 が使えないとき、または IDE 内だけで完結させるとき |

製品名で判別できない場合は、サブエージェント起動ツールの有無を唯一の判定基準とする。

### ツールが自動的にサブエージェントを作る（Antigravity 2.0 / CLI）（推奨）
- 各Phaseの作業を**独立したコンテキストを持つサブエージェントに委譲**する。メイン会話はオーケストレーターとして「Phase間の遷移・承認ゲートでのProduct Ownerとのやり取り」だけを扱い、全Phaseを通して存続する。
- サブエージェントへの指示に含めてよいのは、**(a) 適用するペルソナスキルのパス (b) `last_phase_summary.md` を最初に読む指示 (c) 入力となる承認済みドキュメントのパス (d) 成果物の出力先パス (e) Product Ownerからの明示的な指示** のみ。
- **メイン会話のチャット履歴・未確定の議論をサブエージェントへ要約して渡すことを禁止**する（承認済みドキュメントだけが真実である）。
- リセットの実現は `context-reset` の**方式A**。

### 人間がサブエージェントを作る（Antigravity IDE / v1）
- エージェント開発/実行ツールがサブエージェントを自動作成できないため、**人間が次Phase用のサブエージェント（新しいチャット）を作る**。
- 1つの会話が**現在のPhaseの作業を直接実行**する（ペルソナスキルを自分に適用する）。
- 承認ゲート通過後、`context-reset` スキルの方式B（手動リセット）でProduct Ownerに新しいチャットウィンドウの開始を依頼し、会話を終える。
- 次の会話のエージェントが「起動時の状態判定」により `last_phase_summary.md` から文脈を復元し、次Phaseを引き継ぐ。
- **例外（実行モードが自律型の場合）**: 方式Bは人間の操作を待つため、自律完走ができない。この場合は `context-reset` スキルの**方式C（自律連続実行）**を用い、同一会話内でサマリーを書き出してから次Phaseのペルソナスキルを召喚する。

## 共通原則
- **プロセスの遵守**: 基本原則（承認ゲート、アテンション-リセット、不変条件と手順の分離、機械的検証の委譲、スケール制御、ID体系、承認の定義等）はすべてワークスペースルール `.agents/AGENTS.md` に従うこと。
- **ドキュメント準拠性**: 基本は `docs/guidelines/dada_document_guidelines.md` に従う。ただしProduct Ownerから「IEEE29148_2018に準拠」等の規格指定や、「企業のテンプレートに従う」等の指示があった場合は、`docs/templates/` 配下の該当ひな形ファイルを読み込み、その構造を絶対的に優先すること。
- **開発対象がエージェント定義の場合の自動参照**: Phase 0で開発対象が「エージェント定義」と判定された場合、Product Ownerからのテンプレート指定を待たずに、`docs/guidelines/agent_design_principles.md` と `docs/templates/agent/` 配下の該当ひな形を参照すること（利用者がテンプレート名を指定する必要はない）。Product Ownerが別のテンプレートを明示した場合のみ、そちらを優先する。
- **進行状況の常時表示**: DADAプロセス実行中は、**すべての応答の末尾に**以下の1行を表示し、迷子を防ぐこと。

  `[DADA | Phase N: フェーズ名 | 状態: 作成中/レビュー中/承認待ち | 対象: プログラム/エージェント定義 | 承認ゲート型/自律型 | ツール自動/人間作成 | Guided/Autonomous]`

- **想定外の状況のエスカレーション**: 本スキルとAGENTS.mdのルールで判断できない状況に遭遇した場合、推測で進めず、作業を停止して状況と選択肢をProduct Ownerに報告すること。

## 禁止事項（オーケストレーション全体）
- **フェーズのスキップ禁止**: スケール判定（Phase 0）で省略が認められたPhase以外を飛ばしてはならない。
- **先行作業の禁止**: 承認ゲート通過前に、次Phaseの成果物（特にソースコード）を作り始めてはならない。「ついでに実装しておきました」は重大なプロセス違反である。
- **複数Phaseの一括実行禁止（承認ゲート型のみ）**: 実行モードが承認ゲート型の場合、1回の応答で複数の承認ゲートをまたいではならない。各ゲートで必ず停止し、Product Ownerの入力を待つこと。自律型では、後述の自律ゲートの条件をすべて満たす場合にのみ連続実行してよい。
- **承認の推定禁止**: `.agents/AGENTS.md` の「承認の定義」に該当しない発言を承認と見なしてはならない。**実行モードの推定も禁止**する。起動指示に自律実行の明示がなければ、承認ゲート型として扱う。
- **自律ゲートの条件の緩和禁止**: 自律型において、`.agents/AGENTS.md` 第10.3節の6条件を「概ね満たしている」という判断で通してはならない。1つでも欠ければ停止する。
- **自律遷移の無記録禁止**: 自律ゲートを通過・停止したのに `docs/process/autoloop_log.md` へ記録しないことを禁止する。

## 共通レビュー手順
Phase 1〜3で繰り返す標準手順。各Phaseでは以下のパラメータを指定して実行する。

| パラメータ | 説明 |
| :--- | :--- |
| **作成スキル** | 文書を作成・修正するペルソナスキル |
| **レビュースキル** | 文書を検証するペルソナスキル |
| **成果文書** | 出力する開発ドキュメントのパス |
| **レビュー記録** | 指摘と対応を記録するレビュー記録表のパス |
| **ひな形** | 新規作成時にコピーする出発点。**開発対象によって切り替わる**（従来型プログラム=作成スキルの `references/` 配下のスケルトン / エージェント定義=`docs/templates/agent/` 配下のファイル） |

1. **[作成]**: 作成スキルを読み込んでペルソナを適用し、成果文書を作成する。
2. **[機械チェック]**: スキル `dada-check` を実行する（`python tools/dada_check.py all`）。検出されたHigh・Mid指摘を作成者ペルソナのまま修正し、再実行して解消を確認する。
   - （目的: ID対応漏れ・曖昧語・空欄といった機械的な欠陥を、人間のレビュー前に消しておく。レビュアーが形式的な指摘に埋もれず、内容の妥当性の検証に集中できる）
3. **[レビュー]**: レビュースキルを読み込んでペルソナを適用。**機械チェックで検出済みの形式的欠陥ではなく、内容の妥当性**（要求の適否・テストの十分性・設計の適切さ・用語の一貫性・論理矛盾）を検証し、指摘をレビュー記録に記録する。
4. **[修正・記録]**: 作成スキルのペルソナに戻り、指摘を修正してレビュー記録に対応結果を記録する。（レビュー→修正は最大2周。**2周目のレビューは全文を見直さず、各レビュアースキルの「2周目以降の再レビュー」に従いOpen指摘と変更箇所だけを対象とする。**残ったHigh指摘は隠さず次項で報告する）
5. **[ゲート]**: 実行モードによって分岐する。**判断に迷う場合は必ず5-A（人間の承認）を選ぶ。**

   **5-A: 承認ゲート（実行モードが承認ゲート型の場合）**
   以下の定型で報告し、Product Ownerの承認を待つ。**承認が得られるまで次の作業を一切行わない。**

   > Phase N（フェーズ名）の成果物が完成しました。
   > - 成果文書: [パス]
   > - 機械チェック: [`dada_check.py` の要約行をそのまま貼る / 未実行の場合はその理由]
   > - 自己レビュー: 指摘N件（うち解消M件、残課題K件）→ 詳細は [レビュー記録のパス]
   > - 残課題・TBD: [なし / 内容]
   > - 手順からの逸脱: [なし / 何をどう置き換えたか1行]
   > ご確認のうえ、承認いただけますか？（修正点があれば、チャットまたはREV101への記入でご指摘ください）

   **5-B: 自律ゲート（実行モードが自律型の場合）**
   `.agents/AGENTS.md` 第10.3節の6条件を**1つずつ順に確認**し、結果を判定する。

   1. `python tools/dada_check.py all` を実行し、**終了コード**を確認する（`0` 以外なら遷移不可）。Phase 4では加えて `python tools/dada_check.py report` の終了コードが `0` であること。
   2. レビュー記録表（`REV101_*.md`）を開き、Open のHigh指摘がゼロであることを確認する。
   3. 当該Phaseの「完了条件」を、保存済みファイルを読み直して全項目確認する。
   4. 開発対象がエージェント定義の場合、Phase 2以降は評価セットの定義（およびPhase 4では `docs/process/eval_report.md` の閾値達成）を確認する。
   5. 第10.4節の必須停止条件9項目に該当しないことを確認する。
   6. `docs/process/autoloop_log.md` に1行追記する（日時 / Phase / 機械チェックの要約行 / 自己レビュー結果 / 判定 / 根拠）。**この記録は省略できない。**

   判定が **PROCEED** の場合、以下の1行だけを報告して次のPhaseへ自律遷移する（Product Ownerの入力を待たない）。

   > [自律ゲート通過] Phase N → 次Phase | 機械チェック: [要約行] | 残High: 0 | 記録: `docs/process/autoloop_log.md`

   判定が **HALT** の場合、`autoloop_log.md` に HALT を記録し、5-Aの定型で停止理由と選択肢を添えてProduct Ownerに報告する。**自律型であっても、停止条件に該当したら必ず止まる。**

6. **[リセット]**: ゲート通過後、スキル `context-reset` を実行し、次のPhaseへ遷移する（承認ゲート型は方式A/B、人間がサブエージェントを作る場合かつ自律型なら方式Cを選ぶ）。

## フェーズ内での中断・再開
1つのPhaseが長引き、コンテキストが尽きた場合や会話が中断した場合は、次の手順で再開する。**やり直しではなく、続きから再開すること。**

| 中断したPhase | 再開の手がかり |
| :--- | :--- |
| Phase 1〜3（文書作成中） | 書きかけの成果文書そのもの。`python tools/dada_check.py all` を実行し、未記入・欠落箇所を特定してそこから続ける |
| Phase 1〜3（レビュー中） | `REV101_*.md` のステータス列。`Open` の指摘から続ける |
| Phase 4（実装中） | `docs/process/impl_progress.md` の実装進捗台帳。「未着手」のUNIT-IDから続ける |

## Phase 0: ルーティング（3つの判定）

Product Ownerからの指示内容を分析し、以下の3つを**この順に**判定する。判定は推測ではなく、指示文の記述を根拠にすること。いずれも判定できない場合は既定値を採用し、Product Ownerに確認する。

| # | 判定 | 判定手順 | 既定値 |
| :---: | :--- | :--- | :--- |
| 1 | **開発対象** | `.agents/AGENTS.md` 第9節の判定手順（2問） | 従来型プログラム |
| 2 | **実行モード** | 起動指示に自律実行の明示（「DADAプロセス自律型」「自律型」「人間の確認を待たずに」、旧称「自律メタLoop」等）があるか。なければ承認ゲート型。旧称「対話型」「対話モード」は承認ゲート型 | 承認ゲート型 |
| 3 | **変更スケール** | `.agents/AGENTS.md` 第8節の判定手順（3問） | Major（全Phase実行） |

**報告の定型**（1回の応答でまとめて報告する）

> 本依頼を以下と判定しました。
> - 開発対象: **[従来型プログラム / エージェント定義]**（理由: ～）
> - 実行モード: **[承認ゲート型 / 自律型]**（理由: ～）
> - 変更スケール: **[Hotfix / Minor / Major]**（理由: ～。適用フロー: ～）

**判定に応じた準備（この時点で行う）**

- 開発対象が**エージェント定義**の場合: `docs/guidelines/agent_design_principles.md` をロードし、以降の各Phaseで `docs/templates/agent/` 配下のひな形を使うことを宣言する。
- 実行モードが**自律型**の場合: `docs/process/autoloop_log.md` の存在を確認し（なければ作成し）、今回の実行の開始行を追記する。適用限界（`.agents/AGENTS.md` 第10.7節）に該当する場合は、承認ゲート型への変更を提案する。
- 実行モードが**自律型**で、かつProduct Ownerが「要求仕様だけ確認する」と指示している場合: Phase 1完了後に1回だけ承認ゲート（5-A）を挿入する旨を宣言する。

**判定に迷う場合は、安全側（従来型プログラム / 承認ゲート型 / Major）を選び、Product Ownerに確認する。**

| レビュー記録 | `docs/artifacts/REV101_Test.md` |
| ひな形（従来型プログラム） | `.agents/skills/test-engineer/references/SWP6_skeleton.md` |
| ひな形（エージェント定義） | `docs/templates/agent/phase2_agent_eval_spec_template.md`（二重評価仕様書。単体テスト＋評価セット） |

- **【要求へのループバック】**: テスト項目を書けない要求（検証条件が曖昧・矛盾・不足）を検出した場合、テスト仕様を推測で埋めずに、**Phase 1へ差し戻す**（`test-engineer` スキルの差し戻し手順に従う）。これがこのPhaseを設計より先に置く最大の目的である。

**完了条件**: すべての `REQ-ID` に対応する `TC-ID` が存在し（1:1以上、機械チェックの `trace` で確認済み）、SWP6の承認状態が **計画承認済** であり、ゲート（5-Aまたは5-B）を通過していること。この時点では5〜6章は空でよい（結果はPhase 4でAIが記入する）。開発対象がエージェント定義の場合は、加えて**「評価」区分のすべてのTC-IDに評価ID（`EV-001` 形式）が1件以上割り当てられ、試行回数と合格率の閾値が数値で定義されている**こと。

## Phase 4: 実装・デバッグ・総合テスト報告 (Implementation & System Test Report)

実装・デバッグ・単体テストはAIが自律する（人間は中を見ない）。総合テストの実施・判定・報告書作成もAIが行う。承認ゲート型で人がゲートするのは**完成した総合テスト報告書（SWP6の5〜6章）**である。

1. **[実装計画]**: スキル `.agents/skills/programmer/SKILL.md` を読み込んでペルソナを適用。SW205のUNIT-IDを `docs/process/impl_progress.md`（実装進捗台帳）に転記し、依存の下層から順に実装する計画を立てる。
2. **[自律実装]**: 1ユニットずつ実装し、`unit-test-generator` スキルを活用して自律的にデバッグする。**1ユニット完了ごとに実装進捗台帳を更新する**（コンテキストが尽きても続きから再開できるようにするため）。
3. **[バグ対応]**: バグを修正した際は、必ず `docs/artifacts/BUG101_バグ管理表.md` に記録し、解決済にすること。
   - **【設計へのループバック】**: バグ修正に伴い、アーキテクチャ設計（SW205）の変更が必要と判断した場合は、独断で実装を修正せず、必ず「Phase 3: アーキテクチャ設計」に戻り、設計書の修正と承認からやり直すこと。
4. **[総合テストの実施と報告書の締結]**: SWP6の**すべての**テスト項目（実行区分「自動」「手動」「評価」）をAIが実施し、結果を5章に、総合判定を6章に記入する。実施者は常にAIである。「手動」はスクリプト化しない確認をAIがツールで行う区分であり、Product Ownerが実施する区分ではない。主観的な検収（好み・業務適合）はSWP6に書かず Phase 5 へ残す。
5. **[機械チェック]**: スキル `dada-check` を実行する。まず `python tools/dada_check.py all`、続けて **`python tools/dada_check.py report`**。未実装ユニット、テストコードのない「自動」TC-ID、skipされたテスト、5〜6章の欠落が検出されないことを確認する。
6. **[コードレビュー]**: スキル `.agents/skills/code-reviewer/SKILL.md` を読み込んで自己検閲する。対象はソースコード（エージェント定義ではスキル・ルール・知識の一貫性を含む）。総合テスト報告書は次項の担当である。
7. **[報告書レビュー]**: スキル `.agents/skills/test-reviewer/SKILL.md` の Phase 4 用の節に従い、SWP6の5〜6章を自己検閲する。指摘は `REV101_Test.md` に記録する。
8. **[ゲート]**: 実行モードによって分岐する。

   **承認ゲート型（5-A: 総合テスト報告書の承認）**: 以下の定型で報告し、Product Ownerの承認を待つ。**人間は報告書を読んで承認するだけであり、SWP6にテスト結果を追記してはならない。** 承認後、SWP6の承認状態を **報告書承認済** にし、スキル `context-reset` を実行して Phase 5 へ遷移する。

   > Phase 4（実装・総合テスト報告）の成果物が完成しました。
   > - 成果文書: `docs/artifacts/SWP6_ソフトウェア総合テスト仕様書・報告書.md`（5〜6章まで記入済み。承認状態を報告書承認済へ更新する）
   > - 実装したユニット: [UNIT-ID一覧]（詳細は `docs/process/impl_progress.md`）
   > - ユニットテスト: 全N件 グリーン
   > - 総合テスト: 全N件をAIが実施（自動 n / 手動 n / 評価 n）。結果はSWP6の5章、総合判定は6章
   > - 機械チェック: [`dada_check.py all` の要約行] / [`dada_check.py report` の要約行]
   > - 自己レビュー: コード [N件] / 報告書 [N件]（詳細は BUG101 および REV101_Test）
   > - 対応したバグ: [B-ID一覧 / なし]
   > - 起動・動作確認の手順: [コマンド等]
   > 総合テスト報告書をご確認のうえ、承認いただけますか？

   **自律型（5-B）**: `.agents/AGENTS.md` 第10.3節に加え、`dada_check.py report` の終了コード 0 と、SWP6の5〜6章が記入済みであることを確認してから遷移する。人間の報告書ゲートは置かない。SWP6の承認状態は **報告書承認済**（自律ゲートによる事前委譲）とする。

**完了条件**: 全ユニットテストがグリーンであり、SWP6のすべてのTC-IDについて5章に Pass/Fail があり、6.2の総合判定が記入され、`dada_check.py all` と `dada_check.py report` およびコードレビュー・報告書レビューのHigh指摘がゼロ（または残課題として報告済み）であること。承認ゲート型では報告書の承認ゲートを通過していること。SWP6の承認状態が **報告書承認済** であること。

### 開発対象がエージェント定義の場合の追加手順（従来型プログラムの場合は読み飛ばす）
1. **成果物の生成**: SW205の各UNITの「成果物パス」に従い、ファイルを生成する。自然言語レイヤーは `.agents/skills/<name>/SKILL.md`（frontmatterの `name` と `description` が必須）・`AGENTS.md`・`references/` 配下、プログラムレイヤーは `tools/` 配下のスクリプトである。
2. **一貫性の確認**: `.agents/AGENTS.md` 第9節の一貫性5項目（単一情報源・定数の二重定義の禁止・手順とツールの引数の一致・参照パスの実在・終了コードの意味の一致）を確認する。`python tools/agent_def_check.py` を実行し、終了コード0を確認する。
3. **評価セットの実行**: SWP6の4.3節の各評価ID（`EV-001` 形式）について、入力プロンプトを**定義された試行回数だけ**投入し、必須要素・禁止要素を判定する。結果（試行回数・合格数・合格率・閾値・判定）を `docs/process/eval_report.md` に記録し、集計をSWP6の5.3節へ転記する。これは手順4（総合テストの実施）の一部であり、実施者はAIである。
   - **1回の試行で合格したことをもって合格と報告してはならない。**
   - 閾値を下回った場合は、指示の具体化または決定論的判定への移行で対応する。**評価セットや閾値を緩めて合格させることを禁止する。**
   - LLM-as-judgeを用いる場合、評価対象のエージェントと採点者を同一の会話で兼任させない。
4. **ゲート報告への追加行**: 上記のゲート定型に、以下の2行を追加する。
   > - 一貫性チェック: [`agent_def_check.py` の要約行 / 未実行の場合はその理由]
   > - 評価セット: 全N件の評価IDが閾値を満たす（詳細は `docs/process/eval_report.md`）

## Phase 5: 人間による評価と要求見直し (Human Evaluation & Requirement Review)

> **Phase 5は実行モードによらず人間が行う。自律型でも自動化してはならない。** 完走後は成果物と総合テスト報告書をProduct Ownerへ引き渡す。人間は評価し、必要なら開発Loop（成果を見て要求を足し、DADAプロセスによる開発を再起動する外側のループ）を回す。承認ゲート型でも、成果物を踏まえて開発Loopを回す場合がある。
>
> Phase 5は**検収・動作評価**である。総合テストの実施とSWP6への結果記入は Phase 4 で終わっている。人間は承認済みの報告書を読んでよく、SWP6の5〜6章を追記してはならない。
1. **[評価1: 動作評価とバグ対応]**: Product Owner（人間）がプログラム（またはエージェント定義）を実際に動かして評価する。（推奨ガイド: `docs/process/phase5_evaluation_guide.md`）。好み・使用感など主観的な検収もここで行う。人間がバグを発見して `docs/artifacts/BUG101_バグ管理表.md` に記載した場合、AIはそれを読み取ってPhase 4に戻りデバッグを行い、修正後に `BUG101` に「原因と修正内容」を記入（解決済に）すること。総合テストを再実施した場合は、AIがSWP6の5〜6章を更新する。
2. **[評価2: 要求仕様の変更検討]**: 実際の動作を踏まえて要求仕様を変更したくなった場合、プロセスは**「Phase 1: 要求定義」にループバック**する。Product OwnerがAIに新しい要求を自然言語で指示するか、Product Owner自身が直接要求仕様書(`SW105`)を書き直す。
3. **[テスト仕様・設計への波及]**: 要求仕様が変更・確認された後は、自動的に**「Phase 2: 総合テスト仕様策定」へ遷移してSWP6を改訂**する。続いて、設計変更の要否をスケール判定し、必要なら「Phase 3: アーキテクチャ設計」を、不要なら直接「Phase 4: 実装・総合テスト報告」を実行する。
4. **[完了]**: 追加の要求変更がなく、Product Ownerの最終承認が得られた段階で、開発工程を完全に終了する。
