# ユニットテスト自律生成・修復 (Unit Test Generator)

本スキルは、実装フェーズ（Phase 4）において、`programmer` ペルソナがユニットテストの作成・実行・デバッグを人間の関与なしに裏側で完結させるための自動実行ループ手順である。

## 実行手順 (Mechanical How)

1. **テストフレームワークの特定**:
   - 設計書（`SW205` 8.2節）およびプロジェクトの設定ファイル（`package.json`、`pyproject.toml` 等）から、使用するテストフレームワーク（`vitest`、`pytest` 等）と実行コマンドを特定する。未導入の場合は、設計書で確定したフレームワークを導入する。
2. **内部テスト計画の立案（人間へのレビュー依頼は行わない）**:
   - 対象ユニット（`UNIT-ID`）の「公開インターフェース」「検証条件」（`SW205`）および対応する要求（`SW105`）に基づき、テストケースをコンテキスト内部で立案する。正常系に加え、境界値・異常系を必ず含める。
   - **【厳守】この単体テスト計画をProduct Owner（人間）に提案・承認依頼してはならない。即座にStep 3へ進む。**（人間が承認するのはPhase 2の総合テスト仕様書とPhase 4の総合テスト報告書のみである）
3. **テストコードの生成と配置**:
   - プロジェクトのテストフレームワーク構文に従い、テストファイルを生成する。
   - **開発対象が「エージェント定義」の場合の配置注意**: プログラムレイヤー（`tools/<name>.py`）の単体テストは、`tools/` 配下ではなく**必ず `tests/` 配下（例: `tests/test_<name>.py`）に配置**する。`tools/` は `dada_check.py` の走査除外ディレクトリのため、そこに置くとテスト未実装と判定される。
   - `docs/guidelines/coding_guidelines.md` に従い、AAAパターン（`Arrange` / `Act` / `Assert`）のコメントと、対応する **`UNIT-ID` および `TC-ID`（`SWP6` の「自動」区分に該当する場合）** をテストコード内に明記する。
   - **対応IDの明記は省略できない。** 機械チェック（`python tools/dada_check.py code`）はこのIDを手がかりに「テストコードが存在しない自動TC-ID」を検出する。
4. **完全自律デバッグループ**:
   - ターミナルコマンドで単体テストを実行する。
   - 失敗（Fail / Error）が発生した場合は**その都度人間に報告せず**、自らエラー出力とスタックトレースを読み取り、実装コードまたはテストコードを修正して再実行する。
   - 修正の判断基準: **常に `SW105` の検証条件と `SW205` の設計が「正」である**。テストが設計どおりで実装が誤っていれば実装コードを直し、テスト側が設計のインターフェースや前提を誤解していればテストコードを直す。
   - 対象ユニットのすべての単体テストが「グリーン（成功）」になるまで、このループを自律的に繰り返す。
5. **スタックした場合の脱出ルール（無限ループ防止）**:
   - **同一のテストが5回連続で失敗**した場合、自律デバッグループを打ち切る。
   - 状況を `docs/artifacts/BUG101_バグ管理表.md` に記録（現象・試した修正・原因の仮説）し、Product Ownerに「自律解決できない問題」として報告して判断を仰ぐ（自律型でも必須停止条件に該当する）。
   - 設計（`SW205`）自体の矛盾や不備が原因と判断した場合は、`programmer` スキルの「3. 設計との不一致を発見した場合（差し戻し手順）」に従い、Phase 3への差し戻しを提案する。
6. **実装進捗台帳の更新と完了報告**:
   - オールグリーンを確認したら、`docs/process/impl_progress.md` の該当 `UNIT-ID` の「テスト」列に `N件グリーン` と記録し、呼び出し元の `programmer` ペルソナ（または `dada-process` オーケストレーター）へ結果とテスト件数を報告する。

## 禁止事項

- **テストの改ざんによるグリーン化の禁止**: テストを通すために、期待値を実装の現状に合わせて弱める・テストを削除する・`skip` 等で無効化することを禁止する。無効化は `dada_check.py` が検出し、`code-reviewer` がテスト改ざんとしてHigh指摘にする。
- **検証（Assert）なしテストの禁止**: Assertを持たず「関数を呼び出して例外が出ないだけ」のテストを合格件数に数えてはならない。
- **虚偽報告の禁止**: 実際にコマンドを実行していない、または失敗が残っている状態で「グリーン」と報告してはならない。報告には必ず実際のテスト実行件数を添えること。
