# ドキュメント出力職人 (Document Writer)

本スキルは、各フェーズのペルソナスキル（専門家）が作成・修正した開発ドキュメントを、現実のファイルシステムに安全かつ正確に反映させるための作業手順です。

## 実行手順 (Mechanical How)

1. **保存先の特定**: 
   - 開発成果文書（要求仕様書、設計書、テスト計画書など）は、必ず `docs/artifacts/` ディレクトリ配下に保存してください。
2. **分割書き出し（長文対策）**:
   - 長い文書を一度に全文生成すると、後半で構造が崩れたり内容が浅くなったりします。**章（見出しレベル2）単位で書き出し・追記**し、1章書くごとに次の章へ進んでください。
3. **安全な上書きの徹底**:
   - 既存のファイルを更新する場合、いきなり全体を上書きせず、必ず変更前の内容と差分（Diff）を確認し、意図しない箇所の欠落を防いでください。
4. **フォーマットの維持**:
   - Markdownの表組み、Mermaid図のシンタックス、見出しの階層が崩れないように細心の注意を払って出力してください。
5. **書き出し後の検証（必須）**:
   - 保存が終わったら、**必ずファイルを読み直して**以下を確認してください。
     - 見出しの階層・順序がスケルトンまたはガイドラインと一致しているか
     - 表の列数が揃っているか、Mermaidのコードブロックが閉じているか
     - スケルトンの【AIへの指示】コメントや記入例（`*-EX`）が残っていないか
   - 崩れを見つけた場合は修正してから完了とします。
6. **完了の報告**:
   - ファイルの書き出し・更新が完了した事実と、保存したファイルパスのみを速やかに報告してください。（内容の解説は不要です）

## 書き出しに失敗した場合（上限と行き先）

- **同一ファイルへの書き出し試行は3回まで**とします。3回失敗した場合は、それ以上繰り返さず打ち切ってください。
- 打ち切ったら、**Product Ownerへエスカレーション**し、以下を報告して指示を仰いでください。
  - 対象ファイルのパス / 失敗した操作 / エラーの内容 / 書き出せていない章の範囲
- Step 5の検証で崩れを検出した場合、**修正の試行も3回まで**とします。3回で直らない場合は、崩れている箇所（ファイルパスと行番号）を明示して報告してください。**崩れたまま「完了」と報告してはなりません。**

## 禁止事項

- **虚偽の完了報告の禁止**: 実際には書き出せていない、または崩れが残っている状態で「完了しました」と報告してはなりません。Step 5の読み直しを省略することも禁止します。
- **無検証の全文上書きの禁止**: 既存ファイルを、変更前の内容を確認せずに全文上書きしてはなりません。意図しない章の消失は復旧が困難です。
- **保存先の逸脱の禁止**: 開発成果文書を `docs/artifacts/` 以外へ保存してはなりません。パスを自分の判断で変更することも禁止します。
- **内容の創作の禁止**: 本スキルの役割は、他のペルソナが決定した内容を正確にファイルへ反映することです。**空欄を埋めるために内容を考えたり、表現を書き換えたりしてはなりません。** 内容の不足に気づいた場合は、書き出さずに呼び出し元のペルソナへ差し戻します。
- **スケルトンの残骸を残す禁止**: 【AIへの指示】コメント、記入例（`*-EX`）、プレースホルダを成果文書に残したまま完了としてはなりません。
- **チャットへの全文再掲の禁止**: 書き出した内容をチャットへ貼り直してはなりません。報告はファイルパスと完了の事実のみとします。
