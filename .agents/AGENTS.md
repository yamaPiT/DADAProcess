# DADA Process Workspace Rules (特別法)

本ファイルは、このワークスペースにおけるAIエージェントの最上位ルール（ワークスペース憲法）です。
Antigravity v1で使用していたルールファイル（rules/dada_workspace_rules.md）は、v2構成に伴い本ファイルへ集約されました。現在は存在しません。

## 1. DADAプロセスの定義と目的
本プロジェクトは「DADA (Document-and-Agent-Driven Agile) プロセス」を適用します。
DADAプロセスは、**人間とAIによる協同開発プロセス**です。目的は、AIエージェントの独走を防ぎ、常に「人間が理解・承認できるドキュメント」と「ソースコード」が完全に一致した高品質なソフトウェアを高速に構築することです。

DADAプロセスは、IPAのESPR（ESPR Ver.2.0：【改訂版】 組込みソフトウェア向け開発プロセスガイド）をベースに、人間が設計した工程をスキルとルールとしてAIに与えます。DADAプロセスは次の2型に分かれます。

| 名称 | 略称 | 内容 |
| :--- | :--- | :--- |
| **DADAプロセス承認ゲート型** | 承認ゲート型 | AIエージェントの動作の要所に承認ゲートを設ける。人間の承認が得られた場合に、AIエージェントは処理を進める。成果物を踏まえ、人間がさらに開発Loopを回す場合もある |
| **DADAプロセス自律型** | 自律型 | AIエージェントは要求を受けたあと、自律動作をして開発しきる。成果物を踏まえ、人間がさらに開発Loopを回す場合もある |

本文・進行表示では略称を使ってよい。正式名称は本節の表を正とする。

**旧称の扱い**: 「対話型」「対話モード」は承認ゲート型、「自律メタLoop型」「自律メタLoopモード」は自律型として扱う。起動指示に旧称があっても、実行モードの判定を拒否してはならない。

## 2. DADAプロセスの起動（必須）
- **すべての開発依頼はDADAプロセスで処理する**: Product Ownerからソフトウェアの新規開発・機能追加・修正・バグ対応の依頼を受けた場合、必ずスキル `dada-process` を読み込み、その手順（Phase 0〜5）に従って作業を進めること。
- チャットでの雑談や質問応答など、開発成果物の変更を伴わない依頼はこの限りではありません。
- **起動時に3つの判定を行う**: Phase 0では「①開発対象（第9節）②実行モード（第10節）③変更スケール（第8節）」を判定し、結果を宣言すること。いずれも判定できない場合は既定値（従来型プログラム／承認ゲート型／Major）を採用し、Product Ownerに確認すること。

## 3. DADAプロセスの4原則（厳守事項）
### ① ドキュメント絶対主義 (Single Source of Truth)
- **コード先行の禁止**: いかなる実装・修正も、対応する開発ドキュメント（要求仕様書・設計書等）の更新なしに行ってはなりません。
- **UIの限定**: 主な戦場は「ドキュメント（実ファイル）」です。チャットでの合意は一時的なものとみなし、必ず実ファイル（`docs/artifacts/`内）へ書き出し、確定させてください。

### ② 厳格なる承認ゲート
- **工程遷移の制御**: 承認ゲート型では、人がゲートする文書（要求仕様書、総合テスト仕様、アーキテクチャ設計書、**総合テスト報告書（SWP6の5〜6章）**）の完成時に、必ずProduct Ownerの明示的な承認を求めてください。自律型では、起動時の指示をPhase 1〜4の承認の事前委譲とみなし、自律ゲートで遷移します（「要求仕様だけ確認する」と指示した場合はPhase 1完了後のみ人が承認する。解釈は第10節）。
- **独走の防止**: Product Ownerの承認（承認ゲート型）または自律ゲートの条件充足（自律型）を得るまでは、次のフェーズの作業（コードの実装など）を開始してはなりません。実装・デバッグ・単体テスト・総合テストの実施はAIが行う。承認ゲート型で人が止めるのは上記の文書であり、総合テストの結果を人間がSWP6へ追記してはならない。

### ③ アテンション-リセットの遵守
- **コンテキストの洗浄**: フェーズ移行時には、過去のチャット履歴に含まれる議論や推測を情報源から除外してください。これを確実に行うため、承認ゲートまたは自律ゲートの通過直後に**必ずスキル `context-reset` を実行**すること。
- **環境によるリセット方式の切り替え**: リセットの実現方法は実行環境と実行モードで異なる。**エージェント開発/実行ツール**がサブエージェントを自動作成できる環境（Antigravity 2.0 / CLI。サブエージェント起動ツール `invoke_subagent` 等がある）では **ツールが自動的にサブエージェントを作る（推奨）** となり、次Phaseの作業を独立したコンテキストのサブエージェントに委譲して自律的にリセットする（`context-reset` の方式A）。**自動作成できない環境（Antigravity IDE / v1）**では **人間がサブエージェントを作る** となる。人間がサブエージェントを作る場合かつ承認ゲート型なら、Product Ownerに新しいチャットウィンドウ（サブエージェント）の開始を依頼する（方式B）。人間がサブエージェントを作る場合かつ自律型なら、同一会話内の論理リセット（方式C）で進める。判定と手順の詳細は `context-reset` スキルおよび `dada-process` スキルの「フェーズ実行の方式」に従うこと。
- **汚染の持ち込み禁止**: いずれの方式でも、新しいコンテキストに渡してよいのは承認済みドキュメントとサマリーのみで、チャット履歴の要約を渡してはならない。
- **最新ドキュメントとサマリーの再ロード**: 洗浄後の新しいコンテキスト（サブエージェント、新しい会話、または方式Cの論理リセット後）では、作業を開始する前に**必ず `docs/process/last_phase_summary.md` を読んで前回の文脈を復元し**、その時点で承認されている「最新の開発ドキュメント」のみを真実として参照し直してください。

### ④ 役割の純化
- 各工程において、AIエージェントは該当するペルソナスキル（`requirements-engineer`、`architect`、`programmer` 等）を読み込み、その役割に完全になりきること。役割の範囲外の作業を越権して行わないこと。

## 4. 不変条件と手順の分離（モデル能力への適応）

本ワークスペースのルールとスキルは、**「不変条件」と「手順」の2層**で構成されています。エージェントはこの2つを混同してはなりません。

| 層 | 内容 | 扱い |
| :--- | :--- | :--- |
| **不変条件 (Invariants)** | 4原則（承認ゲート・ドキュメント絶対主義・アテンション-リセット・役割の純化）、ID体系、各スキルの「禁止事項」「完了条件」「完了前の自己チェック」、機械的検証の実行、二重出力の禁止 | **常に絶対。いかなる理由でも省略・緩和してはならない** |
| **手順 (Procedure)** | 各スキルの「作業手順」「レビュー手順」に書かれたステップの順序と粒度、報告の定型文 | **品質の下限を保証する足場。下限であり上限ではない** |

手順は、推論力の限られたモデルでも一定の品質に到達できるよう、意図的に細かく分解されています。したがって次の2点が同時に成り立ちます。
- 手順を**逐語的に実行すれば、必ず下限品質に到達する**。判断に迷った場合は、必ず手順どおりに実行すること。
- 手順は**達成可能な品質の上限を定めるものではない**。各手順には目的がある。不変条件を守ったうえで、その目的をより高い水準で達成できる手段があるなら、採用してよい。

### 実行プロファイル
| プロファイル | 使う場面 | 振る舞い |
| :--- | :--- | :--- |
| **Guided（既定）** | 特に指示がないとき | 手順を書かれた順に1ステップずつ実行する。判断に迷ったら停止してProduct Ownerに確認する |
| **Autonomous** | Product Ownerが「自律的に進めて」等と指示したとき、または手順を上回る手段を明確に説明できるとき | 不変条件を守る範囲で、手順の統合・順序変更・より深い分析・代替案の提示を行ってよい |

- 既定は **Guided** です。Autonomousへ切り替える場合は、切り替えた事実と理由を1行で宣言してください。**無断で手順を省略することは、Autonomousではなく単なるプロセス違反です。**
- Autonomousでも、**「完了前の自己チェック」と「機械的検証（スキル `dada-check`）」は省略できません**。これらは手順ではなく不変条件です。
- 手順を逸脱した場合は、何をどう置き換えたかを承認ゲートの報告に1行で記録してください。

## 5. 開発文書と管理表の運用
- 開発成果文書は必ず `docs/artifacts/` ディレクトリ配下に保存してください。
- **文書ID早見表**（IDと文書を取り違えないこと）:

| 文書ID | 文書名 | 作成Phase |
| :--- | :--- | :--- |
| SW105 | ソフトウェア要求仕様書 | Phase 1 |
| SWP6 | ソフトウェア総合テスト仕様書・報告書 | Phase 2（計画）/ Phase 4（結果・報告） |
| SW205 | ソフトウェアアーキテクチャ設計書 | Phase 3 |

- **文書IDは開発対象によって変わらない**: 開発対象が「エージェント定義」の場合も、文書IDは上表のままとし、ID体系（`REQ` / `TC` / `UNIT`）も変更しない。使用するひな形のみを `docs/templates/agent/` 配下へ差し替える（詳細は第9節）。
- **レビュー記録表 (REV101)**: 工程別に `REV101_Requirements.md`（Phase 1）, `REV101_Test.md`（Phase 2の計画および Phase 4の報告書）, `REV101_Design.md`（Phase 3）を使用し、指摘と修正結果を記録します。
- **Phase 5はSWP6に結果を書かない**: 総合テストの実施・判定・報告書作成は Phase 4 でAIが完了する。Phase 5は成果物の動作評価・BUG101へのバグ記入・要求見直しであり、人間がSWP6の5〜6章を追記する工程ではない。
- **バグ管理表 (BUG101)**: プログラムのバグおよびコードレビューで検出された問題は `BUG101_バグ管理表.md` に集約します。
- **プロセス状態ファイル**: 開発文書ではなく、フェーズ間・フェーズ内の文脈を保持するための作業ファイルです。

| ファイル | 役割 | 更新者 |
| :--- | :--- | :--- |
| `docs/process/last_phase_summary.md` | フェーズ移行時の引き継ぎサマリー | `context-reset` スキル |
| `docs/process/impl_progress.md` | Phase 4のユニット単位の実装進捗台帳 | `programmer` スキル |
| `docs/process/check_report.md` | 機械チェックの結果（自動生成） | `dada-check` スキル |
| `docs/process/autoloop_log.md` | 自律型の工程遷移ログ | `dada-process` スキル |
| `docs/process/eval_report.md` | エージェント定義の評価セット実行記録 | Phase 4（エージェント定義のとき） |
| `docs/process/agent_def_check_report.md` | エージェント定義チェックの結果（自動生成） | `agent_def_check.py` |

## 6. エージェントの行動指針
- **自己校正の義務**: 作業完了後、Product Ownerへ提示する前に、必ず対応するレビュアーのペルソナスキル（`requirements-reviewer`、`code-reviewer` 等）へ切り替わり、自己検閲を行ってください。
- **エスカレーション**: 要求の矛盾や技術的な不確実性を検知した場合は、作業を中断して速やかにProduct Ownerへ報告し、指示を仰いでください。
- **オンデマンド・ロード**: ASDoQモデルや規約類は、執筆・レビューの瞬間にのみロードして基準とすること。
- **二重出力の禁止（トークン経済）**: 成果物・レビュー指摘の全文はファイル（`docs/artifacts/` 等）にのみ書き、チャットにはファイルパスとサマリだけを出力すること。ファイルに書いた内容をチャットへ再掲しないこと。

## 7. 共通行動指針（全ペルソナスキルに適用）
以下のルールは、すべてのペルソナスキル（作成者・レビュアー）に共通で適用されます。各スキルファイルに重複して記述せず、ここに集約します。

### 機械的検証の委譲（省略禁止）
- ID対応の照合（`REQ` ↔ `TC` ↔ `UNIT`）、曖昧語・指示語の走査、表の空欄の検出、未実装ユニットの検出といった**網羅的な機械作業は、推論で行わずスキル `dada-check` を実行して検証**してください。対象件数が増えるほど、推論による照合は必ず取りこぼします。
- スクリプトを実行できない環境では、各スキルに記載された**手動の走査手順にフォールバック**し、**その事実を報告に明記**してください。実行していない検証を「実施済み」と報告してはなりません。
- 機械チェックが検証するのは**形式だけ**です。**内容の妥当性（要求の適否・テストの十分性・設計の適切さ・用語の一貫性・論理矛盾）は、必ずエージェント自身が判断**してください。機械チェックが「OK」でも、それは品質の証明ではありません。

### 品質基準のロード（ASDoQ文書品質モデルの三層活用）
ASDoQ品質モデルは、場面に応じて以下の3ファイルを使い分けること。
- **執筆時（作成者スキル）**: `docs/guidelines/asdoq_writing_rules.md`（執筆ルール12箇条）をロードし、**書く時点で違反を作らない**こと。レビューで直すより執筆時に守る方が手戻りが少ない（予防的品質作り込み）。
- **レビュー時（レビュアースキル）**: `docs/guidelines/asdoq_checklist.md`（軽量チェックリスト）をロードし、冒頭の「文書別の重点特性ガイド」に従って検証すること。
- **厳密校正時**: Product Ownerから「ASDoQ文書品質モデルに基づき厳密にレビューして」等の指示があった場合のみ、`docs/guidelines/asdoq_model_markdown.md`（フル版：例文・違反例付き）をフルロードすること。

### ドキュメントの構成準拠
- 文書の構成は、基本として `docs/guidelines/dada_document_guidelines.md` に従うこと。Product Ownerから「IEEE29148_2018に準拠」等の規格指定や「企業のテンプレートに従う」等の指示がある場合は、`docs/templates/` 配下の該当ひな形ファイルを読み込み、その構造を絶対的に優先すること。

### レビュー指摘の記録
- 作成者スキルが修正を行った後は、対応するレビュー記録表（`docs/artifacts/REV101_*.md`）に対応結果を記録すること。
- レビュアースキルが指摘を行う際は、同じレビュー記録表に指摘内容を具体的かつ客観的に記入すること。

### トレーサビリティID体系（全ドキュメント共通）
すべての成果物で以下のID形式を使用し、上流→下流の対応を機械的に照合できる状態を保つこと。

| 対象 | ID形式 | 定義場所 | 下流での参照義務 |
| :--- | :--- | :--- | :--- |
| 要求 | `REQ-001` 形式 | SW105 | SW205の各ユニット、SWP6の各テスト項目が対応REQ-IDを明記 |
| 設計ユニット | `UNIT-001` 形式（名称併記可） | SW205 | ソースコードのファイル/関数ヘッダが対応UNIT-IDを明記 |
| テスト項目 | `TC-001` 形式 | SWP6 | テストコードのコメントが対応TC-IDを明記 |
| 評価ケース | `EV-001` 形式 | SWP6（エージェント定義の評価セット） | `eval_report.md` の各行が対応EV-IDを明記 |
| レビュー指摘 | `R001` 形式 | REV101_* | — |
| バグ | `B001` 形式 | BUG101 | 修正コミット・修正報告が対応B-IDを明記 |

- **IDは転記、創作禁止**: 他文書のIDを引用・照合する際は、必ず元文書を開いてIDをコピーすること。記憶からIDを書いたり、存在しないIDを推測で作ったりしてはならない。照合表を作る際は、両方の文書を開いて転記する。
- **ID形式の厳守**: IDは `REQ-001` のようにハイフン＋3桁以上の連番で書くこと。書式を崩すと機械チェックが検出できなくなる。

### 自己校正の回数上限とエスカレーション
- 「作成→レビュー→修正」の自己校正ループは**最大2周**とする。
- 2周で解消しない重要度Highの指摘は、無理に解消（または黙殺）せず、**残課題としてProduct Ownerに正直に報告**し、判断を仰ぐこと。

### 承認の定義（誤判定の防止）
- 「承認」とは、Product Ownerによる明示的な肯定（「承認します」「OK」「次へ進んで」等）**のみ**を指す。
- Product Ownerからの質問・感想・部分的な同意は承認ではない。**承認を推定・先取りして次フェーズへ進むことを禁止**する。

## 8. スケール制御（変更規模に応じたフロー最適化）
AIエージェントは、Product Ownerからの指示内容を分析し、以下の基準で**変更スケールを自律的に判定**します。判定結果は `docs/process/last_phase_summary.md` の引き継ぎ事項に記録し、Product Ownerが後から確認できるようにしてください。

| スケール | 判断基準 | 適用フロー |
| :--- | :--- | :--- |
| **Hotfix** | バグ修正のみ。要求・設計の変更を伴わない | Phase 4 → Phase 5 のみ（BUG101に記録） |
| **Minor** | 既存機能の微調整。設計書（SW205）の変更を伴わない | Phase 1（差分更新）→ Phase 2（テスト仕様改訂）→ Phase 4 → Phase 5 |
| **Major** | 新機能追加や大幅な仕様変更 | 全Phase通過（標準フロー） |

### 判定手順（3問に順に答える）
1. **要求仕様書（SW105）の追加・変更が必要か？** → 不要なら **Hotfix**。
2. （必要な場合）**設計書（SW205）にユニットの追加、公開インターフェースの変更、依存関係の変更が必要か？** → 不要なら **Minor**。
3. 必要なら **Major**。

判断できない設問が1つでもあれば、安全側の **Major** として扱い、Product Ownerに確認すること。

- **Minorでもテスト仕様は必ず改訂する**: 設計変更が不要な軽微な仕様変更でも、要求（SW105）が変わる以上、対応するテスト項目（SWP6）の追加・改訂は省略してはならない。省略してよいのはPhase 3（アーキテクチャ設計）のみである。
- **判定報告の義務**: AIは判定結果を「本変更は **[Hotfix/Minor/Major]** と判定しました。理由: ～」の形式でProduct Ownerに報告し、異議がなければ該当フローで進行すること。
- **エスカレーション**: 判定に迷う場合は、安全側（Major）として扱い、Product Ownerに判断を仰ぐこと。

## 9. 開発対象の二系統（従来型プログラム / エージェント定義）

AI時代の開発対象は2系統に分かれる。DADAプロセスは**どちらも同じPhase 1〜5・同じ承認ゲート・同じID体系で開発する**。切り替わるのは、参照するひな形と検証方法だけである。

| 開発対象 | 成果物 | 検証方法 | 参照するひな形 |
| :--- | :--- | :--- | :--- |
| **従来型プログラム**（既定） | ソースコード | 単体テスト・総合テスト（決定論的） | 各ペルソナスキルの `references/` 配下のスケルトン |
| **エージェント定義** | スキル（`SKILL.md`）・ルール（`AGENTS.md`）・知識/ひな形＋従来型プログラム（ツール） | 単体テスト（プログラムレイヤー）＋評価セット（自然言語レイヤー） | `docs/templates/agent/` 配下の3ファイル |

### 判定手順（2問に順に答える）
1. **Product Ownerが「開発対象: エージェント定義」「エージェント一式を作る」と明示しているか** → Yesなら **エージェント定義**。
2. 明示がない場合、**最終成果物がAIに読ませる自然言語の指示書（スキル・ルール・プロンプト）であるか** → Yesなら確認のうえ **エージェント定義**、Noなら **従来型プログラム**。

判定できない場合は既定の**従来型プログラム**として扱い、Product Ownerに確認すること。

### エージェント定義開発時の追加義務
- **参照の義務**: `docs/guidelines/agent_design_principles.md` と `docs/templates/agent/` 配下の該当ひな形を必ずロードすること。ロードせずに書き始めることを禁止する。
- **工程省略の禁止**: 「自然言語なので書きやすい」ことを理由にPhaseや承認ゲートを省略してはならない。省略してよいのはスケール判定（第8節）で認められた範囲のみである。
- **1回の成功を成功と報告する禁止**: エージェント定義の振る舞いは確率的である。評価は必ず複数回試行し、合格率で判定すること（試行回数と閾値はSWP6に記載する）。
- **評価セットの改変による合格の禁止**: 評価が閾値を下回ったときに、評価セット・必須要素・閾値を緩めて合格させてはならない（テストの改ざんに相当する）。対応は、指示の具体化、決定論的判定への移行、Product Ownerとの許容範囲の再合意のいずれかである。

### 自然言語とプログラム言語の一貫性遵守（不変条件）
エージェント定義は二重構造であり、2つのレイヤーが食い違うとエージェントは自然言語の記述を信じて誤動作する。次の5項目を常に満たすこと。

| # | ルール | 違反の例 |
| :---: | :--- | :--- |
| 1 | **単一情報源**: 同じ知識を2箇所に書かない。両方に書く場合はどちらが正かを明記し、他方は参照にする | 禁止語リストをスキル本文とスクリプトの両方に別内容で持つ |
| 2 | **定数の二重定義の禁止**: 閾値・パス・ID書式は一方に定義する。やむを得ず両方に書く場合は、相互に「他方と同一に保つこと」とコメントする | スクリプトの閾値を変えたのに文書の閾値が古い |
| 3 | **手順とツールの引数の一致**: `SKILL.md` に書いたコマンド行を、実際のスクリプトの引数・オプションと一字一句一致させる | スクリプトのサブコマンドを増やしたのにスキルの手順が旧コマンドのまま |
| 4 | **参照パスの実在**: 自然言語レイヤーが参照するすべてのファイルパスが実在すること | 存在しない `references/` を読ませる指示 |
| 5 | **終了コードの意味の一致**: スクリプトの終了コード（0/1/2）の意味を、手順側の分岐と一致させる | スクリプトは1を返すのに手順が「0以外は実行エラー」と書いている |

- **変更時の同時修正**: いずれかのレイヤーを変更した場合、対応する他方のレイヤーを**同じ作業単位の中で**修正すること。「あとで直す」は禁止する。
- **検証**: 上記4・5の一部は `python tools/agent_def_check.py` で機械的に検出できる。実行できない環境では手動確認し、その事実を報告に明記すること。

## 10. 実行モード（承認ゲート型 / 自律型）と権限委譲

### 10.1 2つの実行モード

| 実行モード | 人間の位置 | Phase 1〜4の承認 | Phase 5 |
| :--- | :--- | :--- | :--- |
| **承認ゲート型**（既定。正式名称: DADAプロセス承認ゲート型） | AIの要所で承認ゲートに立つ | Product Ownerの明示的承認が必要 | 人間が評価する。成果物を踏まえ、さらに開発Loopを回す場合もある |
| **自律型**（正式名称: DADAプロセス自律型） | 要求を渡したあと、完走まで内側に立たない | 後述の条件を満たせば**自律ゲート**で通過する。「要求仕様だけ確認する」と指示した場合のみ、Phase 1完了後に1回人が承認する | **人間が評価する（自律化しない）**。成果物を踏まえ、さらに開発Loopを回す場合もある |

- **既定は承認ゲート型**である。Product Ownerが起動時に自律実行を明示的に指示した場合のみ自律型となる。**実行モードを推定してはならない。**（動作モード＝ツールが自動的にサブエージェントを作るか／人間がサブエージェントを作るかは、開いたエージェント開発/実行ツールで自動判定するものであり、ここでいう実行モードとは別である）
- **Phase 5は決して自律化しない。** 自律型でも、完走後は必ず人間の評価に戻す。これが開発Loopの起点である。

### 10.2 権限委譲の定義（承認の定義との関係）

第7節「承認の定義」（承認とはProduct Ownerによる明示的な肯定のみを指す）は不変条件であり、緩めない。自律型では次のように解釈する。

> **Product Ownerが起動時に「DADAプロセス自律型で進めてください」と明示的に指示した行為そのものを、Phase 1〜4の承認の「事前委譲」とみなす。** 旧称「自律メタLoopモードで進めてください」および「人間の確認を待たずに」も、同じ事前委譲として扱う。

これは承認の推定ではなく、委譲の明示である。したがって次が導かれる。
- 起動指示に自律実行の明示がなければ、事前委譲は成立しない（承認ゲート型として扱う）。
- 事前委譲の範囲は**Phase 1〜4の工程遷移**である。要求の追加・変更（開発Loopで足す分）、スコープの拡大、破壊的操作は委譲の対象外である。
- Product Ownerが起動時に「要求仕様だけ確認する」と指示した場合は、Phase 1完了後のみ人間の承認が必要になり、事前委譲は **Phase 2〜4** に限る（第10.6節）。

### 10.3 自動フェーズ遷移の承認条件（すべて満たすときのみ遷移可）

| # | 条件 |
| :---: | :--- |
| 1 | Product Ownerが起動時に自律型（または旧称の自律メタLoop）を明示的に指示している |
| 2 | `python tools/dada_check.py all` の**終了コードが 0**（High指摘ゼロ）である。Phase 4では加えて `python tools/dada_check.py report` の終了コードも **0** である |
| 3 | 自己校正ループが2周以内に完了し、未解消のHigh指摘がゼロである |
| 4 | 当該Phaseの「完了条件」を、保存済みファイルを読み直す自己チェックで全項目満たしている |
| 5 | 開発対象がエージェント定義の場合、Phase 2で評価セットが定義済みであり、Phase 4では `docs/process/eval_report.md` の全評価IDが閾値を満たしている |
| 6 | 下記10.4の必須停止条件に1つも該当しない |

1つでも欠ける場合は遷移せず、停止してProduct Ownerに報告すること。**「概ね満たしている」「軽微な残りだけ」という判断で遷移してはならない。**

### 10.4 必須停止条件（自律型でも人間に必ず戻す）

| # | 条件 | 停止する理由 |
| :---: | :--- | :--- |
| 1 | テスト項目を書けない要求を検出した（Phase 2の差し戻し条件） | 曖昧な要求を推測で埋めることは、実行モードと無関係に禁止 |
| 2 | 実装中に設計の不備・矛盾・実現不可能性を検出した（Phase 4の差し戻し条件） | 同上 |
| 3 | 自己校正2周でHigh指摘が未解消 | 第7節「自己校正の回数上限とエスカレーション」 |
| 4 | 機械チェックのHigh指摘を2回連続で解消できない | 無限修正ループの防止 |
| 5 | 同一のテストが5回連続で失敗した | ループ上限 |
| 6 | 開発対象・実行モード・スケールの判定が不能 | 安全側へ落として確認する |
| 7 | 破壊的操作（ファイル削除・履歴の書き換え）、外部課金、秘密情報の取り扱いが必要 | グローバルルールの安全第一 |
| 8 | スコープ外の新規要求が必要と判断した | 要求の追加は開発Loop（人間）の役割 |
| 9 | 同一Phaseへのループバックが2回発生した | 発散の防止 |

停止する場合は、**何が起きて何を判断してほしいのかを1回の応答で伝える**こと（選択肢を添える）。

### 10.5 記録義務（透明性）

自律ゲートを通過または停止するたびに、`docs/process/autoloop_log.md` へ1行追記すること。省略を禁止する。

- 記録する項目: 日時 / Phase / 機械チェックの要約行 / 自己校正の結果（指摘件数と残課題） / 判定（PROCEED または HALT）/ 根拠
- **記録がない自律遷移はプロセス違反**として扱う。人間はこのログだけで全判断を追跡できなければならない。

### 10.6 要求仕様の確認ゲート（任意挿入）

自律型では既定でPhase 1〜4を通して停止しない。ただしProduct Ownerが起動時に「要求仕様だけ確認する」と指示した場合は、**Phase 1完了後に1回だけ承認ゲートを挿入**し、以降のPhase 2〜4を自律実行する。

### 10.7 自律型の適用限界

次の場合は自律型を選ばず、承認ゲート型を使うこと。AIは該当を検知したら、モードの変更をProduct Ownerに提案する。
- 人命・金銭・法令遵守に直接影響する機能を含む
- 極めて高度な品質（高い再利用性・効率性・認証取得）が要求される
- 要求が曖昧なまま着手せざるを得ない（先に要求を固める必要がある）
