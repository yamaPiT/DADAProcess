## 1. 概要

### 1.1 目的と位置づけ
本設計書は、DADAプロセス v7.0 の省トークン化および高速化改訂に向けたソフトウェアアーキテクチャを定義する。想定する読み手は、Product Owner（マサ）、本プロセスを運用する開発者、および Phase 4 を担当する AI エージェントである。本設計書は、承認済みの要求仕様書（`SW105`）および総合テスト仕様書・報告書（`SWP6`）を唯一の根拠とする。本書では自然言語レイヤーとプログラムレイヤーの責務境界、全機能ユニットの公開インターフェース、ACI 仕様、性能見積り、および技術選定根拠（ADR）を確定する。

### 1.2 適用範囲
本設計の対象は、本リポジトリ内のワークスペース憲法、スキル群、ガイドライン群、および `tools/` 配下の決定論的 CLI 群と `tests/` 配下の単体テスト群である。主対象の AI 実行製品は Antigravity App（CLI を含む）とする。移植対象には Antigravity IDE、Claude Code、Cursor、Codex、および GitHub Copilot を含める。`tools/office_io.py` の描画・パッチ機能の全面書き換え、ASDoQ 品質基準および `tools/asdoq_dictionary.json` の改変、ならびに Phase 5 の人間による動作評価の自動化は対象外とする。理由: これらは `SW105` の 1.2 節でスコープ外と定義済みであるため。

#### スキル分割方針
`SW105` の 2.3 節で定めた役割分割方針に基づき、全機能を 10 ユニットへ分割する。内訳は制御系（`UNIT-002`）・作成役（`UNIT-003`）・レビュー役（`UNIT-004`）・単体兼用（`UNIT-005`）・指針（`UNIT-006`）・最適化層（`UNIT-007`）・プログラム 3 群（`UNIT-008`〜`UNIT-010`）である。作成役とレビュー役は内部でフェーズ別の `SKILL.md` ファイル（1 役割 1 `SKILL.md`）に分かれており、Generator と Evaluator の分離を維持する。共通のワンパス執筆手順やキャッシュ再利用手順を持つスキル群は、役割グループ単位の `UNIT-ID` にまとめる。この構成により、依存図は 10 ノードの完全な非循環有向グラフ（DAG）を維持できる（詳細は 8.1 節の ADR-001 参照）。

各 `SKILL.md` の `frontmatter` における `description` は発動条件を先頭に配置し、他スキルとの重複を排除する。工程スキルでは「DADAプロセスの Phase N で〜するとき」という形式で発動条件を明記する。単体兼用スキルでは「単体タスクまたは〜の推敲／ASDoQレビュー／Office変換を求められた場面」という記述により、Routing における誤発動を防ぐ。

### 3.2 機能ユニットの定義

#### UNIT-001: ワークスペース憲法（軽量版）
- **責務**: 全フェーズで自動注入される DADA プロセスの不変条件、ID 体系、承認定義、および実行モード規則の正本を 12,288 bytes 以下で定義する。
- **レイヤー**: 自然言語
- **成果物パス**: `.agents/AGENTS.md`
- **対応要求**: REQ-001
- **公開インターフェース**: 発動条件=ワークスペース内の全チャット起動直後にシステムが自動注入する。入力=なし（最上位規則）。出力=応答内の原則遵守宣言。思考過程の出力=開始および完了の時点で「(1) 現在地 (2) 判断の根拠 (3) 次の一手」を出力し、DADA 実行中は末尾に `[DADA | Phase N: ...]` 1 行を出力する。出力形式=Markdown（不変条件表・ID 早見表・禁止事項リスト・参照先パス表のみを保持し、目標サイズ 8,000〜10,500 bytes、上限 12,288 bytes）。呼び出すツール=なし（参照先として `docs/guidelines/agent_def_phase_addon.md` へのポインタのみを記載する）。
- **依存先**: なし
- **検証条件**: UTF-8 ファイルサイズが 12,288 bytes 以下であること。`agent_def_check.py` が不変条件 4 原則の記載と参照リンク切れ 0 件で終了コード 0 を返すこと。評価セット `EV-001`・`EV-002` で 10 回中 9 回以上合格すること。
- **適用するポカヨケ**: 思考過程の強制／ルート固定パス／二重出力の禁止／ラベルの固定／禁止事項の明示

#### UNIT-002: オーケストレーター・工程制御スキル群
- **責務**: Phase 0 の 3 判定（開発対象・実行モード・変更スケール）、`context-reset` による文脈洗浄、および承認ゲートまたは自律ゲートの遷移を制御する。
- **レイヤー**: 自然言語
- **成果物パス**: `.agents/skills/dada-process/SKILL.md`, `.agents/skills/context-reset/SKILL.md`, `.agents/skills/dada-check/SKILL.md`
- **対応要求**: REQ-002, REQ-006
- **公開インターフェース**: 発動条件=ソフトウェア開発を依頼された場面（`dada-process`）、ゲート通過により次工程へ移行する場面（`context-reset`）、および機械検証を実行する場面（`dada-check`）。入力=Product Owner の指示、`docs/process/last_phase_summary.md`、承認済み文書群。出力=`docs/process/last_phase_summary.md`、`docs/process/autoloop_log.md`、各フェーズ担当者への委譲指示。思考過程の出力=Phase 0 判定結果と「(1) 現在地 (2) 判断の根拠 (3) 次の一手」および末尾進行表示 1 行を必ず出力する。出力形式=Markdown（ゲート報告定型文および遷移ログ 1 行）。呼び出すツール=UNIT-008（`python tools/dada_verify.py`）、UNIT-010（`python tools/agent_def_check.py`）。
- **依存先**: UNIT-001, UNIT-003, UNIT-004, UNIT-006, UNIT-007, UNIT-008, UNIT-010
- **検証条件**: 従来型プログラム指定では `agent_design_principles.md` を読み込まないこと。エージェント定義指定では `docs/guidelines/agent_def_phase_addon.md` を読み込むこと。曖昧入力や参照欠損で停止・確認でき、評価セット `EV-003`・`EV-004`・`EV-005` で 10 回中 9 回以上合格すること。
- **適用するポカヨケ**: 思考過程の強制／ルート固定パス／二重出力の禁止／status コード制御／ループ上限とエスカレーション／禁止事項の明示／完了条件のチェックリスト化

#### UNIT-003: 作成役ペルソナスキル群（ワンパス軽量版）
- **責務**: Phase 1 から Phase 4 までの各開発成果文書（`SW105`・`SWP6`・`SW205`・テスト結果）およびソースコード・単体テストを、ワンパス執筆手順により作成・修正する。
- **レイヤー**: 自然言語
- **成果物パス**: `.agents/skills/requirements-engineer/SKILL.md`, `.agents/skills/test-engineer/SKILL.md`, `.agents/skills/architect/SKILL.md`, `.agents/skills/programmer/SKILL.md`, `.agents/skills/document-writer/SKILL.md`, `.agents/skills/unit-test-generator/SKILL.md`
- **対応要求**: REQ-002, REQ-003
- **公開インターフェース**: 発動条件=Phase 1 から Phase 4 までの各作成工程を開始する場面（各 `SKILL.md` の `description` に担当 Phase と文書名を明記）。入力=`docs/process/last_phase_summary.md`、承認済み上流文書、テンプレート、`docs/guidelines/asdoq_writing_rules.md`。出力=`docs/artifacts/SW105_ソフトウェア要求仕様書.md`・`SWP6`・`SW205`・`docs/process/impl_progress.md`・`eval_report.md`・ソースコード・`tests/` 配下のテストコード。思考過程の出力=作業開始および完了の時点で「(1) 現在地 (2) 判断の根拠 (3) 次の一手」と末尾進行表示 1 行を出力する。出力形式=Markdown（標準目次・固定ラベル形式）およびチャット要約（ファイルパス・検証要約行のみ）。呼び出すツール=UNIT-008（`python tools/dada_verify.py`）、`python tools/style_check.py snapshot`、`python tools/style_check.py verify`。
- **依存先**: UNIT-001, UNIT-005, UNIT-006, UNIT-008
- **検証条件**: 初回執筆後の `dada_verify.py` 指摘が 0 件ならリライト往復を省略すること。指摘が 1 件以上なら該当行のみ局所修正して `style_check.py verify` の終了コード 0 を確認すること。2 回超過後は原文の意味を優先して停止でき、`EV-006`・`EV-007` で 10 回中 9 回以上合格すること。
- **適用するポカヨケ**: 思考過程の強制／ルート固定パス／二重出力の禁止／status コード制御／ラベルの固定／ループ上限とエスカレーション／禁止事項の明示／完了条件のチェックリスト化

#### UNIT-004: レビュー役ペルソナスキル群（再利用・省トークン版）
- **責務**: 各フェーズの成果文書およびソースコードを、直前の検証キャッシュ再利用と ASDoQ 反証観点により検査し、指摘を `REV101_*` または `BUG101` へ記録する。
- **レイヤー**: 自然言語

## 8. その他・特記事項

### 8.1 アーキテクチャ決定記録（ADR）

#### ADR-001: 統合機械検証CLIの単一プロセス直交化・キャッシュ再利用、および単体テストフレームワークの選定
- **背景**: 従来は 1 フェーズ内で `dada_check.py`、`asdoq_lint.py`、`style_check.py`、`agent_def_check.py` を作成工程とレビュー工程で重複実行しており、CLI 呼び出しが 9〜11 回に達していた。さらに `SWP6` 表1 で単体テストフレームワークと統合検証 CLI コマンドが未確定（Phase 3 で確定する項目）であった。
- **決定**: 統合機械検証 CLI として `tools/dada_verify.py`（`UNIT-008`）を新設し、単一プロセス内で既存 4 検証を直交実行する（重複走査の 1 パス統合と重複指摘の排除）。既存の個別 4 CLI は廃止せず、既存サブコマンド・引数・終了コード（0/1/2）の後方互換を維持する。あわせて `docs/process/.verify_cache.json` に SHA-256 ハッシュと検証引数を保存する。`--reuse-cache` 指定で未編集文書はキャッシュから応答し、編集された文書は自動で再実行する。単体テストフレームワークは Python 標準ライブラリ `unittest` を採用し、`tests/` 配下へ配置する。
- **理由**: Python 標準ライブラリのみで動作させることで `SW105` 3.1 節のランタイム制約（追加パッケージ不要）を満たす。`tests/` 配置により `dada_check.py code` が「自動」区分 TC を自動検出できる。また単一プロセス化とキャッシュ再利用により、1,000 行規模で 3.0 秒以内かつ CLI 回数 2〜5 回を達成できる。なお、役割別ファイル群を 10 ユニットへ集約した設計は、`SW105` 2.3 節の役割単位に沿いつつ図1を 10 ノードの完全 DAG に保つために採用した。
- **捨てた選択肢**: シェルスクリプトによる既存 4 CLI の逐次ラッパー、および `pytest` の必須化。理由: ラッパーはプロセス起動負荷と重複走査を解消できず Windows PowerShell 互換性も劣るため。`pytest` は外部パッケージ未導入環境で自動テストが停止する懸念があるため。

#### ADR-002: エージェント定義追加手順の `docs/guidelines/agent_def_phase_addon.md` への単一情報源集約
- **背景**: 従来は `dada-process`、`requirements-engineer`、`test-engineer`、`architect`、`programmer` の 5 スキルすべてにエージェント定義用の追加手順が重複記述されていた。この重複により、従来型プログラム開発のフェーズでも不要なバイト数が読み込まれていた。
- **決定**: エージェント定義専用の差分手順を `docs/guidelines/agent_def_phase_addon.md`（`UNIT-006`）の単一ファイルへ抽出し、各スキルからは 1〜2 行の条件付き参照ポインタのみを置く。さらに `docs/guidelines/agent_design_principles.md` の重複例示を圧縮して軽量化する。
- **理由**: 単一情報源の原則を守りながら、従来型プログラム開発での Phase 1・3・4 読込バイト数をベースライン比 67%〜71% 削減できるため。またエージェント定義開発の場面でも参照先が 1 箇所に定まり保守性が向上する。
- **捨てた選択肢**: 各スキル内部に長い条件分岐を残す案、および別系統の専用スキルセット（`agent-architect` や `agent-programmer`）を新設する案。理由: 長い条件分岐を残すと、読込削減率 50% 以上の目標を達成できないため。専用スキル新設はスキル数倍増により Routing の誤発動リスクが高まるため。

#### ADR-003: Antigravity最適化アダプター層の分離による移植性確保
- **背景**: `SW105` の 1.2 節および `REQ-006` では、Antigravity App の固有機能（Plan/Execute モデル使い分け・軽量サブエージェント・並列実行・`run_workflow`・明示時の `/swarm`）の活用が求められている。あわせて Antigravity IDE や互換ツール（Claude Code・Cursor・Codex・GitHub Copilot）への移植性も必要である。
- **決定**: 固有機能に関する指針をポータブルコア層（`UNIT-001`〜`UNIT-006`）から分離し、独立ファイル `docs/guidelines/antigravity_adapter.md`（`UNIT-007`）として配置する。ポータブルコア側は利用可能ツールに応じたフォールバック分岐のみを保持する。
- **理由**: コアスキルが特定ベンダー固有ツールに強く結合すると他環境への移植の場面で停止・誤動作を招くため。アダプター層を分離することで、非対応環境でもエラー停止せず標準順次実行または標準サブエージェントへ切り替えられる。
- **捨てた選択肢**: `dada-process/SKILL.md` 本体に Antigravity App 固有の呼び出し規則を埋め込む案。理由: 他ツール環境での指示汚染と読込バイト数の増大を招くため。

#### ADR-004: `tools/dada_benchmark.py` の v6.1.0 ベースライン定義とフェーズ読込ファイルセット計測方式
- **背景**: `SW105` 表7 のベースライン値と比較するため、計測の再現性とファイルセット定義における透明性を確保する必要がある（`SW105` 表9 項目4）。
- **決定**: `tools/dada_benchmark.py`（`UNIT-009`）は、`SW105` 表7 と一致する v6.1.0 実測値を標準定数辞書として内蔵し、各フェーズの規定読込ファイルリストから UTF-8 実バイト数を合算する。各フェーズの対象ファイルは次の通り定める。(1) Phase 1 執筆（従来型、基準 126,875 B）の構成要素は憲法・`dada-process`・`requirements-engineer`・`SW105_skeleton`・`document-writer`・`asdoq_writing_rules`・`JP-Humanizer` である。(2) Phase 1 レビュー（従来型、基準 119,264 B）の構成要素は憲法・`requirements-reviewer`・`asdoq_checklist`・`asdoq-reviewer`・重点 4 特性（C1〜C5）・`JP-Humanizer` である。(3) Phase 1 執筆（エージェント、基準 174,335 B）は従来型から `SW105_skeleton` を除き、`phase1_agent_requirements_template`、`agent_def_phase_addon`、および `agent_design_principles` を加えた構成とする。(4) Phase 3 執筆（従来型、基準 129,449 B）の構成要素は憲法・`dada-process`・`architect`・`SW205_skeleton`・`document-writer`・`asdoq_writing_rules`・`JP-Humanizer` である。(5) Phase 4 執筆（従来型、基準 117,432 B）の構成要素は憲法・`dada-process`・`programmer`・`unit-test-generator`・`coding_guidelines`・`JP-Humanizer` である。標準 CLI 検証回数は、対象ルート内の作成・レビュー手順ファイル（`requirements-engineer`・`requirements-reviewer`）を対象に計測する。具体的には、1 フェーズ標準手順上の Python 検証コマンド行を正規表現で走査・計数する（`TC-022` のダミー検証でも同一計数式を用いる）。
- **理由**: 外部の `git show` 依存を排し、単体ディレクトリやテスト用ダミーディレクトリでも決定論的にベンチマークを実行できるため（`TC-022`・`TC-023` の要件充足）。外部 JSON 基準値へ差し替える場面では `--baseline <json_path>` オプションで上書きできる構造にする。
- **捨てた選択肢**: 実行のたびに `git show main:...` を実行する方式。理由: 切り出し済み単体スキルセットや `.git` 非存在環境、およびダミーディレクトリテストで実行エラーになるため。
