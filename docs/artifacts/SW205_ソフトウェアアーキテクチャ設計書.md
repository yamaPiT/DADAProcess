## 1. 概要

### 1.1 目的と位置づけ
本設計書は、承認済み要求仕様書（`SW105` 版数 1.3、`REQ-001`〜`REQ-007`）と総合テスト仕様書・報告書（`SWP6` 版数 1.1、`TC-001`〜`TC-023`、`EV-001`〜`EV-010`）の実現に向けた構成を定める。プログラムと自然言語定義を組み合わせたエージェント定義一式について、モジュール構造、ACI仕様、およびデータ制御方式を定義する。

本版（1.2）では、旧サイクル（版数 1.1）からの4つの基盤刷新を設計へ反映する。第1に TypeSafe AI `Jev` を廃止し、Google `gemini-decision-1`（Decisions API `v1beta/decisions`）へ移行する。第2に分類タグを `[ASDoQ:特性-副特性]` へ統一し、第3に図表分割と接続番号ルールを全工程へ組み込む。第4に任意の `/swarm` および `Gemini 4 Hydrogen`/`Argon` アダプタを本体定義から分離する。

### 1.2 適用範囲
本設計が規定する構築・改修対象（スコープ内）と、対象外事項（スコープ外）を以下に定める。

- **スコープ内**:
  - プログラムレイヤー: `tools/asdoq_dictionary.json`、`tools/asdoq_lint.py`、`tools/export_skillset.py`、`tests/test_asdoq_reviewer.py` の4資産。
  - 自然言語レイヤー（レビュー系・基盤）: `.agents/skills/asdoq-reviewer/SKILL.md`（同 `references/` 6定義 `C1`〜`C6`）、`.agents/AGENTS.md`・レビュー4スキル・`JP-Humanizer`・`dada-process`、および配布設定（`README.md`・`.env.example`・`.gitignore`）。
  - 自然言語レイヤー（作成系・帳票）: DADA作成4スキル、スケルトン3種、エージェント用ひな形3種、ガイドライン3種、およびレビュー記録表3種。
- **スコープ外**:
  - `Gemini 4 Carbon` モデルへの依存（Google AI Pro 契約範囲の `Gemini 4 Hydrogen` と `Argon` のみで動作を完結させる）。
  - `tools/office_io.py` や `tools/style_check.py` に対する新たな変換エンジンの追加開発。
  - Phase 3 設計時点における外部 `gemini-decision-1` API の実通信（Phase 3 の文書検証はローカル点検 `OFF` で行い、実機 `ON` 試験 `TC-012` と `EV-006` は Phase 4 総合テストで行う）。

## 2. システム構成

### 2.1 システム全体構成
本システムは3層構造をとる。最上位の自然言語レイヤー（Layer 2）は利用者環境と対話し、中間の判定レイヤー（Layer 1）は外部APIまたはローカル規則で疑義スライスを絞る。最下層のプログラムレイヤー（Layer 0）は決定論的解析と図表検査を担う。全体構成は図1の内部ユニット構成と図2の外部連携・配布構成へ分割し、両図は `[接続①]` によって論理的に連結する。

```mermaid

    PO["利用者 (Product Owner)"] --> ENV["実行環境アダプタ (Antigravity・他4ツール)"]

    ORCH --> SPEC["Layer 2 6特性専門定義 (UNIT-004)"]

    DICT["Layer 0 拡張・企業辞書 (UNIT-001)"] --> L0

```

## 3. ソフトウェア構成（静的構造）

### 3.1 ソフトウェア全体構成
エージェント設計原則ガイドライン（`agent_design_principles.md` 第2.2節・第2.4節）および `SW105` 第2.5節に基づき、5つの設計パターンの採用・不採用理由と適用箇所を表4にまとめる。不採用パターンはなく、条件付き並列を含め目的に応じて最小限の構成で採用する。

| Prompt Chaining | 採用 | Layer 0機械解析、Layer 1確率選別またはローカル代替、Layer 2反証レビュー、`JP-Humanizer` 推敲、および `style_check.py verify` を順次連結し、各段階の異常で停止または修正ループへ差し戻すため（`UNIT-002`, `UNIT-003`, `UNIT-005`）。 |

## 8. その他・特記事項

### 8.1 アーキテクチャ決定記録（ADR）

#### ADR-001: プログラムレイヤー（`UNIT-001`〜`UNIT-003`）の単一CLIスクリプト集約とデータ分離
- **コンテキスト**: `REQ-001`〜`REQ-003` の辞書管理、Layer 0解析、および Layer 1判定を独立スクリプトへ分散すると、バンドル切り出しの依存解決と単一コマンド起動が煩雑になる。
- **決定**: 辞書データのみを `tools/asdoq_dictionary.json`（JSON）へ分離し、プログラムロジック（`UNIT-001`・`UNIT-002`・`UNIT-003`）は単一の `tools/asdoq_lint.py` 内のモジュール境界関数群として集約する。
- **根拠とトレードオフ**: 自然言語レイヤーが覚えるべきCLIは1コマンドで完結し、`export_skillset.py` の同梱対象も最小化できる。将来ロジックが肥大化した場合はPythonパッケージ分割へ移行できるが、現規模（約1,800行見込み）では単一ファイルが保守性と配布性に優れる。

#### ADR-002: 要求1対1の7ユニット分割とテンプレート汚染防止のパス管理
- **コンテキスト**: `SW105` は `REQ-001`〜`REQ-007` の7機能要求から成り、`UNIT-006` は多数のDADAスキル・ガイドライン・スケルトン・ひな形・帳票へ跨る。
- **決定**: `REQ-001`〜`REQ-007` へ1対1で紐づく `UNIT-001`〜`UNIT-007` を維持し、`UNIT-004` の6特性定義は1特性1ファイル（各200行以下）へ分割する。また `UNIT-006` の `- **成果物パス**:` にはスキル・憲法・ガイドラインのみを列挙し、複製対象のスケルトン・ひな形・`REV101` 帳票は `- **関連テンプレート・帳票更新対象**:` へ分けて `UNIT-006` タグを付さない。
- **根拠とトレードオフ**: スケルトン複製時の新規案件文書へ不要な `UNIT-006` IDが混入する不具合を防ぎつつ、`agent_def_check.py unit` による開発対象ファイルの実装漏れ検知を両立できる。

#### ADR-003: 単体テストフレームワーク選定（`unittest`）とローカルHTTPモック／実機テスト境界
- **コンテキスト**: `SWP6` 2.2節（表1）の単体テストフレームワーク選定（`SWP6` 時点の `TBD`、Phase 3の8.2節で確定済み）が未決定であり、`TC-010`〜`TC-012` で外部依存と誤課金を防ぐ検証設計が必要である。
- **決定**: 単体・自動総合テストフレームワークとしてPython標準ライブラリ `unittest`（`pytest` 互換）を採用し、`tests/test_asdoq_reviewer.py` に配置する。HTTP通信検証は標準 `http.server` ローカルモックサーバと決定論的 `MockDecision1Client` で自動化し、実機API接続は `TC-012`（実行区分「手動」・Phase 4でAIが `.env.local` を用いて1回検証）へ分離する。
- **根拠とトレードオフ**: `unittest` は追加パッケージ不要でどのPython 3.8以降環境でも動作し、CIやオフライン環境での常時回帰実行を100%決定論的に維持できる。実API特有の仕様差異はPhase 4の `TC-012` と `EV-006` で確実に観測する。

#### ADR-004: TypeSafe AI `Jev` 廃止、`gemini-decision-1` 移行、閾値 `0.30` 是正、およびひな形除外設計
- **コンテキスト**: 旧版（`SW205` v1.1）は TypeSafe AI `Jev` を前提としており、さらに本文表で閾値 `0.65` と `0.30` の矛盾が残存していた。加えて、`SW105` v1.3 の第6章見出しや `SWP6` 第4章のテスト項目表列名といった公式ひな形語句が `asdoq_lint.py` で誤検知を起こしていた。

#### ADR-005: `/swarm`・`Gemini 4 Hydrogen`/`Argon` アダプタ分離（`Carbon` 非依存）と `README.md` 番号整合

#### ADR-006: Mermaid 10ノード以下分割・`[接続N]` 対・図直下と表直上のキャプション配置の恒久化
- **コンテキスト**: 大規模なMermaid図は人間にもAIにも視認性を落とし、図表キャプション位置の揺れは文書構造チェックで整合性低下を招く。
- **決定**: 「1つのMermaid図を10ノード以下へ分割し、分割間は `[接続N: ...]` の対で結ぶ」という分割規則を採用する。さらに「図キャプションは直下、表キャプションは直上へ配置する」の規約を `SW205` 自身とDADA作成4スキル・スケルトン・ひな形・ガイドラインおよび `asdoq_lint.py` へ定着させる。
- **根拠とトレードオフ**: 分割に伴う図数増加のコストはあるが、各図のノード数が10以下に保たれ、機械的検査（`heading_figure_table_check`）によって孤立図や参照漏れを確実に検出できる。
