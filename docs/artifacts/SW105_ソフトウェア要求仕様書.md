## 1. 概要

### 1.1 目的と位置づけ
本要求仕様書は、ASDoQ文書品質モデルと日本語技術文書基準に基づき、本質的な文書レビューと修正を低トークン消費で遂行するエージェント定義一式（スキル名: `asdoq-reviewer`）とDADAプロセス統合仕様を定める。
2025年以前のAI単体レビューには、(1) 全文走査によるトークン浪費、(2) 作成者の意図を好意的に推測して合格にする「忖度（追認バイアス）」という課題があった。さらに、(3) 「目的適合性・保守性」の素通り、(4) 「理解容易性・可読性」でのAI臭い文体、(5) 企業固有の「規範適合性」ルールへの未対応、(6) 図の過大化や分類表記の揺れも課題であった。
本プロジェクトはレビューの質とDADAプロセス全体の文書品質とを引き上げるため、新たに「4つの柱」を導入する。システム全体はLayer 0（NLP・図表・構造解析）、Layer 1（Google `gemini-decision-1` 判定またはローカルルール選別）、Layer 2（ASDoQ 6特性別専門レビュアー群）の3層で構成する。

- **第1の柱（6特性別エージェント分割と表記完全統一）**: ASDoQの6大品質特性ごとに専門レビュアー定義を分割する。指摘分類の表記を `[ASDoQ:特性-副特性]` の組へ完全統一し、責任境界と検査観点を明確にする。
- **第2の柱（拡張違反例辞書・企業カスタム辞書と図表ルールの恒久化）**: ASDoQ違反例に加え、NHK・共同通信、TC協会・JTF・JIS Z 8301、文化庁の知見を統合する。さらに「過大なMermaid図の分割」「図下・表上キャプション」「分割図間の接続番号明記」をDADA全作成スキルとひな形へ恒久組み込みする。
- **第3の柱（NLP＋Gemini Decision 1＋構造クロスリファレンス抽出による客観的証拠化）**: 形態素解析と構造クロスリファレンス抽出で客観的証拠を生成する。利用者が明示的にAPI有効化（ON）を選んだ場合のみ、`gemini-decision-1`（Decisions API）で出力トークン0の一括確率判定を実行する。OFF設定のまま実行する場合は外部通信せず、透過的なローカルルール選別へ切り替える。
- **第4の柱（反証駆動レビュー・Before/After提示・クォータ保護付き並列連携）**: 反証駆動（悪魔の代弁者）プロトコルと合格時の証拠引用義務を徹底する。既定は単一モデル省トークン動作とし、Product Ownerの明示指示があるときだけ Antigravity `/swarm` と `Gemini 4 Hydrogen` / `Argon`（Carbon非依存）による並列処理を起動する。

### 1.2 適用範囲
- **対象（スコープ内）**:
  - 単体およびDADAプロセス内で動作する調整スキル（`asdoq-reviewer`）と、ASDoQ 6大品質特性別の専門レビュアー定義（6モジュール）の構築
  - 拡張違反例辞書および企業カスタムルール編集機構（`tools/asdoq_dictionary.json`）の構築（`[ASDoQ:特性-副特性]` 表記統一を含む）
  - Layer 0 NLP解析・構造クロスリファレンス抽出・過大図および分割図接続番号検証を行う `tools/asdoq_lint.py` の構築
  - Layer 1 Google `gemini-decision-1`（`v1beta/decisions`）一括判定モジュール、APIキー安全読込（`.env.local` / `.env` / `.env.example`）、実行時ON/OFF選択制御、および透過的ローカルルールフォールバックの構築
  - DADA全作成スキル・ひな形・ガイドラインへの図分割・図下および表上キャプション・接続番号・自己点検ルール組み込み（対象: `requirements-engineer`・`test-engineer`・`architect`・`document-writer`・各 `*_skeleton.md`・`docs/templates/agent/phase1〜3_*.md`・`docs/guidelines/`）
  - 既存レビュアーおよび運用定義への `[ASDoQ:特性-副特性]` 統一と環境別アダプタ統合（対象: `requirements-reviewer`・`test-reviewer`・`architecture-reviewer`・`code-reviewer`・`JP-Humanizer`・`dada-process`・`.agents/AGENTS.md`・`REV101_*.md`）
  - スキルセット切り出しツール（`tools/export_skillset.py`）の拡張および `README.md` の整備（料金比較・API設定・思考レベル・`/swarm`・他ツール利用手順）
- **対象外（スコープ外）**:
  - DADAプロセスの承認ゲート型における最終的なドキュメント承認判断（Product Ownerである人間が実施する）
  - ソースコードのアルゴリズム欠陥や単体テストコード自体の論理検証（`code-reviewer` と `dada_check.py code` が担当する）
  - Google Cloud Billing や Google AI Studio 上でのAPIキー発行・課金上限設定・請求支払い運用（利用者自身が管理する）
  - `Gemini 4 Carbon` モデルへの依存（Google AI Pro 契約範囲の `Gemini 4 Hydrogen` / `Argon` のみで全工程を完結させる）

### 2.3 役割分割方針（三原則 Simplicity）

| :--- | :--- | :--- | :--- |
| レビュー調整・修正役（`asdoq-reviewer`） | API利用有無（ON/OFF）を確認し、文書種別プロファイル判定、`tools/asdoq_lint.py` 実行、必要特性へのルーティング（既定省トークン／任意 `/swarm` アダプタ）、統合レポートと修正文書生成を担う | する（メインスキル） | 単体切り出し単位を一本化し、API利用選択とルーティングを一箇所で制御するため（問2・問3・問5がYes） |

**分割しない場合の記録**: 6大品質特性別の専門定義ファイルは `.agents/skills/` 直下に6個並べるのではなく、`asdoq-reviewer/references/` 配下に配置する。入口を `asdoq-reviewer` に一本化すると、利用者や他ツール利用時の起動ルーティング衝突を防げる。

## 4. 機能要求

### 4.1 ユースケースとシナリオ
1. **ユースケース1：単体利用モードによるレビューと修正（API選択＋任意 `/swarm` 厳密モード）**
   - **シナリオ**: 利用者が `asdoq-reviewer` で対象文書のレビューを指示する。オーケストレーターは最初に `gemini-decision-1` APIの使用可否（ON/OFF）を利用者へ確認する。ON設定の運用では `tools/asdoq_lint.py --decision1 on` を、OFF設定（既定）では `--decision1 off` を実行する。通常は省トークンで重点特性のみを検証し、利用者が「`/swarm` を使って」「全6特性厳密に」と指示した場合のみ `/swarm` 並列検証を起動する。最後に `[ASDoQ:特性-副特性]` ラベル付きのBefore/Afterレポートと検証済み修正文書を返す。
2. **ユースケース2：DADAプロセスでの作成時自己点検・フェーズ別API制御・工程レビュー**
   - **シナリオ**: 承認ゲート型では各Phase開始時に、自律型ではPhase 0/1の開始前に、利用者が Decision 1 APIのON/OFFを選択する。要件・テスト・設計・文書記述の4作成スキルは規定の「大図分割」「図下・表上」「分割図の接続番号」規則で文書を作成し、完了前に `asdoq_lint.py` で事前点検する。続く自己校正で工程別レビュアーが共通エンジンと専門定義を参照し、`REV101_*.md` へ `[ASDoQ:特性-副特性]` 形式で指摘を記録する。
3. **ユースケース3：企業カスタム辞書・秘密情報隔離環境での運用と他ツール切り出し**
   - **シナリオ**: 利用者がカスタム辞書に企業固有NG/OK表現を追加する。有料または無料API連携を使う運用では `.env.local` または `.env` に `GEMINI_API_KEY` を設定する。さらに `tools/export_skillset.py` でスキル一式を切り出し、Antigravity以外の環境（Codex / Claude Code / Cursor / GitHub Copilot）でも設定ファイル互換で運用する。

### 4.2 機能詳細

#### REQ-001: 拡張違反例辞書・企業カスタム辞書機構と表記基準統一
- **概要**: ASDoQ 6大品質特性、TC協会・JTF・JIS Z 8301、NHK・共同通信・文化庁の知見を統合した拡張違反例辞書と企業カスタム辞書機構を提供する。全ルールの品質特性名と指摘ラベル表記を `[ASDoQ:特性-副特性]` 形式に統一する。
- **レイヤー**: プログラム
- **入力 / 処理 / 出力**:
  - 入力は標準辞書JSON（`tools/asdoq_dictionary.json`）および任意のカスタム辞書JSON（`--custom-dict <path>`）とする。
  - 処理ではカテゴリ1〜8の標準ルールと企業カスタム領域を検証し統合する。併せて品質特性名を正準6特性名（`目的適合性`・`保守性`・`整合性`・`理解容易性`・`可読性`・`規範適合性`）および `[ASDoQ:特性-副特性]` 書式へ統一する。
  - 出力として検証済みルールセットオブジェクトを返す。辞書検証コマンドの実行際は、登録件数・カスタム件数・ライセンス表示を標準出力へ出して終了コード0で終了する。
  - **カテゴリ1（非曖昧性・一意性 / `[ASDoQ:理解容易性-非曖昧性（一意性）]`）**: 曖昧語・相対日時表現・全体否定・部分否定の曖昧表現・状態とイベントとの混同・中止法連鎖を検査する。
  - **カテゴリ2（非曖昧性・識別性 / `[ASDoQ:理解容易性-非曖昧性（識別性）]`）**: 必須補語を欠いた単独動詞記述、起点「より」と終点「へ」・方向「に」の誤用を検査する。
  - **カテゴリ3（表現適切性・AI-Slop排除 / `[ASDoQ:可読性-表現適切性]`）**: 動作主のない受動態連続、視点不統一、AI特有の比喩・誇張・過剰対比・英語由来ダッシュ繋ぎを検査する。
  - **カテゴリ4（簡潔性・冗長表現 / `[ASDoQ:可読性-簡潔性]`）**: 二重否定、多重入れ子文、冗長な複合動詞・官庁表現、4語以上の名詞連続を検査する。
  - **カテゴリ5（表記適切性・用字用語 / `[ASDoQ:可読性-表記適切性]`）**: 敬体と常体の混在、括弧不統一、数値単位欠落、ひらがな推奨語の漢字表記を検査する。
  - **カテゴリ6（文法適合性 / `[ASDoQ:規範適合性-文法適合性]`）**: 主語と述語のねじれ、同一助詞の1文内3回以上連続、ら抜き・さ入れ・い抜き言葉、順接「が」の長文化を検査する。
  - **カテゴリ7（整合性・保守性・目的適合性シグナル / `[ASDoQ:整合性-無矛盾性]` ほか）**: 理由なき省略記述、解消時期のない未決定記述、検証手段のない抽象目標語、図表番号と参照の不整合を検査する。
  - **カテゴリ8（規範適合性・図表配置とラベル規則 / `[ASDoQ:規範適合性-記法適合性]` ほか）**: 推測・意見ラベル欠落、図表番号位置違反（図は直下・表は直上）、過大な図（10ノード超）や分割図の接続番号欠落、旧分類表記の残存を検査する。
  - **企業カスタム編集機能**: `custom_ng_rules`・`custom_ok_terms`・`disabled_rule_ids`・`corporate_conformance_rules` をコード変更なしで編集・反映できる。
- **異常系**: 辞書ファイル不在またはJSON構文不正が発生した場合、もしくは必須キー（`id`, `category`, `asdoq_characteristic`, `severity`, `pattern_type`, `hint`）が欠落した場合は、標準エラー出力へ原因を表示して終了コード2で終了する。
- **検証条件 (Acceptance Criteria)**:
  - カテゴリ1〜8を網羅する合計80件以上の標準ルールが `tools/asdoq_dictionary.json` に定義されていること。
  - 全ルールの特性名と出力ラベルが `[ASDoQ:特性-副特性]` 書式かつ正準6特性名（`目的適合性`・`保守性`・`整合性`・`理解容易性`・`可読性`・`規範適合性`）へ統一されていること（旧称 `合目的性` を特性ID・ラベル名に使わないこと）。
  - カスタム辞書へ追加したNG表現・規範ルールをシステムが検出し、同時にホワイトリスト語を違反対象から除外すること。
  - MIT LicenseおよびASDoQドキュメントライセンス（ADL）表記を満たすこと。
  - 不正JSONや欠損パスを指定した場合、終了コード2を返すこと。
- **優先度**: Must

#### REQ-002: Layer 0（形態素解析・拡張辞書・構造クロス・図表分割/接続検査）ツール
- **概要**: 形態素解析と拡張辞書で文書を走査し、確定違反一覧と4種類の構造クロスリファレンス表を抽出する。併せて過大Mermaid図・図下および表上の位置・分割図接続番号を検査し、Layer 1向け疑義スライス抽出機能付きCLIツール（`tools/asdoq_lint.py`）を提供する。
- **レイヤー**: プログラム
- **入力 / 処理 / 出力**:
  - 入力は検査対象Markdownパス（`--input <path>`）およびCLI引数（`--dict`・`--custom-dict`・`--profile`・`--characteristic`・`--format`・`--summary`・`--max-items` 既定25）とする。
  - 処理では以下のステップ1〜6を実行する。
  - 出力として確定指摘・構造クロス表・疑義スライス・6特性スコア・推奨ロード特性を返す。判定結果に応じ、終了コード（`0`=Highなし、`1`=Highあり、`2`=エラー）で終了する。
  - **ステップ1（文書構造分解）**: 通常コードブロックを検査対象から除外する。そのうえで文書を見出し・段落・表・Mermaid図ブロック・一文単位へ分解する。
  - **ステップ2（形態素・構文解析）**: `janome` が導入済みの場合は形態素解析を実行する。未導入の場合は、Python標準ライブラリの正規表現と文字種境界解析とへ自動フォールバックする。
  - **ステップ3（辞書照合）**: REQ-001の統合ルールで確定違反を検出する。
  - **ステップ4（構造クロスリファレンス表と図表ルールの自動抽出）**:
    1. **目的・スコープ要素チェック**: 文書内の「読み手」「目的」「適用範囲（対象内・対象外）」およびプロファイル別必須章の有無を抽出する。
    2. **用語集 vs 本文クロス突合**: 用語定義表の登録語の本文出現数、本文に3回以上出現し用語定義表に未定義の複合名詞・専門用語候補、および類似表記ゆれペアを抽出する。
    3. **数値・単位・条件クロス一覧**: 文書内のすべての「数値＋単位」と条件閾値を行番号・章名付きで一覧化する。
    4. **見出し・図表クロス突合（図分割・接続番号ペア・位置検査強化）**: 以下5点を検査する。
       - 過大なMermaid図検出: 1つのMermaid図ブロック内のノード数が推奨上限（**10ノード**）を超える場合（11ノード以上）、分割推奨の警告を出力する。
       - 分割図間の接続番号整合検査: 各Mermaid図から `[接続①: ...]` 形式（丸数字または半角数字）の接続番号トークンを抽出する。同一番号が2つ以上の異なるMermaid図ブロックに出現すれば対成立と判定し、1ブロックのみに出現した番号を孤立接続番号として警告する。
       - 図下・表上キャプション位置検証: 図タイトルがMermaid図より上にある違反、表タイトルが表ブロックより下にある違反を検出する。
       - 図表参照突合: 本文中の図番号・表番号参照と定義済みキャプションとの一致状況、さらに図内ラベルと本文用語との一致を抽出する。
       - 希薄見出し検出: 中身が1文以下しかない見出し節を抽出する。
  - **ステップ5（疑義スライス抽出）**: 文脈判定が必要なグレーゾーン文・段落に対し、行番号・見出し名・疑われる特性コードを付与して抽出する。
  - **ステップ6（スコア・推奨特性算出）**: プロファイル重み付けを反映した6特性別健全度スコアと要重点レビュー特性を算出する。
- **異常系**: 対象ファイル不在または空ファイル（0バイト）の場合は標準エラー出力へ原因を表示し、終了コード2で終了する。`janome` 未導入でも例外停止せず標準ライブラリモードで完走する。
- **検証条件 (Acceptance Criteria)**:
  - REQ-001のカテゴリ1〜8違反を含むテスト文書に対して、全8カテゴリの指摘を行番号および `[ASDoQ:特性-副特性]` 付きで検出すること。
  - 構造クロスリファレンス表の4項目すべてが出力に含まれること。さらに `heading_figure_table_check` が「11ノード以上の過大Mermaid図」「1ブロックのみ出現の孤立接続番号 `[接続N]`」「図上・表下の位置違反」を機械検出すること。
  - 正常文が70%以上を占める2,000文字以上の基準Markdown文書を入力したとき、正常文除外後の疑義スライス文字数が原文書の50%以下へ圧縮されること。
  - `--format json` 実行後に確定指摘・構造クロス表・疑義スライス・6特性集計から成る有効JSON文字列を標準出力へ返すこと。
  - `janome` 有無の双方で例外なく完走すること。
- **優先度**: Must

#### REQ-003: Layer 1（Google `gemini-decision-1` Decisions API）一括判定と透過的フォールバック
- **概要**: TypeSafe AI（Jev）を完全に廃止し、Layer 1を Google の `gemini-decision-1`（Decisions API / `v1beta/decisions`）へ全面刷新する。1回のprefillリクエストで最大1,000問の確率判定を出力トークン0で実行する。API未使用（既定 `off`）設定では外部通信を行わず、同一の `answers` 互換出力構造で後段へ引き渡す。
- **レイヤー**: プログラム
- **入力 / 処理 / 出力**:
  - 入力はLayer 0の疑義スライスと構造検証項目、およびCLIオプション（`--decision1 <off|on|mock>` 既定 `off`、`--threshold <0.0-1.0>` 既定 `0.30`）とする。
  - 処理ではステップ1〜6を実行し、外部APIの呼び出し可否を制御する。
  - 出力として `gemini-decision-1` の `answers` 構造と互換な判定結果（`noul`・`choice`・`score`・採否ステータス・`DECISION1_MODE`）を返す。
  - **ステップ1（APIキー読込と利用モード判定）**: `GEMINI_API_KEY` を「OS環境変数 > `.env.local` > `.env`」の順で読み込む。ファイル読込では前後の引用符（`"`・`'`）を除去し、空文字 `""` は未設定とみなす。`--decision1 off`（既定）ではAPIキー有無に関わらず外部通信をせずステップ5へ進む。
  - **ステップ2（バッチ構成と肯定表現制約）**: 質問数0件ではHTTP送信はせず、`DECISION1_MODE: on_skipped (no_questions)` と空の `answers` を返す。コンテキストキャッシュとBatch APIは非対応である。1件以上ある場合、文書抜粋（262,144入力トークン以内）と質問群 `questions`（1〜1,000問単位）から1リクエストを構成する。`Question key` は `[A-Za-z0-9_-]+`（最大64文字）形式に従う。キー文字列はモデルへ伝わらないため、質問文 `instructions` へスライスID・行番号・見出しを必ず明記し、否定形ではなく肯定表現で記述する。
  - **ステップ3（3種質問プリミティブの送信）**: エンドポイント `POST https://generativelanguage.googleapis.com/v1beta/decisions`（`x-goog-api-key` ヘッダ）または `google-genai` SDK v3.2以上（`api_version="v1beta"`）で呼び出す。SDK未導入の場合は標準ライブラリ `urllib.request` でREST呼出しを実行する。
    - `noul`: 真偽判定確率（0.01〜0.99）と `confidence` を取得し、曖昧性・主体欠落・理由欠落・事実意見混同・検証困難を評価する。
    - `choice`: `criteria` の選択肢キーには前後の空白や非ASCII文字を含まないASCII識別子（例: `C1_1`, `C4_1`, `other`）のみを使用し、受信後にPython側で `[ASDoQ:特性-副特性]` ラベルへ変換する。
    - `score`: `criteria` 配列を低度から高度の順（例: `[レベル0問題なし, レベル1中程度, レベル2重大]`）で指定し、期待値 `score`、`legend`、段階確率 `probabilities` を取得する。
  - **ステップ4（見逃し防止閾値判定）**: 見逃し防止のため閾値既定値を安全側の `0.30` とする。`noul >= 0.30` または重度 `score` / 重大 `choice` 判定のスライスをLayer 2へ昇格させ、`0.29` 以下の明確な正常スライスのみを棄却する。
  - **ステップ5（`--decision1 off` 設定の透過的ローカルルールフォールバック）**: 外部API通信を行わず、ローカルルール判定により `noul`・`choice`・`score` から成る同一 `answers` 互換辞書を生成して後段へ渡す。ただしレポート上の表示は偽らず、必ず `DECISION1_MODE: off (local_rule_fallback)` と明記し、文脈判定をLayer 2へ委ねる。
  - **ステップ6（`--decision1 mock` 単体テスト支援）**: 決定論的モック応答（`DECISION1_MODE: mock`）を返し、ネットワーク不要で `noul`/`choice`/`score`・ASCIIキー変換・閾値 `0.30` 分岐を検証できるようにする。
- **異常系**:
  - `--decision1 on` 指定時に `GEMINI_API_KEY` が環境変数・`.env.local`・`.env` のいずれにも未設定であれば、設定ファイルパス（`.env.local` / `.env`）と書式（`GEMINI_API_KEY="..."`）を標準エラー出力へ案内して終了コード2で終了する。
  - 廃止オプション `--jev` が指定された場合は引数エラーとし、`--decision1` への移行案内とともに終了コード2で終了する。
  - `--decision1 on` 実行でのタイムアウトやHTTP 429/5xx には最大2回リトライし、2回失敗した場合は警告を出してローカルフォールバックへ切り替える。

- **形態素解析および既存DADAツール連携**:
  - `janome`（未導入のときは標準ライブラリ自動フォールバック）。
  - `tools/dada_check.py`、`tools/style_check.py`、`tools/agent_def_check.py`、`tools/office_io.py` と競合せず協調動作する。

## 6. 非機能要求（性能・品質等）

### 6.1 性能・効率性
- **ローカル解析性能（Layer 0 + 透過フォールバック）**: 10,000文字規模のMarkdown文書に対する `python tools/asdoq_lint.py --decision1 off` の実行時間が、標準的なPC環境で **3秒以内** であること（測定区間はCLI起動から終了コード返却までとする）。
- **Decisions API 一括効率**: `--decision1 on` 設定では、コンテキストキャッシュとBatch非対応を補うため、1リクエスト（最大262,144入力トークン・最大1,000問）へ質問を束ねて送信する。1リクエスト内での一括評価により、出力トークン 0（エンドツーエンド約150〜250ms/リクエスト）で判定を完了する。
- **クォータ・トークン消費抑制**: 疑義スライス抽出文字数は原文書の **50%以下** に圧縮し、1カテゴリ出力上限を既定 **25件** とする。通常レビューのロード対象は **最大4特性以内** に抑え、`/swarm` は明示指示があるときだけ起動する。

### 6.2 信頼性・安全性
信頼性および安全性に関する非機能要求を表7に示す。

**表7：信頼性・安全性要求**

| 項目 | 要求 |
| :--- | :--- |
| 確率的振る舞いの許容範囲 | 自然言語レイヤー評価セットにおいて、Must要求は5回試行で4回以上（合格率80%以上）、Should要求は3回試行で3回合格を満たすこと。プログラムレイヤーの単体テストは合格率100%であること。 |
| 課金・外部通信の安全側既定 | `--decision1` の既定値を `off` とし、利用者が明示的にONを選択しない限り外部Decision APIへの課金や送信を発生させないこと。 |
| 透過モードの表示誠実性 | `--decision1 off` 設定では同じ `answers` 互換形式で後段へ渡しつつ、レポート表示に `DECISION1_MODE: off (local_rule_fallback)` を明記し、API実行と誤認させないこと。 |
| 幻覚・忖度・逸脱への対策 | 指摘箇所・IDは実ファイルから転記し創作しない。DADA統合時はレビュアーによる成果文書直接編集を禁止し、修正後は `style_check.py snapshot` / `verify` で意味保持を確認する。 |
| 停止条件 | 単体修正ループおよびDADA自己校正ループは最大2周を上限とし、未解消のHigh指摘はProduct Ownerへ報告する。 |

### 6.3 保守性・拡張性
- **Simplicityと100%移植性**: 6特性定義と `tools/asdoq_lint.py` へロジックを集約する。`/swarm` や推論深さの設定は `.agents/AGENTS.md`・オーケストレーター・`README.md` のアダプタ層に分離し、Codex・Claude Code・Cursor・GitHub Copilot での動作互換を維持する。
- **辞書駆動拡張と整合検証**: JSON編集のみで企業ルール・カスタム語彙を追加できる。変更後は `python tools/agent_def_check.py` により整合性を検証し、終了コード0で終了する状態を維持する。

### 6.4 セキュリティ
- **APIキーの厳格隔離**: `GEMINI_API_KEY` は環境変数または `.gitignore` で除外済みの `.env.local` / `.env` のみから読み込む。ソースコード・スキル文書・ログ・コミット対象ファイル（`.env.example` は空テンプレートのみ）へAPIキーを絶対に出力・保存しない。
- **外部送信制御とデータ保護案内**: `--decision1 off` 設定では外部ネットワーク通信を0回に抑える。`--decision1 on` を利用する場合は、Free Tier（学習利用の可能性あり）と Paid Tier（データ保護・従量課金）の差異を `README.md` と開始確認で明示し、機密文書ではPaid Tier推奨またはOFF選択を促す。
