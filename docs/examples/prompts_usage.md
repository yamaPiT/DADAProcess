# DADAプロセス プロンプト集（そのままコピーして使えます）

このファイルは、DADAプロセスで開発を始めるための**指示文（プロンプト）の見本**です。作りたいものに合わせて、下の4つから1つ選んでコピーし、要求の部分を書き換えて使ってください。

> [!TIP]
> **むずかしい言葉は、このファイルの最後にある[やさしい言い換え表](#付録-用語のやさしい言い換え表)にまとめてあります。** 読んでいて意味が分からない言葉が出てきたら、そこを見てください。

---

## まず、2つの質問に答えてください

DADAプロセスの進み方は、次の2つを決めるだけで確定します。

### 質問1：何を作りますか？

| 答え | 選ぶもの | 具体例 |
| :--- | :--- | :--- |
| **プログラム**を作りたい | **従来型プログラム** | Webアプリ、スマホアプリ、業務システム、機械を制御するソフト |
| **AIの相棒（エージェント）**を作りたい | **エージェント定義** | 議事録を書くAI、データを分析するAI、コードをレビューするAI |

**「エージェント定義」とは**、AIに「こういう時はこう動いてね」と教える説明書のことです。プログラムのコードではなく、**日本語で書いた手順書**が主な成果物になります（このリポジトリの `.agents/skills/` の中身が、まさにその実例です）。

### 質問2：どう進めますか？

| 答え | 選ぶもの | どうなるか |
| :--- | :--- | :--- |
| 区切りごとに内容を確認したい | **DADAプロセス承認ゲート型** | 「要求」「テスト計画」「設計」「総合テスト報告書」の各段階が終わるたびにAIが止まり、あなたの承認を待ちます |
| 完成するまでAIに任せたい | **DADAプロセス自律型** | 要求を受けたあと、AIが自分で点検して開発しきります。できあがったものを見て、必要ならあなたが開発Loopを回します |

**開発Loop**とは、できあがったものを見てから「ここをこう直したい」と要求を足し、再び開発することです。承認ゲート型でも自律型でも、人間が回す場合があります。

### 組み合わせると、4つになります

| | **承認ゲート型**（区切りごとに確認） | **自律型**（一気に完成まで） |
| :--- | :--- | :--- |
| **プログラム（P）** | [P開発承認ゲート型](#p開発承認ゲート型-プログラムを区切りごとに確認しながら作る) | [P開発自律型](#p開発自律型-プログラムを一気に完成まで作る) |
| **AIの相棒（A）** | [A開発承認ゲート型](#a開発承認ゲート型-aiの相棒を区切りごとに確認しながら作る) | [A開発自律型](#a開発自律型-aiの相棒を一気に完成まで作る) |

> **P** は Program（プログラム）、**A** は Agent（エージェント定義／AIの相棒）の略です。

> [!NOTE]
> **何も指定しなくても動きます。** 「DADAプロセスで開発を開始してください。〜」と書くだけなら、**プログラム × 承認ゲート型**（P開発承認ゲート型）として進みます。今までどおりの使い方は変わりません。

> [!IMPORTANT]
> **最後の「動かして確かめる」作業は、どの使い方でも人がやります。** 自律型でAIに任せられるのは、実装と総合テスト報告書が終わるまでの部分です。できたものが本当に役に立つかどうかは、機械には判断できません。人間がSWP6にテスト結果を書く必要はありません。

## P開発承認ゲート型 プログラムを区切りごとに確認しながら作る

**こんなときに使います**：品質や安全性が大事な開発。仕様を自分で握っておきたいとき。**初めてDADAプロセスを使うなら、まずこれをおすすめします。**

### コピー用の指示文

```text
DADAプロセス承認ゲート型を開始します。
・開発対象：従来型プログラム（Python/FastAPIによるREST APIサーバー）
・要求概要：[システムの要求]
各Phase（要求・テスト仕様・アーキテクチャ・実装と総合テスト報告）の完了ごとに自己校正を行い、人間の確認・承認ゲートを挟んで進めてください。
```

### 上の指示文を、やさしい言葉で書いた版（意味は同じです）

```text
DADAプロセスで開発を始めてください。区切りごとに私の確認を取りながら進めてください。

・作るもの：Pythonで動くWebサービスの裏側（PythonのFastAPIというしくみを使ったAPIサーバー）
・やりたいこと：[作りたいものを、ふつうの日本語で書く]

「何を作るか（要求）」「どうテストするか」「どう組み立てるか（設計）」「実装と総合テスト報告」の4段階で進めてください。
各段階が終わったら、AI自身が一度見直して直したうえで、私に見せて確認を取ってください。実装のあとにAIが総合テストを実施して報告書を書くので、その報告書も確認してください。テスト結果をあなたがSWP6に書く必要はありません。
```

### 指示文の各行が何を意味するか

| 書いた言葉 | 意味 |
| :--- | :--- |
| 承認ゲート型 | 区切りごとに人が確認する進め方 |
| 開発対象：従来型プログラム | 作るものはプログラムのコードです、という宣言 |
| 要求概要 | 「何を作りたいか」の説明。箇条書きでも、文章でもかまいません |
| Phase（フェーズ） | 開発の段階のこと。要求→テスト仕様→設計→実装の順に進みます |
| 自己校正 | AIが自分の書いたものを、別の視点で見直して直すこと（人に見せる前の下書き点検） |
| 承認ゲート | 人が「これでOK」と言うまで先へ進めない関門 |

### AIはこう返してきます（この宣言が出れば正常です）

> 本依頼を以下と判定しました。
> - 開発対象: **従来型プログラム**
> - 実行モード: **承認ゲート型**
> - 変更スケール: **Major**（新規開発のため全Phase実行）

宣言があなたの意図と違っていたら、その場で「対象はエージェント定義です」などと訂正してください。

**「変更スケール」の意味**：作業量の見積もりです。3種類あります。

| 表示 | 意味 |
| :--- | :--- |
| **Major**（大きい） | 新しく作る、または大きく仕様を変える。全段階を通ります |
| **Minor**（小さい） | 今ある機能の微調整。設計の作り直しは省きます |
| **Hotfix**（バグ直しだけ） | 不具合の修正だけ。要求や設計は変えません |

### できあがるもの

| 段階 | できあがるファイル |
| :--- | :--- |
| 1. 要求 | `docs/artifacts/SW105_ソフトウェア要求仕様書.md`（何を作るかの一覧）<br>`docs/artifacts/REV101_Requirements.md`（指摘と直した記録） |
| 2. テスト仕様 | `docs/artifacts/SWP6_ソフトウェア総合テスト仕様書・報告書.md` の1〜4章（どう確かめるかの計画）<br>`docs/artifacts/REV101_Test.md` |
| 3. 設計 | `docs/artifacts/SW205_ソフトウェアアーキテクチャ設計書.md`（どう組み立てるかの図と部品一覧）<br>`docs/artifacts/REV101_Design.md` |
| 4. 実装と総合テスト報告 | プログラム本体とテストのコード<br>`docs/process/impl_progress.md`<br>SWP6の5〜6章（AIがテストを実施した結果と総合判定。**あなたは報告書を承認する**）<br>`docs/artifacts/BUG101_バグ管理表.md` |

### あなたがやること

各段階の終わりに、AIが「点検結果」と「見直しの結果」を添えて確認を求めてきます。中身を読んで、良ければ「承認します」と返してください。Phase 4の終わりでは、**総合テスト報告書（SWP6の5〜6章）**を承認します。テスト結果をあなたがSWP6に書く必要はありません。できあがったものを動かす評価は、そのあとの Phase 5 です。

直してほしい点があるときは、次のどちらでも伝わります。

1. チャットに書く（かんたん）
2. `docs/artifacts/REV101_*.md` というファイルに直接書き込む（あとで記録として残る）

## P開発自律型 プログラムを一気に完成まで作る

**こんなときに使います**：とりあえず動くものを早く見たいとき。とても高い品質（他でも使い回せる、極限まで速い、認証を取る）までは求めないプログラム。

### コピー用の指示文

```text
DADAプロセス自律型を開始します。
・開発対象：従来型プログラム（C言語による組込み通信制御モジュール）
・要求概要：[モジュールの要求]
・自律実行指示：各Phaseの自己校正および機械チェック（dada_check.py等）がAPPROVEDになったら、人間の確認を待たずに次Phaseへ自律遷移し、Phase 4の実装・総合テスト実施および報告書完成まで一気に完走してください。人間は完成した最終成果物と報告書を評価します。
```

### 上の指示文を、やさしい言葉で書いた版（意味は同じです）

```text
DADAプロセスで開発を始めてください。完成するまで、私の確認を待たずに進めてください。

・作るもの：C言語で書く、機械に組み込む通信制御のプログラム
・やりたいこと：[作りたいものを、ふつうの日本語で書く]

各段階の終わりに、AI自身の見直しと点検ツール（tools/dada_check.py）による自動点検を必ず実施してください。
どちらも問題なしとなったら、私を待たずに次の段階へ進んでください。
実装・総合テストの実施と報告書が終わるところまで、そのまま進めてください。私はできあがったものと報告書を見て評価します。
```

### 指示文の各行が何を意味するか

| 書いた言葉 | 意味 |
| :--- | :--- |
| 自律型 | AIが自分で判断して次の段階へ進む進め方 |
| 機械チェック | 点検用のプログラム（`tools/dada_check.py`）を実行して、書き漏れや対応漏れを自動で探すこと。AIの記憶や勘に頼らず、確実に数えます |
| APPROVED | 点検が「合格」だったことを表す合図の言葉（英語で「承認された」の意味） |
| 自律遷移 | AIが自分の判断で次の段階へ移ること |
| 単体テスト | 部品ひとつずつが正しく動くか確かめるテスト |
| 総合テスト | 要求どおり動くかを、できあがったもの全体で確かめるテスト。DADAでは結合テスト工程は置かない |
| 完走 | 途中で止まらず最後まで進むこと |

### AIが勝手に走り続けるわけではありません

各段階の終わりで、AIは次の**6つをすべて満たしたときだけ**次へ進みます（詳しい定義は `.agents/AGENTS.md` の第10.3節にあります）。

1. あなたが最初に「DADAプロセス自律型で」（または「自律型で」）と書いている
2. 点検ツールが**合格（終了コード 0）** を返した ＝ 重大な指摘がゼロ
3. AI自身の見直しが2回以内で終わり、重大な指摘が残っていない
4. その段階の「終わっていい条件」を全部満たしている
5. （AIの相棒を作る場合のみ）動作の確かめが基準を満たしている
6. 下の「必ず止まる場面」に当てはまらない

### 必ず止まる場面

次のことが起きたときは、自律型でもAIは**手を止めて、あなたに判断を求めます**。分からないところを勝手な想像で埋めて進むことはしません。

- テストの書きようがないほど、要求がぼんやりしている
- 実装している途中で、設計の不備や矛盾が見つかった
- 見直しを2回やっても、重大な指摘が消えない
- 点検の重大指摘が2回続けて消えない
- 同じテストが5回続けて失敗した
- 何を作るか・どう進めるかの判定ができない
- ファイルを消す・お金がかかる・パスワードなど秘密の情報を扱う、といった取り返しのつかない操作が必要になった
- 最初に聞いていた話の範囲を超える、新しい要求が必要だと分かった
- 同じ段階へのやり直しが2回起きた

定義の全文は `.agents/AGENTS.md` 第10.4節の9項目です。

### あとから「なぜ進んだのか」を確かめる方法

AIが自分で下した判断は、すべて `docs/process/autoloop_log.md` に1行ずつ記録されます。完成後にこのファイルを見れば、**どの段階を、何を根拠に通過したのか**を追いかけられます。人の確認を省いた分の透明性を、この記録が担保しています。

### 応用：「作りたいものの認識だけ、先に合わせたい」とき

いちばん困るのは、**要求の受け取り方がズレたまま最後まで作られてしまうこと**です。それだけ先に防ぎたい場合は、上の指示文の最後に次の1行を足してください。

```text
ただし、要求仕様書（SW105）ができた時点でのみ一度止まって、私の確認を受けてください。
```

こうすると、最初の「何を作るか」の段階だけ確認が入り、そこから先は一気に進みます。

## A開発承認ゲート型 AIの相棒を区切りごとに確認しながら作る

**こんなときに使います**：仕事で使うAIエージェント（AIへの手順書と、それを支える道具）を、品質を確かめながら作りたいとき。

### コピー用の指示文

```text
DADAプロセス承認ゲート型を開始します。
・開発対象：エージェント定義（Antigravity 2.0向け議事録生成・評価エージェント一式）
・要求概要：[エージェントの要求]
・構成留意点：エージェント定義は『自然言語レイヤー（SKILL.md, AGENTS.md, 参照docs）』と『プログラム言語レイヤー（Pythonツール、構文チェッカー）』の二重構造として責務を切り分けること。
各Phaseごとにエージェント要求仕様書、二重評価仕様書（Eval Dataset＋単体テスト）、アーキテクチャ設計書、総合テスト報告書を作成し、人間の承認ゲートを挟んで進めてください。
```

### 上の指示文を、やさしい言葉で書いた版（意味は同じです）

```text
DADAプロセスで開発を始めてください。区切りごとに私の確認を取りながら進めてください。

・作るもの：AIの相棒（Antigravity 2.0で動く、議事録を書くAIと、その出来を採点するAIの一式）
・やりたいこと：[作りたいものを、ふつうの日本語で書く]

作るときは、次の2種類に役割をはっきり分けてください。
 (1) 日本語で書く手順書（SKILL.md、AGENTS.md、参考資料）… 状況を見て判断する部分を担当
 (2) Pythonで書く道具（点検ツールなど）… 決まった手順で確実に処理する部分を担当

各段階で「何を作るかの一覧」「確かめ方の一覧（AIの振る舞いの採点表＋道具のテスト）」「組み立て方の設計」を作り、
そのたびに私の確認を取ってください。実装のあとにAIが総合テストを実施して報告書を書くので、その報告書も確認してください。
```

### 指示文の各行が何を意味するか

| 書いた言葉 | 意味 |
| :--- | :--- |
| エージェント定義 | AIに「こう動いてね」と教える説明書一式 |
| 自然言語レイヤー | **日本語で書く部分**。状況に応じた判断や、作業の段取りを担当します |
| プログラム言語レイヤー | **プログラムで書く部分**。答えが1つに決まる処理や、抜けのない照合を担当します |
| レイヤー | 「層」のこと。ここでは「役割の担当区分」という意味で使っています |
| 責務 | 「担当する仕事」のこと |
| 二重構造 | 上の2つに役割を分ける作り方 |
| 二重評価仕様書 | 上の2つを**別々の方法で確かめる**ための計画書 |
| Eval Dataset（評価セット） | AIの振る舞いを採点するための問題集。同じ問題を何回も出して、合格した割合で判定します |
| 単体テスト | 道具（プログラム）が正しく動くか確かめるテスト |
| 構文チェッカー | 書き方の誤りを見つける道具 |

### なぜ確かめ方を2種類に分けるのか

作るものの性質が根本的に違うためです。

| | プログラムで書いた部分 | 日本語で書いた部分 |
| :--- | :--- | :--- |
| 振る舞い | 同じ入力なら**いつも同じ結果**になる | 同じ入力でも**結果が毎回ゆれる**（AIが読んで解釈するため） |
| 確かめ方 | テストを1回流して合否を見る | **同じことを何回も試して、うまくいった割合を見る** |
| 判定 | 通った / 通らなかった | 例：10回試して9回以上うまくいけば合格 |

**日本語の手順書を1回試してうまくいっても、それは「うまくいくことがある」だけの証明です。** だから複数回試して割合で見ます。

### プログラム開発（P開発承認ゲート型）と違うところ

| 項目 | どう変わるか |
| :--- | :--- |
| 書類の名前 | **変わりません**（SW105 / SWP6 / SW205 のまま）。番号の付け方（REQ / TC / UNIT）も同じです |
| 使う下書きの型 | `docs/templates/agent/` の3ファイルに**自動で切り替わります**。あなたが指定する必要はありません |
| 要求の書き方 | 1件ごとに「日本語担当かプログラム担当か」が付きます。日本語担当の確かめ方は「**必ず入っているべきもの・入っていてはいけないもの・試す回数・合格ライン**」の形で書きます |
| テストの書き方 | プログラム担当は単体テスト、日本語担当は採点表（`EV-001` のような番号を付けます） |
| 設計書 | 道具の使い方の説明（コマンドの打ち方、渡す情報、返ってくる合否の数字、使用例）と、間違い防止の工夫の一覧が加わります |
| 見直しの観点 | コードの正しさではなく、**手順書と道具の言っていることが食い違っていないか**が主な対象になります |
| 実装 | コードではなく、`.agents/skills/名前/SKILL.md` などのファイル一式を作り、採点表を何回も試して合格割合を出します |

### できあがるもの（実装の段階）

| 担当 | できあがるもの |
| :--- | :--- |
| 日本語で書く部分 | `.agents/skills/名前/SKILL.md`（先頭に「名前」と「いつ使うか」の設定を付けます）、`AGENTS.md`、`references/` の中の参考資料やひな形 |
| プログラムで書く部分 | `tools/名前.py` などの道具・点検ツール |
| 記録 | `docs/process/eval_report.md`（何回試して何回うまくいったか、の記録）<br>SWP6の5〜6章（総合テスト報告書。**あなたは報告書を承認する**） |

> [!IMPORTANT]
> **手順書を日本語で書けるからといって、工程が省かれることはありません。** 確認の関門、テストを先に作ること、AIによる見直しは、プログラム開発とまったく同じように行われます（`.agents/AGENTS.md` 第9節）。切り替わるのは「下書きの型」と「確かめ方」だけです。

## A開発自律型 AIの相棒を一気に完成まで作る

**こんなときに使います**：AIエージェント一式を早く形にして、実際に動かしながら要求を足していきたいとき。

### コピー用の指示文

```text
DADAプロセス自律型を開始します。
・開発対象：エージェント定義（データ分析自動化エージェント一式）
・要求概要：[エージェントの要求]
・自律実行指示：docs/guidelines/agent_design_principles.md に従い、二重構造（自然言語/プログラム言語）の設計および自己校正を実施してください。機械的チェックおよび評価セットの検証がクリアされたら、人間に停止を求めずPhase 4のファイル生成（.agents/skills/配下のSKILL.mdおよび関連スクリプト一式）まで一気に自律完走してください。
```

### 上の指示文を、やさしい言葉で書いた版（意味は同じです）

```text
DADAプロセスで開発を始めてください。完成するまで、私の確認を待たずに進めてください。

・作るもの：AIの相棒（データ分析を自動でやってくれるAI一式）
・やりたいこと：[作りたいものを、ふつうの日本語で書く]

作り方は docs/guidelines/agent_design_principles.md に従ってください。
「日本語で書く手順書」と「プログラムで書く道具」に役割を分けて設計し、各段階でAI自身の見直しを行ってください。
点検ツールの自動点検と、振る舞いの採点がどちらも基準を満たしたら、私を待たずに次へ進んでください。
ファイル一式（.agents/skills/ の中のSKILL.mdと、関連するプログラム）ができあがるところまで進めてください。
```

### A開発自律型 だけの追加条件

P開発自律型 の6条件に加えて、次が必要になります。**振る舞いがゆれるものを、確かめずに通さないための条件です。**

| いつ | 条件 |
| :--- | :--- |
| テスト仕様の段階の終わり | 採点する項目すべてに番号（`EV-001` の形）が付き、**試す回数と合格ラインが数字で書かれている** |
| 実装の段階の終わり | `docs/process/eval_report.md` の全項目が合格ラインを満たしている。**試した回数が1回だけの記録は不合格として扱います** |
| 実装の段階の終わり | SWP6の5〜6章が記入され、`python tools/dada_check.py report` が終了コード 0 を返す |
| 実装の段階の終わり | `python tools/agent_def_check.py` が合格（終了コード 0）を返す ＝ 参照先ファイルのリンク切れ、手順書に書いたコマンドと実物のズレ、番号の書き漏れがない |

### できあがったあと、あなたがやること（外側の繰り返し）

1. できたAIの相棒を、実際に動かして使ってみる
2. `docs/process/eval_report.md`（採点の記録）と `docs/process/autoloop_log.md`（判断の記録）を見て、どう確かめられたのかを把握する
3. 足りないところを新しい要求として伝え、DADAプロセスをもう一度動かす（最初の段階に戻ります）

この 1→2→3→1→… の繰り返しが「開発Loop（外側の繰り返し）」です。

## 迷ったときの選び方

| こんなとき | おすすめ |
| :--- | :--- |
| 初めてDADAプロセスを使う | **P開発承認ゲート型**。確認の関門がどう動くかを体感してから、自律型へ移るのが安全です |
| 作りたいものが、まだ自分でも固まっていない | **承認ゲート型**（P開発承認ゲート型 / A開発承認ゲート型）。ぼんやりした要求で自律型を使うと、AIが途中で止まるか、誤った思い込みのまま完成してしまいます |
| 人の命・お金・法律に関わる | **承認ゲート型**（`.agents/AGENTS.md` 第10.7節に定めた適用の限界） |
| 高い品質が必要（他でも使い回す、極限まで速くする、認証を取る） | **承認ゲート型** |
| とにかく早く動くものを見て、そこから直したい | **自律型**（P開発自律型 / A開発自律型） |
| 作るものが「AIへの手順書」である | **エージェント定義**（A開発承認ゲート型 / A開発自律型） |

## よくある質問

**Q. 途中で進め方（承認ゲート型 / 自律型）を変えられますか。**
変えられます。「ここから先は承認ゲート型にして、区切りごとに確認を取ってください」と伝えれば切り替わります。逆（承認ゲート型→自律型）も同じです。これは **P開発承認ゲート型 / A開発承認ゲート型** の話です。**サブエージェントをだれが作るか**（開いているエージェント開発/実行ツールの違い）とは別です。

**Q. 「人間がサブエージェントを作る」と A開発承認ゲート型の「A」は同じですか。**
違います。**A開発承認ゲート型の A は Agent**（AIの相棒を作る）です。**動作モードは、開いているエージェント開発/実行ツールがサブエージェントを自動で作れるかどうか**です。Antigravity 2.0 ならツールが自動的にサブエージェントを作ります（推奨）。IDE だけで動くときは人間がサブエージェントを作ります。チャットで指定する必要はなく、開いたエージェント開発/実行ツールで自動的に決まります。人間が作る場合の承認ゲート型では工程の切れ目で新しいチャット（サブエージェント）を開き、P開発自律型 / A開発自律型では同一会話の論理リセットになります。

**Q. 自律型にしたのに、AIが止まってしまいました。**
故障ではありません。上の「[必ず止まる場面](#必ず止まる場面)」に当てはまったとき、AIは**わざと**止まります。理由と選べる道が示されるので、どうするか答えてください。`docs/process/autoloop_log.md` の該当する行にも、止まった理由が記録されています。

**Q. 今までどおりの短い指示でも使えますか。**
使えます。作るものと進め方を書かなければ、**プログラム × 承認ゲート型**として、今までとまったく同じように動きます。

**Q. AIの相棒を作るときは、確認の関門やテストが省かれるのですか。**
省かれません。「日本語だから書くのが楽だ」という理由で工程を飛ばすことは、ルールで禁止されています（`.agents/AGENTS.md` 第9節）。

**Q. 「試す回数」は何回にすればよいですか。**
判断のゆれが小さい作業なら5回程度、ゆれが大きい作業や重要な作業なら10回以上が目安です。**1回はダメです**（1回うまくいっても、それは偶然かもしれません）。決め方の考え方は `docs/guidelines/agent_design_principles.md` の第4章にあります。

**Q. 要求概要は、どのくらい詳しく書けばよいですか。**
最初はふつうの日本語で、箇条書き数行でかまいません。**承認ゲート型なら、足りない部分はAIが質問してきます。** 自律型の場合は、あとから聞き返す機会が少ないため、できるだけ具体的に書いてください（特に「これは絶対に必要」「これはやらなくてよい」の線引き）。
