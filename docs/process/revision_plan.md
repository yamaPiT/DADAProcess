## 1. 出口（受入基準）の確定

本改訂の完了判定は「以下4つの使い方のプロンプトを入力したとき、DADAプロセスが合目的的かつ完全に動作すること」とする。プロンプト全文は `docs/examples/prompts_usage.md` に収録する。

> **ラベル**: **P** = Program（プログラム）、**A** = Agent（エージェント定義）。P対話 / P自律 / A対話 / A自律。PDFの分類番号は「PDF該当」列に残す。

| パターン | 開発対象 | 実行モード | PDF該当 | 人間の関与 |
| :--- | :--- | :--- | :--- | :--- |
| **P対話** | 従来型プログラム | 対話型（承認ゲートあり） | 4-1 | 各Phase末で承認 |
| **P自律** | 従来型プログラム | 自律メタLoop（一気完走） | 5-1 | 最終成果物のみ評価 |
| **A対話** | エージェント定義 | 対話型（承認ゲートあり） | 4-2 | 各Phase末で承認 |
| **A自律** | エージェント定義 | 自律メタLoop（一気完走） | 5-2 | 最終成果物のみ評価 |

**現状の到達度**: P対話のみ完全動作する。P自律は「自律遷移の承認条件」が未定義のため動作しない（`.agents/AGENTS.md` の承認ゲートが人間の明示的肯定を必須としているため、自律遷移は現状ではプロセス違反になる）。A対話・A自律は「エージェント定義」を開発対象とする際の文書構造・評価方法・レイヤー分担が未定義のため動作しない。

## 4. 設計方針（思考過程）と、後方互換を守るための制約

### 方針1: 4パターンを「2軸の直交ルーティング」として実装する
開発対象（program / agent）と実行モード（interactive / autoloop）を独立した2つの判定に分解する。4パターン分の分岐を個別に書くと組み合わせ爆発でスキルが肥大化し、軽量モデルが参照解決に失敗する。2軸に直交化すれば、追記量は「対象の分岐」＋「モードの分岐」の和で済む。

**既定値を `program × interactive` とする。** 判定不能な場合も既定値へ落とす。したがって、開発対象・実行モードを明示しない既存の起動プロンプト（`DADAプロセスで開発を開始してください。…`）は、改訂後も**現在と1文字も違わない挙動**になる。

### 方針2: 文書IDとID体系を変更しない（後方互換の要）
エージェント定義開発でも成果文書は `SW105` / `SWP6` / `SW205` のままとし、`REQ-001` / `TC-001` / `UNIT-001` のID形式を維持する。

- **理由**: `tools/dada_check.py` は `DOC_SPECS`（SW105/SWP6/SW205）と `ID_RE`（REQ/TC/UNIT）を前提に全チェックを構成している。新IDを導入すると機械チェックが機能しなくなり、A自律（自律完走）の根拠となる合否判定が失われる。
- **当初の帰結**: `tools/dada_check.py` は1行も変更しない。
- **【計画からの逸脱・実装時に修正】** 検証の結果、この方針のままでは**A自律（エージェント定義×自律完走）が成立しない**ことが判明したため、`dada_check.py` に1箇所だけ追加変更を行った。詳細は下記「方針2-2」を参照。

### 方針2-2: `dada_check.py` のコード照合に「宣言パス照合」を追加（計画からの逸脱）

**検出した問題**: `dada_check.py` の `code` チェックは、UNIT-IDの実装確認をソースツリーの走査で行う。しかし走査対象は `SOURCE_EXTS`（`.py` `.ts` `.c` 等。`.md` は含まない）に限られ、`SOURCE_EXCLUDE_DIRS` は `.agents` と `tools` と `docs` を除外している。エージェント定義の成果物は `.agents/skills/*/SKILL.md` と `tools/*.py` であるため、**全ユニットが「未実装」と判定され、終了コードが恒久的に 1 になる**。自律遷移の条件2（終了コード 0）を永久に満たせず、A自律 が完走不能だった。

**採った対応**: SW205のUNITブロックに `- **成果物パス**:` が記述されている場合のみ、ソースツリー走査ではなく**宣言されたパスを直接照合**する分岐を追加した（そのパスにファイルが実在し、UNIT-IDが記載されているかを検証する）。

**なぜ後方互換が保たれるか**:

- 従来型プログラム開発のSW205スケルトン（`.agents/skills/architect/references/SW205_skeleton.md`）には `成果物パス` の欄が存在しない。したがって分岐は起動せず、照合経路は従来のソースツリー走査のままである。
- 回帰テスト（`scratch/regress.py`）で、従来型プログラムの成果物セットに対する出力と終了コードが改訂前と**完全一致**することを確認済み。
- **緩和ではない**: 宣言パスにファイルがない場合、UNIT-IDの記載がない場合はいずれも High として検出する（回帰テストのケース3で実証済み）。検証の強度は下がっていない。

**副作用として明文化した制約**: プログラムレイヤーのテストコードは `tools/` ではなく `tests/` 配下に置く必要がある（`tools/` は走査除外のため、そこに置いた「自動」区分のテストは検出されない）。この制約は `docs/templates/agent/phase3_agent_design_template.md`・`.agents/skills/programmer/SKILL.md`・`.agents/skills/dada-check/SKILL.md`・`tools/README.md` に記載した。
- エージェント用ひな形は `docs/templates/agent/` に置き、既存の「テンプレート指定時は `docs/templates/` を優先する」メカニズム（`.agents/AGENTS.md` 第7節）にそのまま乗せる。章構成の差異は `dada_check.py` が既に「要確認（テンプレート指定時は無視してよい）」として扱うため、誤検出も起きない。

### 方針3: 機械チェックが読むフィールド名・列名を一字一句変えない（ポカヨケ）
エージェント用ひな形は、以下のラベルを既存スケルトンと同一表記で維持する。ここを言い換えると機械チェックが黙って通ってしまい、最も危険な「検証したつもり」を生む。

| 文書 | 固定するラベル |
| :--- | :--- |
| SW105 | `#### REQ-001:` 形式の見出し、`- **概要**:` `- **入力 / 処理 / 出力**:` `- **異常系**:` `- **検証条件 (Acceptance Criteria)**:` `- **優先度**:` |
| SWP6 | テスト項目表の列 `テストID` / `対象要件` / `シナリオ` / `前提条件` / `入力データ` / `期待される出力` / `実行区分` |
| SW205 | `#### UNIT-001:` 形式の見出し、`- **責務**:` `- **対応要求**:` `- **公開インターフェース**:` `- **依存先**:` `- **検証条件**:` |

**二重構造の表現は、新IDではなく属性の追加で行う。** 各REQ/UNITブロックに `- **レイヤー**: 自然言語 / プログラム` の1行を足すだけとする。

### 方針4: 評価の二重化は「実行区分」の第3値で表現する
SWP6のテスト項目表の `実行区分` に、既存の「自動」「手動」へ**「評価」**を追加する。

| 実行区分 | 対象レイヤー | 検証方法 | 合否 | `dada_check.py` の扱い |
| :--- | :--- | :--- | :--- | :--- |
| 自動 | プログラムレイヤー | 単体テスト・スクリプト | 決定論的 Pass/Fail | TC-IDを参照するテストコードの存在を照合（既存挙動） |
| 評価 | 自然言語レイヤー | Eval Dataset（N回試行＋ルーブリック判定） | 合格率が閾値以上 | 文字列「自動」に一致しないためコード照合の対象外（**既存コードを変えずに共存できる**） |
| 手動 | 両方 | 人間の目視・実機確認 | 人間の判断 | 対象外（既存挙動） |

「評価」区分の証跡は機械チェックで担保できないため、代わりに `docs/process/eval_report.md`（評価実行結果）への記録を必須とし、自律遷移の条件に組み込む。

### 方針5: 自律メタLoopの承認は「委譲の明示＋機械的合格」の論理積とする
`.agents/AGENTS.md` の「承認の定義」（人間の明示的肯定のみが承認）は不変条件であり、緩めない。代わりに**「Product Ownerが起動時に自律実行を明示的に指示した行為そのものを、Phase 2〜4の承認の事前委譲とみなす」**という条項を追加する。これは承認の推定ではなく、委譲の明示である。

自動遷移は、以下の**すべて**を満たすときにのみ許可する（1つでも欠ければ停止して人間に戻す）。

1. Product Ownerが起動時に自律メタLoopモードを明示的に指示している（推定禁止。曖昧なら対話型）
2. `python tools/dada_check.py all` の終了コードが 0（High指摘ゼロ）である
3. 自己校正ループが2周以内に完了し、未解消のHigh指摘がゼロである
4. 当該Phaseの「完了条件」を自己チェックで全項目満たしている
5. エージェント定義開発の場合、Phase 2の評価セットが作成済みで、Phase 4では `eval_report.md` の合格率が閾値以上である
6. 後述の「必須停止条件」に1つも該当しない

**必須停止条件（自律モードでも人間に必ず戻す）**

| # | 条件 | 根拠 |
| :--- | :--- | :--- |
| 1 | テストを書けない要求を検出（Phase 2の差し戻し条件） | 曖昧な要求を推測で埋めることは、自律実行の可否とは無関係に禁止 |
| 2 | 実装中に設計の不備・矛盾を検出（Phase 4の差し戻し条件） | 同上 |
| 3 | 自己校正2周でHigh指摘が未解消 | 既存の「自己校正の回数上限とエスカレーション」 |
| 4 | 機械チェックのHigh指摘が2回連続で解消できない | 無限修正ループの防止 |
| 5 | 同一テストが5回連続で失敗 | 既存のループ上限 |
| 6 | スケール／開発対象／実行モードの判定が不能 | 安全側（Major・対話型）へ落として確認 |
| 7 | 破壊的操作・外部課金・秘密情報の取り扱いが必要 | グローバルルールの安全第一 |
| 8 | スコープ外の新規要求が必要と判断 | 要求追加はメタLoop（人間）の役割 |
| 9 | ループバックが同一Phaseで2回発生 | 発散の防止 |

**記録義務（Transparency）**: 自律ゲートを通過するたびに `docs/process/autoloop_log.md` へ1行追記する（Phase／判定時刻／機械チェック要約行／自己校正結果／判定 PROCEED か HALT／根拠）。人間は完走後にこのログだけで全判断を追跡できる。

### 方針6: 自律モードのアテンション・リセットに「方式C」を追加する
現行 `context-reset` は方式A（サブエージェント委譲）と方式B（人間に新チャットを依頼）の2つしかなく、**方式Bの環境で自律モードを指定すると人間の操作待ちで必ず止まる**。そこで方式Cを追加する。

- **方式C（自律連続実行）**: サマリーを書き出したうえで、同一会話内で「チャット履歴中の未確定の議論を情報源から除外する」宣言を行い、次Phaseのペルソナスキルを召喚する。参照してよいのは承認済みドキュメントと `last_phase_summary.md` のみ（物理的リセットではなく論理的リセットである旨を明記し、限界も書く）。
- 選択順序: サブエージェントが使えるなら方式A（最も汚染に強い）→ 使えず自律モードなら方式C → 対話モードなら方式B。

### 方針7: 既存ファイルへの追記は「分岐ブロック」の形に閉じ込める
ペルソナスキルの改訂は、既存手順の書き換えではなく、以下の形の**独立したブロックの追記**に限定する。これによりP対話の実行経路は既存の文言をそのまま通る。

```markdown
## X. 開発対象が「エージェント定義」の場合の追加手順（対象が従来型プログラムの場合は本節を読み飛ばす）
```

## 9. 平易化の対応（Product Ownerの指示）

「READMEの記述を平易にする。特にプロンプトサンプルでは、難しい横文字をなるべく使わない、あるいは説明を追加する」という指示に基づき、以下を実施した。**利用者向け文書のみを対象とし、AIが読むスキル・ルール類の用語は変更していない**（機械チェックが参照するラベルや、`AGENTS.md` の節番号との対応が崩れるため）。

### 対象と方針

| 対象 | 方針 |
| :--- | :--- |
| `docs/examples/prompts_usage.md` | 全面的に書き直した。専門用語を使う場合は必ず直後に平易な説明を添える |
| `docs/examples/README.md` | 使い方の手順を平易化し、言い換え表への案内を追加 |
| `README.md` の「4つの使い方」節ほか | 「開発対象／実行モード」という抽象語をやめ、「何を作るか／どう進めるか」の2つの質問に置き換えた |
| スキル・ルール類（`.agents/`） | **変更しない**。AIが読む文書であり、用語の統一が機械チェックの前提になっている |

### プロンプト集に追加した平易化の仕組み

1. **2つの質問から入る導線**: 「開発対象」「実行モード」という言葉を知らなくても選べるよう、「何を作りますか？」「どう進めますか？」の2問に答える形式を冒頭に置いた。
2. **公式版とやさしい言い換え版の併記**: 受入基準である指示文はそのまま残し（意味を変えないため）、その下に同じ意味を平易な日本語で書いた版を併記した。利用者はどちらを使ってもよい。
3. **指示文の各行の意味の表**: パターンごとに、指示文に出てくる言葉（`自己校正` `承認ゲート` `APPROVED` 等）を1語ずつ表で説明した。
4. **用語のやさしい言い換え表（付録）**: 44語を「進め方」「作るもの」「確かめ方」「書類の名前」の4分類で一覧にした。
5. **概念の言い換え**: 主要な言葉に、意味が伝わる日常語を添えた。

| 元の言葉 | 添えた言い換え |
| :--- | :--- |
| エージェント定義 | AIの相棒／AIに「こう動いてね」と教える説明書一式 |
| 自然言語レイヤー | 日本語で書く部分（状況を見て判断する仕事を担当） |
| プログラム言語レイヤー | プログラムで書く部分（答えが1つに決まる処理を担当） |
| 自律メタLoop | 外側の繰り返し（できたものを見て要求を足す大きな繰り返し）を人が回すこと |
| Eval Dataset | 評価セット／AIの振る舞いを採点する問題集 |
| 確率的な振る舞い | 同じ入力でも結果が毎回ゆれること |
| 終了コード | プログラムが返す合否の数字（0が合格） |
| 死リンク | 参照先のファイルが存在しない状態 |
| 閾値 | 合格とみなす最低ライン |

### 副次的に修正した既存の不具合

平易化の検証中に、`README.md` の見出しリンク1件が切れていることを発見し修正した（見出しの絵文字によりアンカーの先頭に余分なハイフンが入っていた）。今回の改訂で作り込んだものではなく、以前から存在した不具合である。
