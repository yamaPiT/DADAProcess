# エージェント定義 設計原則 (Agent Design Principles)

## 0. 位置づけとロードタイミング
- **適用条件**: Phase 0で開発対象が「エージェント定義」と判定された場合のみ（`requirements-engineer` / `test-engineer` / `architect` / `programmer` / 各レビュアーが、`docs/guidelines/agent_def_phase_addon.md` と併せて参照する）。
- **従来型プログラム開発では本ファイルをロードしない**。
- 本ガイドラインはASDoQ品質モデル（`docs/guidelines/asdoq_writing_rules.md`）を置き換えるものではなく、エージェント定義固有の「何を書くか」を追加する。

## 1. 開発対象の二系統

| 観点 | 従来型プログラム | エージェント定義 |
| :--- | :--- | :--- |
| 記述言語・要素 | プログラム言語（アルゴリズム＋データ構造） | 自然言語（スキル・ルール・知識）＋プログラム（ツール） |
| 振る舞い | 決定的（同一入力で同一結果） | 確率的・文脈依存（同一指示でも結果が揺れる） |
| 正しさの保証 | 単体テスト・型・形式検証 | Eval Dataset（複数回試行）＋単体テスト＋一貫性検査 |
| 主な失敗・レビュー対象 | コードの論理誤り・例外 | 幻覚・逸脱・指示漏れ、スキル・ツール間の一貫性 |

**導かれる3帰結**: (1) 確率的振る舞いには複数回試行の評価セットと許容範囲が必要、(2) 決定論的処理はプログラムレイヤーへ分離すべき、(3) 書きやすくても工程・承認ゲート・ID体系（`REQ`/`TC`/`UNIT`）・機械チェックは省略しない。

## 2. 三原則と5つの設計パターン

出典: Anthropic「Building Effective Agents」 https://www.anthropic.com/research/building-effective-agents

本節は**これから開発する対象エージェント**に適用する。DADA自身の実装例を理由に対象への適用を省略してはならない。

### 2.0 必守と参考の区別
- **三原則（Simplicity / Transparency / ACI）**: **必ず守る**。要求（SW105 2.4節）に方針を書き、設計（SW205）で全ユニットへ落とす。
- **5つの設計パターン**: **吟味は必須、採用は任意**。5つすべてについて採用／不採用と理由をSW105（2.5節）とSW205（3.1節）に書く（空欄禁止）。効かないパターンを無理に採用しない。

### 2.1 三原則（必守）

| 原則 | 対象エージェントへの適用 |
| :--- | :--- |
| **Simplicity**（単純さ） | 1スキルに複数役割を詰め込まず、役割ごとに分ける。執筆役（Generator）と評価役（Evaluator）、調整役（Orchestrator）は別スキルにする。発動条件が1文で言い切れない場合は分割する |
| **Transparency**（透明性） | 全自然言語スキルの `SKILL.md` に「思考過程（現在地・判断の根拠・次の一手）を出力する」と明記し、ログや報告書を外在化する。無言の判断遷移を禁止する |
| **ACI**（Agent-Computer Interface） | `description`（発動条件）、手順粒度、入出力パス・見出し・報告定型を迷いなく指定する。ツール呼び出しにはコマンド行・引数・標準出力・終了コード・使用例を定義する |

### 2.2 5つの設計パターン（参考・吟味必須）
**自律エージェント（フリーラン探索ループ）は最後の手段**とし、事前確定できる工程はワークフローパターンで実現する。

| # | パターン | 内容と有効な場面 | 採用しない例 |
| :---: | :--- | :--- | :--- |
| 1 | **Prompt Chaining** | 固定順で前段文書を次段入力へ渡す（段ごとの文書化が可能） | 1回変換で足り、分割が遅延だけを生む |
| 2 | **Routing** | `description` や分類判定で入力種別ごとにスキルを振り分ける（重複禁止） | 入力が1種、振分先が1スキルのみ |
| 3 | **Parallelization** | 独立部分作業の同時実行やN回試行による信頼度確保 | 後段が前段に直列依存する |
| 4 | **Orchestrator-Workers** | 調整役が進行・上限を管理し、ワーカーへ固定入力のみ渡す（履歴要約は渡さない） | 1本道で単一スキルのみ |
| 5 | **Evaluator-Optimizer** | 執筆役と評価役を別スキルにし、明確な基準＋ループ上限で反復改善する | 評価基準が書けない、人間が毎回評価する |

### 2.3 要求定義（Phase 1）での吟味手順（省略禁止）
1. 対象が担う役割を列挙する（ファイル名決めではなく役割定義）。
2. 第2.5節の5問で **Simplicity**（役割分割）を判断し、分割しない場合も分割案と不採用理由をSW105 2.3節に書く。
3. 各自然言語スキルへの **Transparency**（思考過程出力）と **ACI**（発動条件・粒度・出力形式）をSW105 2.4節へ要求化する。
4. 第2.2節の5パターンすべてを1つずつ問い、採用／不採用と理由をSW105 2.5節へ書く。

### 2.4 設計（Phase 3）での吟味手順（省略禁止）
1. 1役割＝1スキル＝1UNIT を原則にユニット化する（統合する場合はADRに理由を残す）。
2. SW105 2.5節の5パターンをSW205 3.1節へ転記し、採否を確定する。
3. **Evaluator-Optimizer** 採用時は Generator と Evaluator を別UNITにし、評価基準は Evaluator のみが持つ。
4. **Orchestrator** 採用時はループ管理と上限・打切先を Orchestrator（4.2節）に集約する。
5. 各自然言語UNITの公開IFに「思考過程の出力」と「出力形式」を含め、`description` の非重複を確認する。

### 2.5 役割分割の判断基準（Simplicity）
次の5問に順に答え、1つでも Yes なら別スキル（別UNIT）への分割を検討する（迷ったら分割する）。
1. 成果物を作る役割と評価する役割が分かれるか → Generator / Evaluator 分割。
2. 複数スキルの順番・反復・打ち切りを管理する役割が必要か → Orchestrator 分割。
3. 入力の種類によって使う手順が分かれるか → Routing 用に分割。
4. 独立に進められる部分作業があるか → Parallelization 用に分割。
5. 前の出力を次の入力にする固定順の段があるか → Prompt Chaining で分割。

### 2.6 適用例：議事録作成（Generator / Evaluator / Orchestrator）
会議メモから議事録を作る課題は、抽出・執筆（Generator：評価基準を持たない）、評価・朱入れ（Evaluator：本文を書かない）、ループ上限管理（Orchestrator：執筆も評価もしない）の3役割へ分離すると自己採点バイアスと指示汚染を防げる。

## 3. 二重構造：自然言語レイヤーとプログラムレイヤー

### 3.1 責務分担

| 観点 | 自然言語レイヤー | プログラムレイヤー |
| :--- | :--- | :--- |
| 実体 | `AGENTS.md`、`skills/<name>/SKILL.md`、`references/` | `tools/*.py`、前処理・後処理、構文チェッカー |
| 得意な仕事 | 文脈解釈、意思決定、工程制御、反証レビュー | 厳密変換、網羅照合、計数、決定論的検証、入出力 |
| 検証方法 | Eval Dataset（N回試行・合格率） | 単体テスト（決定論的 Pass/Fail） |

### 3.2 振り分け判定フロー（3問に順に答える）
1. **出力が入力から一意に決まるか** → Yes ならプログラムレイヤー。
2. **取りこぼしが許されない網羅的な照合・集計か** → Yes ならプログラムレイヤー。
3. **文脈や意図の解釈が必要か** → Yes なら自然言語レイヤー。
3問すべて No の場合は安全側の**プログラムレイヤー**を選ぶ。

### 3.3 レイヤー間の契約（一貫性5項目・不変条件）
1. **単一情報源**: 同一知識を2箇所に別内容で持たず、正本を明記する。
2. **定数の二重定義禁止**: 閾値・パス・ID書式は一方に定義し、併記時は相互同期コメントを置く。
3. **手順とツール引数の一致**: `SKILL.md` のコマンド行はスクリプトの引数と一字一句一致させる。
4. **参照パスの実在**: 参照パスはすべて実在させる。
5. **終了コードの意味一致**: `0`（合格）/ `1`（指摘あり・未達）/ `2`（実行エラー）を手順分岐と一致させる。

## 4. 評価基準の二重化（Eval Dataset と単体テスト）

### 4.1 二重化の原則
確率的振る舞いは1回の成功では証明できない。プログラムは「**自動**」（単体テスト）、自然言語は「**評価**」（Eval Dataset のN回試行）、AIがツール操作で確認する項目は「**手動**」（実施者はAI）へ区分する。

### 4.2 単体テスト仕様（プログラムレイヤー）
`TC-001` 形式で前提条件・入力・期待出力を具体値で定義し、`tests/` 配下のテストコードに対応 `TC-ID` コメントを明記する。

### 4.3 自然言語レイヤーの評価セット（Eval Dataset）
各 `EV-ID` は次の5欄を機械的・再現可能に記述する。
- **入力プロンプト**: 実際に投入する全文（要約・省略禁止）。
- **必須要素**: 出力に必ず含まれる見出し・項目・ID・書式。
- **禁止要素**: 現れてはならない幻覚・役割逸脱・禁止表現。
- **判定方法**: **決定論的アサーション**（正規表現・コマンドログ）→ **ルーブリック採点**（観点別0/1、全観点1点で合格）→ **LLM-as-judge**（評価対象と採点者を別会話に分離）の優先順で選ぶ。
- **合格基準**: 試行回数と合格率閾値を数値で指定する。

### 4.4 許容範囲（試行回数と合格率）

| 要求の重要度 | 試行回数目安 | 合格率閾値目安 |
| :--- | :--- | :--- |
| Must | 10回以上 | 90%以上 |
| Should | 5回以上 | 80%以上 |
| Could | 3回以上 | 60%以上 |

- **1回試行の禁止**。閾値未達時に評価セット・必須要素・閾値を緩めて合格させることは禁止（指示具体化・決定論化・PO再合意で対処）。結果は `docs/process/eval_report.md` へ記録する。

## 5. ポカヨケ設計基準（Mistake-Proofing）

| # | 基準 | 実装方法 |
| :---: | :--- | :--- |
| 1 | **思考過程の強制** | `SKILL.md` に開始・完了時の思考過程3項目と進行表示の出力を明記する |
| 2 | **ルート固定パス** | 入出力ファイルパスを手順内に literal で固定し探索させない |
| 3 | **二重出力の禁止** | 成果物全文はファイルにのみ書き、チャットはパスと要約行のみ返す |
| 4 | **statusコード制御** | CLI終了コード（0/1/2）を受け取り分岐する |
| 5 | **ラベルの固定** | 機械チェック対象の見出し・フィールド名・列名を一字一句固定する |
| 6 | **ループ上限とエスカレーション** | 反復処理に上限回数と打切後の報告先を明記する |
| 7 | **禁止事項の明示** | 「やってはならないこと」を独立節に列挙する（検証改ざん禁止等） |
| 8 | **完了条件のチェックリスト化** | 完了報告前に保存済みファイルを読み直すチェックリストを置く |

## 6. エージェント定義の標準ファイル構成と frontmatter 規約
- 標準配置: `.agents/AGENTS.md`（不変条件のみ）、`.agents/skills/<skill-name>/SKILL.md`・`references/`、`tools/<tool-name>.py`、`tests/test_<tool-name>.py`、`docs/guidelines/`、`docs/templates/`。
- `SKILL.md` 先頭の frontmatter には `name`（ディレクトリ名と一致、英字始まり英数字とハイフン）と `description`（「いつ使うか」を先頭に書き、他スキルと重複させない）を必須とする。

## 7. アンチパターン
1スキルへの複数役割詰め込み（特に執筆と評価の同居）、分割吟味の省略、思考過程未記載、粗い `description`・出力形式、5パターンの無吟味／無理な全採用、網羅照合の自然言語丸投げ、他スキルへの「同一」丸投げ参照、1回試行での合格判定、会話履歴要約のワーカー渡し、検証側の改ざん、上限なしループを禁止する。
