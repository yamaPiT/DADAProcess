# エージェント定義 設計原則 (Agent Design Principles)

## 0. 本ガイドラインの位置づけとロードタイミング

| 項目 | 内容 |
| :--- | :--- |
| **適用条件** | Phase 0の判定で**開発対象が「エージェント定義」**となった場合のみ |
| **ロードするスキル** | `requirements-engineer` / `test-engineer` / `architect` / `programmer` および対応する4つのレビュアースキル |
| **併用するひな形** | `docs/templates/agent/` 配下の3ファイル（Phase 1/2/3に対応） |
| **開発対象が従来型プログラムの場合** | 本ガイドラインはロードしない（従来の `dada_document_guidelines.md` と `asdoq_writing_rules.md` のみを使う） |

本ガイドラインは**ASDoQ品質モデルを置き換えるものではない**。エージェント定義の開発文書も、従来型プログラムと同じく `asdoq_writing_rules.md`（執筆ルール12箇条）に従って書く。本ガイドラインが追加するのは「何を書くか」の観点であり、「どう書くか」の規則は変更しない。

## 1. 開発対象の二系統

AI時代の開発対象は2系統に分かれる。両者は同じ「コンピュータプログラム」でありながら、正しさの保証方法が根本的に異なる。

| 観点 | 従来型プログラム | エージェント定義 |
| :--- | :--- | :--- |
| 記述言語 | プログラム言語 | 自然言語（＋従来型プログラム） |
| 実行の仕組み | コンパイラ・インタプリタが命令を逐次実行する | AIが意図と文脈を解釈して行動する |
| 構成要素 | アルゴリズム＋データ構造＋制御フロー | スキル・ルール・知識＋従来型プログラム |
| 振る舞い | 決定的（同じ入力なら同じ結果） | 確率的・文脈依存（同じ指示でも結果が揺れる） |
| 変更の仕方 | ソースを直して再ビルドする | 指示・知識・ルールを書き換える（再ビルド不要） |
| 正しさの保証 | テスト・型・形式検証が確立している | 評価が難しく、幻覚・逸脱・指示漏れが起きる |
| 主なレビュー対象 | コードの正しさ | スキル・ルール・知識の**一貫性** |

**この違いから導かれる3つの帰結**（本ガイドラインの全体構造は、この3点への対応で決まっている）。

1. 振る舞いが確率的であるため、合否を1回のPass/Failで判定できない。**評価セットと許容範囲**が必要になる（第4章）。
2. 自然言語は解釈の幅を持つため、決定論的な処理を自然言語に書くと品質が揺れる。**レイヤーの責務分担**が必要になる（第3章）。
3. 書きやすさゆえに工程を省略したくなるが、省略すれば品質は下がる。**工程は省略せず、ひな形だけを対象に合わせて差し替える**（DADAプロセスの構造は変えない）。

> エージェント定義の開発でも、Phase 1〜5の工程・承認ゲート・ID体系（`REQ` / `TC` / `UNIT`）・機械チェックは一切省略しない。

## 2. 三原則と5つの設計パターン

出典: Anthropic「Building Effective Agents」 https://www.anthropic.com/research/building-effective-agents

本節は、**これから開発する対象エージェント**に適用する。DADAプロセス自身が同じ原則で組んであることは参考例であり、対象エージェントへの適用を省略する理由にはならない。

### 2.0 必守と参考の区別（取り違え禁止）

| 対象 | 厳格さ | 文書への残し方 |
| :--- | :--- | :--- |
| **三原則**（Simplicity / Transparency / ACI） | **必ず守る** | 要求定義（SW105）に適用方針を書く。設計（SW205）で各ユニットに落とす。省略はプロセス違反 |
| **5つの設計パターン** | **守らなくてもよい**（設計の参考） | **吟味は必須、採用は任意**。5つすべてについて採用／不採用と理由をSW105とSW205に書く。採用しない行を空欄のまま残すことを禁止する |

SW105ひな形の `### 2.3`（役割分割）・`### 2.4`（三原則）・`### 2.5`（設計パターンの吟味）は、本ガイドライン第2章を要求文書へ落とす先である。**節番号は本ガイドラインと一致しない**（本ガイドラインの第2.3節は「要求定義での吟味手順」、SW105の2.3節は「役割分割方針」）。参照するときは「ガイドライン第2.x節」と「SW105の2.x節」を区別すること。

- パターンを全部使う必要はない。効かないパターンは不採用とし、理由を1文で書く。
- パターンを吟味せずに「とりあえず1スキル」で書き始めることを禁止する。
- 簡単な課題では分割しなくてもよい。分割しない場合も、**分割案を一度検討し、採用しなかった理由**をSW105に書く。迷ったら分割する（単純なスキルの方が性能が高いことが多い）。

### 2.1 三原則（必ず守る）

| 原則 | 対象エージェントへの適用（必守） | DADAプロセス自身での具体化（参考） |
| :--- | :--- | :--- |
| **Simplicity**（単純さ） | **1つのスキルに多くを詰め込まず、役割ごとにスキルを分ける。** 成果物を書く役割と、その成果物を評価する役割は同一スキルにしない。調整（ループの管理）が必要なら、それも別スキルにする。1スキルの発動条件が1文で言い切れない、または「〜と〜を行う」と役割が並ぶ場合は分割する | 新しい文書ID・新しいID体系を作らない。`SW105` / `SWP6` / `SW205` と `REQ` / `TC` / `UNIT` を流用し、ひな形と属性だけを差し替える。各スキルは1ファイルで完結させる（他スキルへの間接参照を作らない） |
| **Transparency**（透明性） | 対象エージェントの **`SKILL.md` に「思考過程を必ず出力する」と明示する。** 現在地・判断の根拠・次の一手を、人間が後から追跡できる形で出させる。判断を無言で進める設計は禁止する | Phase 0の3判定を起動時に宣言する。全応答の末尾に進行表示を出す。自律遷移は `docs/process/autoloop_log.md`、機械チェックは `docs/process/check_report.md`、評価は `docs/process/eval_report.md` に残す |
| **ACI**（Agent-Computer Interface） | **description（いつ使うか）と手順・出力形式を丁寧に書き、エージェントが迷わない指示にする。** 発動条件が曖昧なスキル、手順の抜け、出力物の書式が未定義なスキルは作らない。ツールを使う場合は、加えてコマンド行・引数・標準出力・終了コード・使用例を定義する（第5章のACI仕様） | 設計書（SW205）にツールのACI仕様の章を必須とする。ポカヨケ設計基準（第5章）を全ユニットに適用する |

**三原則の関係**: Simplicity で役割を分け、ACI で各スキルの入口・手順・出口を明確にし、Transparency で実行中の思考を外に出す。どれか1つが欠けると、エージェントは迷うか、人間が追跡できなくなる。

### 2.2 5つの設計パターン（守らなくてもよい。設計の参考）

エージェント定義を要求定義・設計するときは、次の5パターンを**1つずつ吟味する**。採用は任意である。**自律エージェント（フリーランの探索ループ）は最後の手段**とし、手順が事前に決まる要求は Prompt Chaining / Routing / Parallelization / Evaluator-Optimizer で実現する。動的な判断が必要な部分だけ Orchestrator-Workers に寄せる。

| # | パターン | 内容 | 使うと効く場面 | 採用しない例 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | **Prompt Chaining**（プロンプトチェーニング） | 複数のスキルや指示を固定順につなぎ、前の出力（文書）を次の入力にする | 手順が事前に決まる。各段の入出力が文書として残せる | 1回の変換で足り、段を分けると遅くなるだけ |
| 2 | **Routing**（ルーティング） | 入力内容に応じて適切なスキルを選ばせる。**description の書き方が振り分けの鍵**になる | 入力の種類で処理が分かれる。スキルを複数持つ | 入力の種類が1つしかない。振り分け先が1スキル |
| 3 | **Parallelization**（並列化） | 複数のエージェントやサブエージェントを同時に動かし、結果を後でまとめる | 独立な部分作業に分けられる。複数回試行で信頼度を上げたい | 後段が前段の出力に依存する。並列にしても待ちが発生する |
| 4 | **Orchestrator-Workers**（オーケストレーター・ワーカー） | Orchestrator（調整役）が全体の流れを管理し、専門スキルに仕事を振る。人間は Agent Manager として俯瞰・介入できる | 部分課題が動的に決まる。専門性ごとに文脈を分離したい。反復の打ち切りを一箇所で管理したい | 手順が1本で、調整する対象が1スキルしかない |
| 5 | **Evaluator-Optimizer**（エバリュエーター・オプティマイザー） | Generator（執筆役）と Evaluator（評価役）を**別スキル**にし、評価結果を次の生成に活かして改善する | 明確な評価基準があり、反復で品質が上がる | 評価基準が書けない。1回の生成で十分。評価を人間が毎回行う |

**吟味の指針**

- 5つすべてについて、SW105の「設計パターンの吟味」とSW205の3.1節に、**採用／不採用と理由**を書く。理由のない「不採用」も、理由のない「採用」も禁止する。
- **Evaluator-Optimizer** を採用するときは、**Generator と Evaluator を同一スキルにしない**（Simplicity）。ループ上限と打ち切り後の行き先は Orchestrator または手順側に定める。上限のない改善ループは停止しない。
- **Evaluator-Optimizer** と **Orchestrator-Workers** を組み合わせる典型は、調整役が執筆役と評価役のやり取りを回す構成である（第2.6節の議事録例）。
- **Orchestrator-Workers** を採用するときは、**ワーカーへ渡す情報を列挙して固定する**。会話履歴の要約を渡すと文脈が汚染される。
- description が他スキルと重複すると、Routing が壊れる（必要なスキルがロードされない／不要なスキルまでロードされる）。

**DADAプロセス自身での実装例**（対象エージェントへの強制ではない）

| パターン | DADAでの例 |
| :--- | :--- |
| Prompt Chaining | Phase 1→2→3→4→5。各段の出力（開発文書）が次段の唯一の入力 |
| Routing | Phase 0の3判定。既定値へ落とす規則を定める |
| Parallelization | 依存のないユニットの並列実装。評価セットのN回試行 |
| Evaluator-Optimizer | 自己校正ループ（作成者⇄レビュアー、上限2周）＋ `tools/dada_check.py` |
| Orchestrator-Workers | `dada-process` がペルソナスキルへ仕事を振る。ツールが自動的にサブエージェントを作る（推奨） |

### 2.3 要求定義（Phase 1）での吟味手順（省略禁止）

開発対象がエージェント定義のとき、要求定義エンジニアは第3章のレイヤー振り分けに**先立って**、本節を実行する。役割の洗い出しは要求であり、スキルのファイル名を決めること（設計）ではない。

1. **役割を洗い出す**: 対象エージェントが担う役割を列挙する（例: 執筆、評価、調整、検証、振り分け）。「何をするか」を役割名で言い切る。
2. **Simplicity を適用する**: 各役割を別スキルにするか、1スキルにまとめるかを判断する。第2.5節の判断基準に従う。分割しない場合は、分割案と採用しなかった理由をSW105の2.3節に書く。
3. **Transparency を要求にする**: 各スキル（自然言語レイヤー）に「思考過程を出力すること」を機能要求または非機能要求として書く。出力しないスキルを黙って作らない。
4. **ACI を要求にする**: 各スキルについて、発動条件（description に書く内容）、手順の粒度、出力形式（ファイルパス・見出し・報告の定型）を、エージェントが迷わない具体さで書く。
5. **5パターンを1つずつ問う**: 第2.2節の表の「使うと効く場面」に当てはまるかを問い、採用候補と不採用をSW105の2.5節の表に残す。採用は任意。空欄は禁止。
6. **簡単な課題でも一度は分割案を検討する**: 「簡単だから1スキル」で始めない。分割した場合の構成を1案書いたうえで、残すか捨てるかを決める。

### 2.4 設計（Phase 3）での吟味手順（省略禁止）

1. **SW105の役割をユニットに落とす**: 1役割＝1スキル＝1 UNIT を原則とする。SW105で分割しないと決めた役割だけ、1 UNIT にまとめてよい。その場合はADRに理由を残す。
2. **5パターンの採用／不採用を確定する**: SW105の吟味を入力に、SW205の3.1節へ5行とも転記し、設計としての採用を決める。要求で不採用としたパターンを、理由なく設計で採用しない。
3. **Evaluator-Optimizer を採用するならスキルを分ける**: Generator と Evaluator を別UNITにする。評価基準は Evaluator だけが持ち、Generator は持たない（評価と執筆の混在を禁止する）。
4. **Orchestrator を採用するならループを一箇所で管理する**: 上限回数と打ち切り後の行き先を4.2節の表に書く。Generator にループ管理を持たせない。
5. **各自然言語ユニットの公開インターフェースに、思考過程の出力と出力形式を含める**: Transparency と ACI の設計への落とし込みである。欠落は設計漏れである。
6. **description が他スキルと重複しないことを確認する**: Routing の前提。重複は発動事故になる。

### 2.5 役割分割の判断基準（Simplicity）

次の5問に順に答える。1つでも Yes なら、該当する役割を別スキル（別UNIT）にする方向で検討する。すべて No なら 1スキルでよい。いずれの場合も、判断と理由をSW105に書く。

1. **成果物を作る役割と、その成果物を評価する役割が分かれるか** → Yes なら Generator と Evaluator に分割する。
2. **複数スキルの順番・反復・打ち切りを管理する役割が必要か** → Yes なら Orchestrator を分ける。
3. **入力の種類によって使う手順が分かれるか** → Yes なら Routing 用にスキルを分け、description で振り分ける。
4. **独立に進められる部分作業があるか** → Yes なら Parallelization の対象としてスキル（またはサブエージェント）を分ける。
5. **前の出力を次の入力にする固定順の段があるか** → Yes なら Prompt Chaining の段ごとにスキル（または手順の章）を分ける。

**迷ったときの既定**: 分割する。1スキルに役割を詰め込んだ方が「簡単に見える」が、発動条件が濁り、評価基準が執筆に混ざり、性能が下がる。分割のコスト（スキル数の増加）より、役割の純化の方が効くことが多い。

**分割しなくてよい例**: 入力が1種類、成果物が1つ、評価を人間が毎回行い、反復も振り分けもない。このとき「分割案は A／B の2スキルだったが、評価を人間が行うため Evaluator を置かず 1スキルとした」のように理由を書く。

### 2.6 適用例：議事録作成（Generator / Evaluator / Orchestrator）

会議メモから議事録を作る課題は、1スキルに「抽出・執筆・自己採点・やり直し」を詰め込みやすい。三原則の Simplicity に従うと、例えば次の3体に分けられる。

| 役割 | 責務 | 持たせるもの / 持たせないもの |
| :--- | :--- | :--- |
| **Generator**（執筆役） | 会議メモから決定事項とタスクを抽出し、議事録を執筆する。朱入れ文書がある場合は、指摘を踏まえて書き直す | 抽出と執筆の手順。評価基準は持たない |
| **Evaluator**（評価役） | 議事録の評価基準だけを持ち、成果物を評価して改善点を「朱入れ文書」に出力する | 評価基準と朱入れの出力形式。議事録本文は書かない |
| **Orchestrator**（調整役） | 執筆役と評価役のやり取りを管理し、新しい朱入れ（指摘）が入らなくなるまで自律ループを回す | 呼び出し順、ループ上限、打ち切り後の行き先。執筆も評価もしない |

この構成は、5パターンのうち **Evaluator-Optimizer**（執筆と評価の分離）と **Orchestrator-Workers**（調整役がループを回す）と **Prompt Chaining**（朱入れを次の執筆の入力にする）を採用した例である。課題が十分に簡単なら 1スキルのままでよいが、その判断は第2.5節に従い、SW105に理由を残す。

## 3. 二重構造：自然言語レイヤーとプログラムレイヤー

エージェント定義は2つのレイヤーで構成される。**どちらに置くかの判断を誤ると、品質が構造的に不安定になる。**

### 3.1 責務分担

| 観点 | 自然言語レイヤー | プログラムレイヤー |
| :--- | :--- | :--- |
| 実体 | `AGENTS.md`（ルール）、`skills/<name>/SKILL.md`（手順）、`references/` 配下の知識・ひな形 | スクリプト、ツール、前処理・後処理、構文チェッカー、CI |
| 得意な仕事 | 文脈依存の知的な意思決定、意図の解釈、ワークフローの制御、判断基準の提示、例示による教示 | 厳密な変換、網羅的な照合、決定論的な検証、集計、ファイル入出力 |
| 苦手な仕事 | 網羅的な数え上げ、厳密な文字列処理、同一結果の再現 | 文脈の解釈、曖昧な入力からの意図推定、判断基準の柔軟な適用 |
| 変更コスト | 低い（書き換えれば即反映） | 中程度（テストの更新が必要） |
| 検証方法 | Eval Dataset（確率的・合格率で判定） | 単体テスト（決定論的・Pass/Failで判定） |
| 失敗の様相 | 幻覚・逸脱・指示漏れ・解釈のばらつき | 例外・誤った出力（ただし再現可能） |

### 3.2 振り分け判定フロー（3問に順に答える）

要求または処理を1つ取り上げ、次の3問に順に答える。

1. **出力が入力から一意に決まるか**（同じ入力なら常に同じ出力であるべきか） → **Yes ならプログラムレイヤー**。
2. **取りこぼしが許されない網羅的な照合・集計か** → **Yes ならプログラムレイヤー**。件数が増えるほど自然言語レイヤーは取りこぼす。
3. **文脈や意図の解釈が必要か**（正解が状況によって変わるか） → **Yes なら自然言語レイヤー**。

3問すべてが No の場合は、**プログラムレイヤーを選ぶ**（決定論的な方が検証が容易であり、安全側である）。

> **判定例**: 「全要求IDに対応するテストIDがあるかを照合する」は問2がYesなのでプログラムレイヤー（`tools/dada_check.py`）。「要求の検証条件がProduct Ownerの意図と合っているかを判断する」は問3がYesなので自然言語レイヤー（レビュアースキル）。DADAプロセス自身がこの判定に従って構成されている。

### 3.3 レイヤー間の契約（一貫性の遵守）

2つのレイヤーが食い違うと、エージェントは自然言語の記述を信じて誤動作する。以下を不変条件とする。

1. **単一情報源の原則**: 同じ知識を2箇所に書かない。自然言語レイヤーが判定基準の一覧を持ち、プログラムレイヤーも同じ一覧を持つ場合、どちらが正であるかを明記し、他方は参照だけにする。
2. **定数の二重定義の禁止**: 禁止語リスト・閾値・パス・IDの書式のような定数は、一方に定義してもう一方はそれを読む。二重に書く場合は、両ファイルに「他方と同一に保つこと」というコメントを相互に書く。
3. **手順とツールの引数の一致**: `SKILL.md` に書いたコマンド行は、実際のスクリプトの引数・オプションと一字一句一致させる。スクリプトの引数を変えたら、同じコミットで `SKILL.md` を直す。
4. **参照パスの実在**: `SKILL.md` が参照するファイルパスは、すべて実在すること。死んだ参照はエージェントの停止か推測を招く。
5. **終了コードの意味の一致**: スクリプトの終了コードの意味（0/1/2）を、`SKILL.md` の手順に書かれた分岐と一致させる。

> この5項目は、レビュアースキルの「一貫性レビュー」の観点であり、`tools/agent_def_check.py` が機械的に検出できる範囲（4・5の一部）はスクリプトへ委譲する。

## 4. 評価基準の二重化（Eval Dataset と単体テスト）

### 4.1 なぜ二重化が必要か

エージェント定義の振る舞いは確率的であり、1回の実行結果は合否の証明にならない。1回だけ成功したことをもって「動作する」と報告してはならない。一方で、プログラムレイヤーは決定論的であり、単体テストで厳密に検証できる。**レイヤーごとに検証方法を切り替える**ことで、過剰な評価コストと検証漏れの両方を避ける。

| レイヤー | 検証方法 | 合否の判定 | 実行区分（SWP6相当の文書での記載） |
| :--- | :--- | :--- | :--- |
| プログラムレイヤー | 単体テスト・スクリプト実行 | 決定論的 Pass/Fail（1回で確定） | **自動** |
| 自然言語レイヤー | Eval Dataset（N回試行） | 合格率が閾値以上（許容範囲で判定） | **評価** |
| 両レイヤーにまたがるがスクリプト化しない確認 | AIがブラウザ・GUI等のツールで実施し、期待値と照合 | Pass/Fail | **手動**（実施者はAI。主観的検収はSWP6に書かず Phase 5） |

### 4.2 プログラムレイヤーの単体テスト仕様

従来型プログラムと同じ。テスト項目（`TC-001` 形式）に、前提条件・入力データ・期待される出力を具体値で書く。テストコードのコメントに対応する `TC-ID` を明記する（機械チェックがコードとの対応を照合する根拠になる）。

### 4.3 自然言語レイヤーの評価セット（Eval Dataset）

評価セットは「入力プロンプト」と「期待される振る舞い」の対からなる。**期待される振る舞いは、判定者が機械的に確認できる要素に分解して書く。**

| 記述欄 | 書き方 | 悪い例 → 良い例 |
| :--- | :--- | :--- |
| 入力プロンプト | 実際に人間が入力する文をそのまま書く（省略・要約をしない） | 「議事録の依頼」→「以下の会議メモから議事録を作ってください。（メモ本文…）」 |
| 必須要素 | 出力に必ず含まれる要素を列挙する（見出し名・項目・ID・形式） | 「必要な情報が含まれること」→「見出し『決定事項』『TODO』『次回議題』の3つを含み、TODOの各行に担当者名と期限を含むこと」 |
| 禁止要素 | 出力に現れてはならない要素を列挙する（幻覚・逸脱の検出点） | 「間違いがないこと」→「入力メモに存在しない人名・日付を含まないこと」 |
| 判定方法 | 誰がどう判定するかを1つ選ぶ（下記3種） | 「目視で確認」→「決定論的アサーション（正規表現による見出しの存在確認）」 |
| 合格基準 | 試行回数と合格率の閾値を数値で書く | 「安定して動くこと」→「10回試行して9回以上合格すること（合格率90%以上）」 |

**判定方法の3種**（上から順に優先して選ぶ。決定論的に判定できるものを自然言語判定に回さない）

| 判定方法 | 内容 | 使う場面 |
| :--- | :--- | :--- |
| 決定論的アサーション | 出力に対する文字列・正規表現・構造の検査をスクリプトで行う | 見出しの存在、形式、ID書式、禁止語の不在 |
| ルーブリック採点 | 観点ごとに0/1で採点する採点表を作り、人間またはAIが埋める | 要約の網羅性、指摘の具体性 |
| LLM-as-judge | 別の会話・別のエージェントに採点を依頼する | ルーブリック採点を自動化する場合 |

> **LLM-as-judge を使う場合の必須条件**: 採点用のルーブリック（観点と0/1の基準）を文書に明記すること。「良いかどうか判断させる」だけの採点は再現性がなく、評価として成立しない。また、**評価対象のエージェントと採点者を同一の会話で兼任させてはならない**（自己採点は甘くなる）。

### 4.4 許容範囲（試行回数と合格率）の決め方

| 要求の重要度 | 試行回数の目安 | 合格率の閾値の目安 |
| :--- | :--- | :--- |
| Must（欠けると使えない） | 10回以上 | 90%以上 |
| Should（品質に影響する） | 5回以上 | 80%以上 |
| Could（あると良い） | 3回以上 | 60%以上 |

- 上記は**出発点の目安**である。Product Ownerが別の値を指示した場合はそれに従い、指示がない場合は上表を採用して要求仕様書に明記する（AIが黙って決めない）。
- **試行回数を1回にしてはならない。** 1回の成功は確率的振る舞いの証明にならない。
- 合格率が閾値を下回った場合の対応は、①自然言語レイヤーの指示を具体化する ②決定論的に判定できる部分をプログラムレイヤーへ移す ③要求の許容範囲をProduct Ownerと再合意する、のいずれかである。**評価セットを緩めて通すことは禁止**する（テストの改ざんに相当する）。
- 評価の実行結果は `docs/process/eval_report.md` に記録する（試行回数・合格数・合格率・閾値・判定）。

## 5. ポカヨケ設計基準（Mistake-Proofing）

エージェント定義は「失敗しうる指示」を書いた時点で失敗が確定する。以下の8基準を全ユニットに適用し、設計書に適用状況を記載する。

| # | 基準 | 実装方法 | 防ぐ失敗 |
| :---: | :--- | :--- | :--- |
| 1 | **思考過程の強制** | **`SKILL.md` に「思考過程を必ず出力する」と明示する**（Transparency）。作業開始時に現在地・根拠・方針を定型で宣言させる。全応答の末尾に進行表示を出させる | 現在地の喪失、無言の方針変更 |
| 2 | **ルート固定パス** | 入力・出力のファイルパスを手順内に literal で固定する。パスを推測・探索させない | 出力先の散逸、参照ミス |
| 3 | **二重出力の禁止** | 成果物の全文はファイルにのみ書き、応答にはパスと要約行だけを出させる | トークンの浪費、ファイルと応答の食い違い |
| 4 | **statusコード制御** | 検証スクリプトの終了コードで合否を伝える（0=合格 / 1=不合格 / 2=実行エラー）。手順側は終了コードで分岐する | 「確認したつもり」の虚偽報告 |
| 5 | **ラベルの固定** | 機械チェックが読む見出し・フィールド名・列名を一字一句固定し、言い換えを禁止する | 検証の空振り（機械が黙って通す） |
| 6 | **ループ上限とエスカレーション** | 反復には必ず上限回数と、打ち切った後の行き先（人間への報告）を定める | 停止しない改善ループ |
| 7 | **禁止事項の明示** | 「やってはならないこと」を独立した節に列挙する。特に、検証を通すために検証自体を書き換える行為を明示的に禁止する | テストの改ざん、承認の推定 |
| 8 | **完了条件のチェックリスト化** | 完了報告の前に、保存済みファイルを読み直して消化するチェックリストを置く | 「書いたつもり」の抜け |

### 5.1 設計時の確認（エージェント定義の各ユニットに対して）

- [ ] 入力と出力のパスが固定されている（推測させていない）
- [ ] 自然言語レイヤーのスキルに、思考過程の出力が手順として明示されている（Transparency）
- [ ] `description`・手順・出力形式が、エージェントが迷わない具体さである（ACI）
- [ ] 1スキルに複数の役割（特に執筆と評価）が詰め込まれていない（Simplicity）
- [ ] 判断が必要な箇所に、判断基準または例示（❌/✅）がある
- [ ] 反復処理に上限回数と打ち切り後の行き先がある
- [ ] 検証手段がある（単体テストか評価セットのいずれか）
- [ ] 禁止事項が列挙されている
- [ ] ツールを呼ぶ場合、ACI仕様（名前・入力型・出力型・エラー・終了コード・使用例）が定義されている
- [ ] 決定論的に処理できる作業を自然言語レイヤーに残していない

## 6. エージェント定義の標準ファイル構成

成果物のファイル構成は、以下を既定とする（対象のAIエージェント製品の仕様が異なる場合は、その仕様を優先し、設計書のADRに理由を記録する）。

```text
.agents/
  AGENTS.md                    # ルール（ガードレール）。常時適用される不変条件
  skills/
    <skill-name>/
      SKILL.md                 # 手順（能力）。frontmatter に name と description が必須
      references/              # 知識・ひな形（スキルから参照する本棚）
tools/
  <tool-name>.py               # プログラムレイヤー。決定論的な検証・変換
docs/
  guidelines/                  # 判断基準（オンデマンドでロードする）
  templates/                   # ひな形（コピーして埋める）
```

**frontmatter の規約**（自然言語レイヤーのポカヨケ）

| 項目 | 規約 |
| :--- | :--- |
| `name` | ディレクトリ名と一致させる。英小文字とハイフンのみ |
| `description` | 「**いつ**使うか」を先頭に書く。エージェントは会話開始時に `description` だけを見て発動を判断するため、機能の説明ではなく発動条件を書く。**他スキルの description と重複させない**（Routing の前提。ACI） |

## 7. アンチパターン（作ってはならないエージェント定義）

| アンチパターン | 何が起きるか | 正しい設計 |
| :--- | :--- | :--- |
| 1つの `SKILL.md` に複数の役割を詰め込む（執筆と評価の同居を含む） | 発動条件が曖昧になり、必要な手順がロードされない・不要な手順までロードされる。自己採点が甘くなる | 役割ごとにスキルを分ける（第2.5節）。Evaluator-Optimizer を使うなら Generator と Evaluator を別スキルにする |
| 簡単な課題だからと、役割分割の吟味自体を省略する | 詰め込みスキルが既定になり、後から分割する手戻りが大きい | 分割案を一度検討し、採用しない理由をSW105に書く |
| `SKILL.md` に思考過程の出力を書かない | 人間が判断を追跡できず、誤りの原因が分からない | Transparency として「思考過程を必ず出力する」と手順に明示する |
| `description`・手順・出力形式が粗い | エージェントが迷い、別スキルを呼ぶ・出力先を推測する | ACI として発動条件・手順・出力形式を具体的に書く |
| 5つの設計パターンを吟味せずに1スキルで実装する | 効くパターンを取りこぼす。後工程で分割しにくくなる | 5つすべてについて採用／不採用と理由をSW105・SW205に残す（採用は任意） |
| 5つの設計パターンを全部無理に採用する | 簡単な課題に過剰な構造を足し、Simplicity に反する | 効かないパターンは不採用とし、理由を書く |
| 網羅的な照合を自然言語で指示する | 件数が増えるほど取りこぼし、「確認したつもり」の報告になる | プログラムレイヤーへ委譲し、終了コードで合否を受け取る |
| スキル間で「他スキルの手順と同一」と参照する | 参照解決に失敗して手順が実行されない | 各スキル内で手順を完結させる（重複を許容する） |
| 評価を1回の実行で判定する | 確率的な揺れを検出できず、再現しない成功を成功と報告する | 評価セットでN回試行し、合格率で判定する |
| 会話履歴の要約をサブエージェントへ渡す | 未確定の推測が確定事項として下流へ伝播する | 承認済み文書とサマリーのみを渡す |
| 検証が落ちたときに検証側を書き換える | 品質の証明が失われる | 実装側を直す。要求が誤っている場合は要求の変更をProduct Ownerに提案する |
| 上限のない自律ループを回す | 停止せず、コストと時間を消費し続ける | 上限回数と打ち切り後の行き先を定める |
