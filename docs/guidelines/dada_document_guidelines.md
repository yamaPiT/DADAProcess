# DADAプロセス ドキュメント作成ガイドライン

## 1. 目的と適用範囲
本ガイドラインは、DADA (Document-and-Agent-Driven Agile) プロセスにおいて、AIエージェントが開発ドキュメントを作成・更新するための標準構成ルールを定める。
DADAプロセスで作成する開発成果文書は以下の3種類を基本とする（番号はテストファーストの作成順）。
1. **`SW105`: ソフトウェア要求仕様書**（Phase 1 で作成）
2. **`SWP6`: ソフトウェア総合テスト仕様書・報告書**（Phase 2 で計画（1〜4章）を作成、Phase 4 で結果・報告（5〜6章）を追記）
3. **`SW205`: ソフトウェアアーキテクチャ設計書**（Phase 3 で作成）

※ Product Ownerから開発成果のプレゼンテーション資料を求められた場合のみ、Phase 4完了後またはPhase 5で **`PRES101`（開発成果プレゼンテーション）** を作成する。

## 2. エージェントへの基本ルール（Agent Instructions）
* **一貫性と追跡可能性**: 要求（`SW105`）→ 総合テスト仕様（`SWP6`）→ アーキテクチャ設計（`SW205`）の間で内容に矛盾や飛躍がなく、トレーサビリティID（`REQ-001` ↔ `TC-001` ↔ `UNIT-001`）が機械的に照合できること。
* **出力形式とOffice連携**: トークン消費量を抑えて推論精度を高めるため、通常の開発工程では `docs/artifacts/` にMarkdown形式（`.md`）のみを出力する。既存のOffice文書・PDFから始める場合や、Product OwnerからOffice文書（`.docx` / `.xlsx` / `.pptx` / `.pdf`）への変換を求められた場合に限り、スキル `.agents/skills/office-document/SKILL.md`（`tools/office_io.py`）を使用する。
* **ワークスペース憲法への準拠**: ドキュメント絶対主義、承認ゲート／自律ゲート、アテンション・リセット、役割の純化、および機械的検証の詳細は `.agents/AGENTS.md` に従うこと。

## 3. ドキュメント別 標準目次構造（作成順）

> [!NOTE]
> 以下の目次構造を具体化した**記入用スケルトン（記入例・AI向け指示コメント付き）**が用意されている。新規作成時は見出し構造を自分で組み立てず、必ずスケルトン（またはひな形）のコピーを出発点とすること。
> - **従来型プログラム開発の場合**:
>   - `SW105`: `.agents/skills/requirements-engineer/references/SW105_skeleton.md`
>   - `SWP6`: `.agents/skills/test-engineer/references/SWP6_skeleton.md`
>   - `SW205`: `.agents/skills/architect/references/SW205_skeleton.md`
> - **エージェント定義開発の場合**（Phase 0で自動切り替え、詳細は `docs/guidelines/agent_design_principles.md`）:
>   - `SW105`: `docs/templates/agent/phase1_agent_requirements_template.md`
>   - `SWP6`: `docs/templates/agent/phase2_agent_eval_spec_template.md`
>   - `SW205`: `docs/templates/agent/phase3_agent_design_template.md`

### 【A】 ソフトウェア要求仕様書 (`SW105` — Phase 1)
要求定義の最終成果物である。後工程（総合テスト仕様策定、アーキテクチャ設計）で第三者が機械的に合否判定できるレベルまで具体化して記述すること。

* **1. 概要**: 本ソフトウェアの存在意義と前提を定義する。
  * 1.1 目的と位置づけ: 解決する課題とシステム全体における役割。
  * 1.2 適用範囲: 対象とするシステムの境界線（スコープ内・スコープ外）。
  * 1.3 用語定義: 開発で共通使用するドメイン用語や略語（1概念1名称）。
* **2. システム全体構成**:
  * 2.1 システム構成概要: ハードウェアおよび連携する外部システムを含めた全体構成。
  * 2.2 ソフトウェアの構成要素: 管轄する主要ブロックの概要（※内部のモジュール分割は `SW205` で行う。エージェント定義開発では2.3 役割分割方針、2.4 三原則の適用、2.5 設計パターンの吟味を追加する）。
* **3. 制約条件と前提事項**: 遵守すべき境界条件。
  * 3.1 ハードウェア制約（エージェント定義では実行環境制約）
  * 3.2 ソフトウェア環境: OS、開発言語、通信プロトコル（Product Owner指定分のみ）。
  * 3.3 準拠規格: 法令や業界標準。
* **4. 機能要求**: システムが「何をしなければならないか」を正常系・異常系の両面から定義する。
  * 4.1 ユースケースとシナリオ: 利用者または外部システムとのやり取り。
  * 4.2 機能詳細: `#### REQ-001: （要求名）` のブロック形式で記述する。各要求には「概要」「入力 / 処理 / 出力」「異常系」「検証条件 (Acceptance Criteria)」「優先度」を含める（エージェント定義では「レイヤー」を追加する）。
* **5. 外部インタフェース要求**:
  * 5.1 ユーザインタフェース (UI) / 5.2 ハードウェアインタフェース / 5.3 ソフトウェアインタフェース
* **6. 非機能要求（性能・品質等）**: 定量的な数値目標を記述する。
  * 6.1 性能・効率性 / 6.2 信頼性・安全性（エージェント定義では確率的振る舞いの許容範囲を含む） / 6.3 保守性・拡張性 / 6.4 セキュリティ
* **7. その他・特記事項**: 未決定事項（TBD、解消の時期と方法を併記）や引き継ぎ事項。

### 【B】 ソフトウェア総合テスト仕様書・報告書 (`SWP6` — Phase 2 計画 / Phase 4 報告)
「テスト仕様書」と「テスト報告書」を兼ねる。**まず計画フェーズ（Phase 2: アーキテクチャ設計より先）で1〜4章を作成**し、Phase 4でAIがテストを実施したあと**結果（5〜6章）を追記して報告書として完成**させる。計画時点で設計が未確定のため、テストフレームワーク等の設計依存項目は「TBD（Phase 3で確定）」と明記する。人間が5〜6章に結果を追記してはならない。

**【計画フェーズ（Phase 2 で作成）】**
* **1. テストの概要と目的**:
  * 1.1 目的 / 1.2 参照ドキュメント / 1.3 対象範囲とバージョン
* **2. テスト環境とシステム構成**:
  * 2.1 システム構成 / 2.2 テスト設備・ツール（設計依存項目は `TBD（Phase 3で確定）`）
* **3. テスト方針**:
  * 3.1 合否判定基準 / 3.2 異常系・例外テスト方針 / 3.3 AIが非スクリプトで実施する項目（実行区分「手動」。エージェント定義では3.3 評価方針、3.4 手動項目）
* **4. テストシナリオと項目詳細（計画）**:
  * `SW105` の全 `REQ-ID` に対して正常系1件以上＋異常系・境界値1件以上を定義するMarkdown表（固定列: `テストID` / `対象要件` / `シナリオ` / `前提条件` / `入力データ` / `期待される出力` / `実行区分`）。
  * 網羅性の確認（全REQ-ID数・対応TC作成済み数・差し戻し中件数）。エージェント定義では4.3節に評価セット定義（`EV-001` 形式）とルーブリックを記述する。

**【実行・報告フェーズ（Phase 4 でAIが追記）】**
* **5. テスト実行結果**: Phase 4でAIが実施した全テスト項目の結果。
  * 5.1 実行環境の記録 / 5.2 結果詳細（列: `テストID` / `実行日時` / `検査結果（Pass / Fail）` / `実際の出力・エラー` / `備考`）。エージェント定義では5.3節に評価セット実行結果の集計を追記する。
* **6. 総合判定と不具合報告**:
  * 6.1 検出された不具合（`BUG101` の `B-ID` 参照） / 6.2 総合判定（AIが3.1の基準に基づき `Pass / Fail` を記入する）。

### 【C】 ソフトウェアアーキテクチャ設計書 (`SW205` — Phase 3)
`SW105` と `SWP6` を満たすための「静的構造」と「動的振る舞い」を定義する。先行して承認された `SWP6` のすべてのテスト項目（自動・手動・評価）が実行・観測可能な構造であること。

* **1. 概要**:
  * 1.1 目的と位置づけ / 1.2 適用範囲 / 1.3 参照ドキュメント / 1.4 用語定義
* **2. システム構成**:
  * 2.1 システム全体構成（外部との境界、Mermaid図推奨） / 2.2 主たるソフトウェア要素
* **3. ソフトウェア構成（静的構造）**: 内部ユニット分割と依存関係。
  * 3.1 ソフトウェア全体構成: 基本方針とコンポーネント図（Mermaid図）。エージェント定義では5つの設計パターンの吟味表と成果物ファイル構成を含める。
  * 3.2 機能ユニットの定義: `#### UNIT-001: （ユニット名）` のブロック形式で、「責務」「対応要求」「公開インターフェース」「依存先」「検証条件」を定義する（エージェント定義では「レイヤー」「成果物パス」「適用するポカヨケ」を追加する）。
* **4. 制御方式（動的振る舞いとリソース割り当て）**:
  * 4.1 メモリ構成とレイアウト（エージェント定義ではコンテキスト管理方針）
  * 4.2 ソフトウェア制御方式: 並行処理・状態遷移方針と主要ユースケースのシーケンス図（Mermaid図1つ以上）。エージェント定義ではループの上限回数と打ち切り後の行き先を含める。
  * 4.3 性能見積り: `SW105` の性能要求に対する定量的な見積もり。
* **5. 機能ユニット詳細**: 外部公開インタフェースの詳細（エージェント定義ではプログラムレイヤー全ユニットのACI仕様表）。
* **6. システムで扱うデータ**: 共有データ構造、DBスキーマ、または読み書きするファイル一覧。
* **7. 例外・異常処理一覧**: `SW105` の異常系要求と1対1で対応する検知方法とリカバリ手順の表。
* **8. その他・特記事項**:
  * 8.1 アーキテクチャ決定記録（`ADR-001` 形式：背景・決定・理由・捨てた選択肢）
  * 8.2 `SWP6` のTBD解消表
  * 8.3 トレーサビリティ表（`REQ-ID` ↔ `UNIT-ID` 対応表）
  * （エージェント定義では 8.4 ポカヨケ適用状況表を追加する）

## 4. 執筆推敲と自己校正の基準 (Writing & Self-Correction Criteria)
エージェントは `.agents/AGENTS.md` 第7節「共通行動指針」に従い、以下の基準とツールを組み合わせて品質を作り込むこと。

1. **執筆時の予防と日本語構造推敲（作成者スキル）**:
   - `docs/guidelines/asdoq_writing_rules.md`（ASDoQ執筆ルール12箇条）をロードして執筆する。
   - 書き出し後は必ず① `python tools/style_check.py snapshot` で推敲前の意味シグネチャを保存する。次に②スキル `.agents/skills/JP-Humanizer/SKILL.md` と `python tools/style_check.py lint` で自然な日本語へ更新する。最後に③ `python tools/style_check.py verify` で元の意味・ID・数値・否定極性が保持されていることを確認する。
2. **機械的検証の委譲（作成者・レビュアースキル共通）**:
   - ID対応の網羅性照合や曖昧語・指示語の走査、表の空欄検出、未実装ユニットの検出は推論で行わない。必ずスキル `dada-check`（`python tools/dada_check.py all`、Phase 4では加えて `report`、エージェント定義では加えて `python tools/agent_def_check.py`）に委譲する。
3. **内容と読みやすさの自己校正（レビュアースキル）**:
   - 通常時は `docs/guidelines/asdoq_checklist.md`（軽量版）、Product Ownerから厳密校正の指示があった場合は `docs/guidelines/asdoq_model_markdown.md`（フル版）をロードする。
   - 機械が形式を保証したうえで、レビュアーは**内容の妥当性（要求の適否・テストの十分性・設計の適切さ・用語の一貫性・論理矛盾）**と**文章の読みやすさ（`JP-Humanizer` 8観点＋`style_check.py lint`）**を厳しく評価し、指摘を `docs/artifacts/REV101_*.md` に記録する。
