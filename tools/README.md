# tools — DADAプロセスの検証ツール

このディレクトリには、DADAプロセスの開発文書・ソースコード・エージェント定義を**機械的に検証**するツールを置きます。

| ツール | 対象 | 使う場面 |
| :--- | :--- | :--- |
| `dada_check.py` | 開発文書（SW105 / SWP6 / SW205）とソースコード | **常時**（全Phaseの承認ゲート前） |
| `agent_def_check.py` | エージェント定義の成果物（`SKILL.md`・参照パス・ツール・評価記録） | **開発対象がエージェント定義の場合**（Phase 3〜4） |

## なぜツールが必要か

DADAプロセスのレビュー手順には、「すべてのREQ-IDに対応するTC-IDがあるか照合する」「曖昧語を検索する」「表の空欄を走査する」といった**網羅的な機械作業**が多く含まれます。
この種の作業をLLMの推論に任せると、次の3つの問題が起きます。

| 問題 | 具体例 |
| :--- | :--- |
| **取りこぼし** | 要求が20件あると、後半のIDの照合が雑になる |
| **幻覚（虚偽の完了報告）** | 実際には照合していないのに「全件確認しました」と報告する |
| **トークンの浪費** | 照合のために3つの文書の全文をコンテキストへ読み込む |

`dada_check.py` はこれらを決定論的なスクリプトに置き換えます。AIは「文書を全文読んで数える」代わりに「コマンドを1回実行して短い結果を読む」だけで済み、**精度と省トークンを同時に達成**します。

そのうえで、AIは機械では判定できない本質的な検証（要求の妥当性、テストの十分性、設計の適切さ）に思考を集中できます。

## dada_check.py

Python 3.8以降の標準ライブラリのみで動作します。外部パッケージのインストールは不要です。

### 使い方

```bash
# 全チェック（推奨。承認ゲートの前に必ず実行する）
python tools/dada_check.py all

# 個別に実行することもできる
python tools/dada_check.py trace    # ID対応（REQ ↔ TC ↔ UNIT）
python tools/dada_check.py lint     # 文書の書き方（曖昧語・指示語・空欄・TBD等）
python tools/dada_check.py code     # ソースコードと設計・テストの対応
python tools/dada_check.py status   # REV101 / BUG101 の未解決件数
python tools/dada_check.py report   # 総合テスト報告書（SWP6 5〜6章）の完成。Phase 4のゲート前のみ。all には含まれない

# サマリ1行だけ欲しいとき
python tools/dada_check.py all --summary
```

`python` で起動できない環境では `python3 tools/dada_check.py all` または `py -3 tools/dada_check.py all` を試してください。

### 出力

- 標準出力に完全なレポートを表示します。
- 同じ内容を `docs/process/check_report.md` に保存します（Product Ownerが後から確認できます）。
- 終了コード: `0` = High指摘なし / `1` = High指摘あり / `2` = 実行エラー

### 検出する内容

| チェック | 検出する欠陥 |
| :--- | :--- |
| `trace` | REQ-IDに対応するTC-ID/UNIT-IDの欠落、存在しないIDの参照（幻覚ID）、検証条件・公開インターフェースの未記述、実行区分の未記入、UNIT間の循環依存、テストIDの重複 |
| `lint` | 規範的記述（検証条件・期待値・責務等）に残った曖昧語・指示語、TBDの解消計画の欠落、表の空欄と列数不一致、スケルトンの残骸（【AIへの指示】・記入例ID・プレースホルダ）、コードブロックの閉じ忘れ、標準目次の章の欠落 |
| `code` | 実装されていないUNIT-ID（またはヘッダのID記載漏れ）、宣言された成果物パスの不在、「自動」区分なのにテストコードがないTC-ID、skip・onlyによるテストの無効化 |
| `status` | REV101・BUG101に残った未解決行 |
| `report` | 4章の各TC-IDが5.2に無い、検査結果が Pass/Fail でない、6.2の総合判定が未記入または5章と矛盾、4.3のEV-IDが5.3に未転記。**Phase 4のゲート前に実行する。`all` には含まれない**（Phase 2の空5〜6章を欠陥にしないため） |

### 重要度の意味

| 重要度 | 意味 | 承認ゲートでの扱い |
| :--- | :--- | :--- |
| **High** | 後工程を開始できない欠陥 | 解消するか、残課題としてProduct Ownerに明示報告する |
| **Mid** | 品質を損なうが工程は進められる | 原則として解消する |
| **要確認** | 機械では判定できず、人間またはAIの判断が必要 | 判断してから報告する |

### `code` の照合方法 — 2通り

`code` チェックは、UNIT-IDの実装確認を2通りの方法で行います。設計書（SW205）の記述によって自動的に切り替わります。

| 設計書の記述 | 照合方法 | 使われる場面 |
| :--- | :--- | :--- |
| UNITに `成果物パス` の記述**なし** | リポジトリ内のソースツリーを走査し、UNIT-IDを含むファイルを探す | 従来型プログラム開発（既定） |
| UNITに `成果物パス` の記述**あり** | 宣言されたパスのファイルが実在し、UNIT-IDを含むかを直接照合する | エージェント定義開発 |

エージェント定義の成果物は `.agents/` や `tools/` 配下に置かれますが、これらはソースツリー走査の除外ディレクトリです（開発対象のコードではなく開発の道具であるため）。走査だけに頼ると全ユニットが「未実装」と誤検出され、終了コードが 0 になりません。そこで**設計書が宣言したパスを正解として照合**します。

> [!NOTE]
> 従来型プログラム開発のSW205ひな形は `成果物パス` の欄を持たないため、**この分岐は起動せず、照合結果は改訂前と完全に同一です**（回帰テストで出力の一致を確認済み）。宣言パスの照合は緩和ではなく、「宣言したパスにファイルが存在しない」「UNIT-IDの記載がない」を High として検出します。

なお、プログラムレイヤーのテストコードは `tools/` ではなく **`tests/` 配下**に置いてください。`tools/` は走査除外のため、そこに置いた「自動」区分のテストコードは検出されません。

### 誤検出の扱い

`lint` の一部（プレースホルダの残存、標準目次の章の欠落）は、意図的な記述との区別が機械ではつきません。これらは **要確認** として報告されます。
特に、Product Ownerがテンプレート（IEEE29148等）を指定した場合、標準目次との差異は正常です。**指摘を機械的に鵜呑みにせず、AIが妥当性を判断**してください。

## agent_def_check.py

開発対象が**エージェント定義**の場合に使用します。`dada_check.py` は一切変更しておらず、本スクリプトは独立した追加ツールです（従来型プログラム開発の検証結果は従来と完全に同一です）。

### なぜ別ツールが必要か

エージェント定義の成果物は、ソースコードではなく**AIに読ませる自然言語の指示書（`SKILL.md` 等）とツール群の二重構造**です。ここで壊れやすいのは「自然言語側の記述とプログラム側の実体がずれる」ことです。

| 壊れ方 | 何が起きるか |
| :--- | :--- |
| 参照パスの死リンク | AIが「`references/foo.md` を読め」と指示されたファイルを開けず、手順が中断する |
| コマンド行と実体の不一致 | `SKILL.md` に書かれたコマンドが存在しない引数を渡し、実行が失敗する |
| frontmatterの欠落 | スキルが `description` を持たず、Progressive Disclosureで発見されない |
| UNIT-IDの記載漏れ | 設計書のユニットと成果物ファイルの対応が追跡できなくなる |

これらはいずれも**決定論的に検出できる**ため、AIの推論ではなくスクリプトで検証します。

### 使い方

```bash
# 全チェック（Phase 4の完了判定で必ず実行する）
python tools/agent_def_check.py all

# 個別に実行することもできる
python tools/agent_def_check.py skill     # frontmatter（name/description）とディレクトリ名の一致
python tools/agent_def_check.py command   # 自然言語に書かれたコマンド行と実スクリプト・引数の一致
python tools/agent_def_check.py unit      # SW205の成果物パスの実在とUNIT-IDの記載
python tools/agent_def_check.py eval      # SWP6のEV-IDが eval_report.md に記録されているか

# 検査対象ディレクトリを指定する場合
python tools/agent_def_check.py all --scan .agents/skills

# サマリ1行だけ欲しいとき
python tools/agent_def_check.py all --summary
```

### 出力

- 標準出力に完全なレポートを表示します。
- 同じ内容を `docs/process/agent_def_check_report.md` に保存します（Git管理対象外）。
- 終了コード: `0` = High指摘なし / `1` = High指摘あり / `2` = 実行エラー

### 検出する内容

| チェック | 検出する欠陥 | 重要度 |
| :--- | :--- | :--- |
| `skill` | `SKILL.md` のfrontmatter欠落、`name`/`description` の未記入、`name` とディレクトリ名の不一致 | High |
| `skill` | 自然言語に書かれた参照パスの死リンク | High |
| `command` | 記述されたコマンドのスクリプトが存在しない、渡している引数がスクリプトに定義されていない | High |
| `unit` | SW205の `成果物パス` が存在しない、成果物ファイルにUNIT-IDの記載がない | High |
| `eval` | SWP6の「評価」区分のEV-IDが `eval_report.md` に未記録、試行回数が1回として記録されている | High |
| `skill` | 「禁止事項」節の欠落、ループ上限・エスカレーション条件の未記述（ポカヨケ） | 要確認 |

### 誤検出を避けるための仕様

自然言語文書はファイルパスに似た文字列を多く含むため、以下は**存在チェックの対象外**です。

- 拡張子を持たないトークン（`references/` のようなディレクトリの総称）
- `docs/artifacts/` 配下のパス（Phase 1以降に生成される出力先であり、定義時点では存在しないのが正常）
- 記入例・スケルトンを示す行（例示であってリンクではない）

参照パスは、リポジトリルート基準と**参照元ファイルの親ディレクトリ基準**の両方で解決を試みます。どちらかで見つかれば正常と判定します。

## ツールが使えない環境について

Pythonが利用できない環境では、各スキルに記述された**手動の走査手順にフォールバック**してください。ツールはあくまで手順の高速化・確実化のための手段であり、DADAプロセスの必須の前提ではありません。
ツールを実行できなかった場合は、その事実を承認ゲートの報告に1行で明記してください（実行したふりをしてはいけません）。

> [!WARNING]
> **自律型では、機械チェックの実行が自律遷移の必須条件です**（`.agents/AGENTS.md` 第10.3節）。Pythonが使えず終了コードを取得できない場合は、自律遷移の条件を満たせないため、**承認ゲート型として人間の承認を求めてください**。
